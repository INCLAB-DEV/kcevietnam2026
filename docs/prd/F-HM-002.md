# F-HM-002: 비즈매칭 모집 (/welcome)

> 로그인은 했지만 **nav 있는 본 서비스에 아직 들어올 자격이 없는** 바이어·참가사가 사는 단독 랜딩. 비즈매칭 신청기간과 `application_status`(ADR-0009)를 보고 "지금 뭘 해야 하는지"(작성·대기·재제출·입장·마감)를 한 화면에서 안내·라우팅한다. **본 서비스(미팅·기업탐색·프로필) 진입은 운영 승인(`approved`) AND 신청기간 종료, 둘 다 충족해야** 열린다.

## Problem Statement

바이어·참가사 입장에서:

- 비즈매칭은 **신청기간(8/26~9/11)에 신청을 받고, 기간이 끝난 뒤 운영 승인을 받은 기업만** 미팅·기업탐색 같은 본 서비스를 쓸 수 있다. 그런데 로그인하자마자 nav가 다 보이면, 아직 신청도 안 했거나 승인도 안 난 사람이 "왜 미팅이 비어 있지?"라며 혼란스럽다.
- 나는 지금 **어느 단계**에 있는지(신청해야 하나, 제출했는데 기다리면 되나, 반려된 건가, 들어가도 되나) 한눈에 알고 싶다.
- 운영자가 "내용을 보완해 다시 내라"고 돌려보냈으면, **무엇을 고쳐야 하는지** 알고 바로 수정에 들어가고 싶다.
- 반려됐다면 막연히 막히는 게 아니라 **어디에 문의해야 하는지** 알고 싶다.
- 신청기간을 놓쳤다면 헛되이 폼을 찾아 헤매는 대신 **마감됐다는 사실**을 분명히 듣고 싶다.

운영(주최/KOTRA) 입장에서:

- 미승인 기업이 본 서비스에 조기 진입하거나 매칭 데이터에 섞이면 안 된다 — **승인된 기업만** 매칭·본 서비스에 들어가야 한다(ADR-0009).

## Solution

바이어·참가사 입장에서:

- 로그인 후, 본 서비스에 들어갈 자격이 안 되면 **`/welcome` 단독 랜딩**에 착지한다(운영자는 `/organizer`로 분기). 글로벌 nav가 없어 "지금은 입장 전 단계"임이 분명하고, 곁길로 새지 않는다.
- 랜딩이 **내 신청기간·상태를 읽어 딱 맞는 안내와 버튼 하나**를 보여준다: 신청서 작성하기 / 주최국 확인 중(제출됨) / 보완 후 재제출(+ 운영자가 남긴 사유) / 반려 안내(+ 문의처) / 미팅 신청 대기중(승인됐고 아직 기간 중) / 입장하기(승인 + 기간 종료) / 신청 마감.
- "신청서 작성하기"를 누르면 역할에 맞는 폼으로 간다(참가사 F-BM-002 `/exhibitor/apply`, 바이어 F-BM-001 `/apply`).
- 승인되고 신청기간이 끝나면 **"비즈니스 미팅 기업 찾기"** 버튼으로 본 서비스(F-HM-001 홈)에 입장한다.

운영 입장에서:

- 본 서비스·매칭 노출은 **`approved` AND 신청기간 종료** 게이트로 강제된다 — 미승인·미충족 사용자는 route-guard가 `/welcome`로 되돌린다.

## User Stories

1. As a 참가사/바이어, I want 로그인 후 본 서비스 자격이 안 되면 nav 없는 전용 랜딩에 도착하기를, so that 지금이 입장 전 단계임을 헷갈리지 않는다.
2. As a 운영자, I want 로그인 후 `/organizer`로 분기되기를, so that 참가자용 입장 게이트와 무관하게 내 대시보드로 바로 간다.
3. As a 참가사, I want 신청기간 중 아직 신청서를 안 썼으면 "신청서 작성하기" 버튼을 보기를, so that 무엇을 해야 할지 바로 안다.
4. As a 참가사, I want "신청서 작성하기"를 누르면 참가사 신청 폼(F-BM-002)으로 가기를, so that 곧장 작성에 들어간다.
5. As a 바이어, I want "신청서 작성하기"가 바이어 신청 폼(F-BM-001)으로 가기를, so that 역할에 맞는 폼을 쓴다.
6. As a 참가사, I want 신청서를 제출(`submitted`)한 뒤에는 "주최국 확인 중" 안내를 보기를, so that 제출이 접수됐고 검토를 기다리면 된다는 걸 안다.
7. As a 참가사, I want 제출 후에는 내용이 잠겨 함부로 안 바뀌기를, so that 검토 중 내가 무심코 바꿔 검토 대상이 흔들리지 않는다.
8. As a 참가사, I want 운영자가 보완을 요청(`changes_requested`)하면 "수정하기" 버튼과 **요청 사유**를 보기를, so that 무엇을 고칠지 알고 바로 재작성에 들어간다.
9. As a 참가사, I want 보완 수정 후 다시 제출하면 검토 대기(`submitted`)로 돌아가기를, so that 정상 재제출 흐름을 탄다.
10. As a 참가사, I want 반려(`rejected`)되면 "반려되었습니다. 사유는 주최측에 문의" 안내를 보기를, so that 막연히 막히지 않고 다음 행동(문의)을 안다.
11. As a 참가사, I want 승인(`approved`)됐지만 아직 신청기간 중이면 "미팅 신청 대기중" 안내를 보기를, so that 승인은 됐고 기간이 끝나면 열린다는 걸 안다.
12. As a 참가사/바이어, I want 승인됐고 신청기간이 끝났으면 "비즈니스 미팅 기업 찾기" 버튼으로 본 서비스에 입장하기를, so that 비로소 미팅·탐색을 시작한다.
13. As a 참가사, I want 신청기간이 끝났는데 신청을 안 했으면 "비즈니스 매칭 신청기간이 마감되었습니다" 안내를 보기를, so that 헛되이 폼을 찾지 않는다.
14. As a 참가사, I want 신청기간이 끝난 뒤 보완 요청 상태로 남았으면 마감 + 문의 안내를 보기를, so that 더 못 고친다는 걸 알고 문의한다.
15. As a 미승인 참가사/바이어, I want 미팅·기업탐색·프로필 같은 본 서비스 URL로 직접 들어가도 `/welcome`으로 되돌려지기를, so that 자격 전에 본 서비스에 잘못 진입하지 않는다.
16. As a 승인된 참가사, I want 이미 입장 자격이 됐을 때 `/welcome`에 가면 본 서비스 홈으로 보내지기를(기간 종료 시), so that 입장 전 화면에 갇히지 않는다.
17. As a 사용자, I want 이 랜딩이 모바일에서도 잘 보이기를, so that 현장에서 휴대폰으로 상태를 확인한다.

## Implementation Decisions

- **단독 렌더(글로벌 nav 없음):** `/welcome`은 `AppShellForRequest`로 감싸지 않고 직접 렌더한다(`/login`과 동일한 "AppShell 밖" 패턴). 세션은 쿠키(`resolveRequestSession`)로 읽는다 — `?as`는 proxy가 쿠키로 미러 후 strip하므로 searchParams로는 보이지 않는다.
- **상태 → 화면 매핑은 deep module(순수 함수):** 입력 `(application_status, 신청기간 개폐)` → 화면 enum 하나로 떨어지는 순수 함수를 `lib/bm/`에 둔다(기존 `lib/bm/` seam·`participant-gate.ts` 자리). 페이지는 이 결과만 렌더. 화면 enum 후보: `write-form` · `under-review`(주최국 확인 중) · `changes-requested` · `rejected` · `meeting-waiting` · `enter-service` · `closed`.
- **매트릭스(참가사 기준, ADR-0002) — 안내 + 액션 버튼:**

  | `application_status` | 신청기간 중 (안내 · 액션) | 신청기간 종료 |
  |---|---|---|
  | `registered`(미제출) | 신청서 작성 안내 · 작성 전=`신청서 작성하기` / 작성 완료(필수 충족)=`수정하기` + `제출하기` | 신청 마감(종단) |
  | `changes_requested` | 보완 요청 안내 + 사유 배너 · `수정하기` + `다시 제출하기` | 신청 마감 + 문의 |
  | `submitted`(미승인) | 주최국 확인 중(제출 후 잠금) · `신청서 보기`(읽기전용) | 주최국 확인 중(승인은 기간 종료 후 진행) |
  | `approved` | 미팅 신청 대기중 · `신청서 보기`(읽기전용) | 비즈니스 미팅 기업 찾기 → 본 서비스(F-HM-001, `/`) |
  | `rejected` | 반려 안내 + 주최측 문의(종단) · `신청서 보기`(읽기전용) | 반려 안내 + 주최측 문의(종단) |

- **저장 vs 제출 분리(2026-06-30):** 신청서 폼은 드래프트 '저장'만 한다(마지막 버튼 `저장하고 나가기` → `/welcome`). 제출(`application_status` 전환)은 `/welcome`의 액션(`ApplicationActions`)이 수행. `registered`는 작성 전(작성하기)/작성 완료(수정하기+제출하기)로 갈리고 **첫 제출도 여기서**. `제출하기`/`다시 제출하기`는 확인 다이얼로그(shadcn `AlertDialog`, "제출하면 수정 불가") 후 실행. (구 예외였던 "미팅 게이트 경유 Visitor 전환은 폼에서 직접 제출"은 자기전환 게이트 폐지로 사라졌다 — 2026-07-02. 이제 예외 없이 모든 제출은 `/welcome`에서.)
- **읽기전용 "신청서 보기":** `submitted`/`approved`/`rejected`는 폼이 읽기전용(참가사 `ProfileView`, 바이어 `StepReview readOnly`)으로 렌더하고 수정 동선을 막는다. 단독 화면이라 "돌아가기"(→`/welcome`) 버튼을 둔다. 편집/읽기전용 판단의 단일 소스는 세션 `application_status`(페이지 prop).
- **역할 분기:** 로그인 후 첫 랜딩 — 운영자 → `/organizer`, 바이어·참가사 → `/welcome`. 랜딩의 "신청서 작성" CTA는 참가사 → `/exhibitor/apply`(F-BM-002), 바이어 → `/apply`(F-BM-001).
- **`changes_requested` vs `rejected`는 서로 다른 상태:** `changes_requested`는 재제출 가능 + 운영자 `review_note`(사유)를 배너로 노출. `rejected`는 종단 + `review_note` 비노출("주최측 문의"). 합치지 않는다.
- **nav 접근 게이트 = `approved` AND 신청기간 종료:** route-guard(`lib/auth/route-guard` + `proxy.ts`)의 nav 경로 판정을 승인 상태로 확장. 미충족 참가자 → `/welcome`. 기존 `SERVICE_OPENS_AT` 단독 타이밍 게이트를 이 합성 게이트가 대체. 운영자는 게이트 면제. 미인증 사용자는 nav 화면 진입 불가 → `/login`(게스트 탐색·`/discover`·`/meetings` 미인증 둘러보기 폐지, 2026-07-02). `/api/*`는 게이트 제외.
- **apply 폼 진입 게이트 = 신청기간 중(전 status 허용):** 폼이 `application_status`로 편집/읽기전용을 정한다(`registered`/`changes_requested`=편집, `submitted`/`approved`/`rejected`=읽기전용 신청서 보기). **신청기간 종료 후에는 status 무관 잠금** → `/welcome`. (종전 "registered/changes_requested만 진입"을, 읽기전용 보기를 폼이 지원하면서 진입 허용+폼 잠금으로 갱신 — 2026-06-30. 제출 후 수정 불가 결과는 동일.)
- **제출 후 잠금(BM-005 정책 반전):** 제출(`submitted`) 후 수정은 막는다(폼이 읽기전용 렌더). 내용을 바꾸는 유일한 경로는 운영자가 `changes_requested`로 돌려보내는 것뿐. (ADR-0002 §3 — 종전 "신청기간이면 제출 후에도 수정 가능"을 반전)
- **세션에 `application_status` 주입:** 게이트가 status를 보려면 세션이 status를 실어야 한다. dev mock(`?as`/`toGuardSession`)에 status를 추가한다. 실연동 시 Cognito 세션 + FastAPI가 내려준 status로 교체(데이터층 진실은 `organization_event_roles.application_status`, ADR-0009).
- **신청기간 출처:** `events.application_start/end`(권위). 현재 데모는 env 임시(`isApplicationOpen`, `lib/bm/application-period`). nav 접근과 apply 작성 가능 여부 둘 다 이 기간을 본다.

## Testing Decisions

- **외부 행동만 검증, 구현 세부 아님.** 상태 매핑 deep module은 입력(status × 기간) → 출력(화면 enum)만 테스트한다.
- **welcome 상태 매핑 순수 함수:** 5 status × {신청기간 중·종료·시작 전} = **매트릭스 전 칸** 단위 테스트(vitest). 시작 전 `approved`는 `meeting-waiting`(루프 방지). ADR-0002 표가 곧 테스트 명세.
- **route-guard 확장:** 기존 `lib/auth/route-guard.test.ts` 패턴을 따라 — 미승인 참가사가 nav 경로 → `/welcome` redirect, `approved`+기간종료 → 허용, 운영자 면제, 신청기간 중 apply는 전 status 진입 허용·종료 후 잠금, `/api/*` 게이트 제외, 승인+기간종료 사용자가 `/welcome` → 홈.
- **프리어트(prior art):** `lib/bm/`의 순수 모듈+테스트(profile-form-state·application-period·participant-gate), `lib/auth/route-guard.test.ts`, `lib/auth/role-branch.test.ts`.
- 페이지 렌더 자체는 무거운 통합 테스트 대신 Playwright(MCP) 라이브 검증으로 확인 — 화면별 CTA·redirect 동선.

## Out of Scope

- **바이어 신청 폼(F-BM-001) 본체** — 별도 세션에서 작업 중. `/welcome`은 바이어를 작성 CTA로 **라우팅만** 한다; 폼 구현·통합은 후속. welcome 매트릭스·게이트는 역할 공용.
- **운영자 승인/반려/보완요청 *행위* UI**(운영자 슬라이스) — 이 게이트는 status를 **읽기만** 한다. 승인 워크플로 화면은 OP-* 소관.
- **실 FastAPI status 연동** — 데모는 mock 세션 + env 신청기간. Cognito 세션·실 API는 별도.
