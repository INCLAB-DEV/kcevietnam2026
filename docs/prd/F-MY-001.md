# F-MY-001: 내 미팅

> 참가사/바이어가 **자기 미팅을 한곳에서 관리**하는 개인 미팅 허브. 보낸 요청·받은 요청을 한 화면에서 조회하고, 받은 요청 수락/거부, 확정 미팅 취소, 참석 Member 지정, 일정·장소 확인을 처리한다. 로그인 직후 첫 랜딩은 `/welcome`(HM-002)이고, 승인·신청기간 게이트를 통과한 본 서비스의 허브는 HM-001(`/`)이며, MY-001은 그 미팅 타임라인 상세를 전원 공용 단일 라우트로 둔다.

## Problem Statement

참가사/바이어 입장에서:

- 내가 **신청한 미팅(보낸 요청)** 과 **상대가 신청한 미팅(받은 요청)** 이 여기저기 흩어져 있으면, 지금 내가 무엇을 해야 하는지(수락할지, 취소할지, 그냥 기다릴지) 한눈에 파악이 안 된다.
- 받은 요청에 빨리 응답하지 않으면 상대를 기다리게 하고, 응답 누락이 노쇼·미확정으로 이어진다. 그런데 "응답이 필요한 건"이 눈에 잘 띄지 않는다.
- 미팅이 확정돼도 **누가 우리 쪽에서 나갈지(참석 Member)** 를 정하지 않으면 현장에서 혼선이 생긴다. 매칭은 기업 대 기업으로 잡혔는데, 실제 나갈 사람은 내가 정해야 한다.
- 확정된 미팅을 무르고 싶을 때(취소), 그게 상대에게 어떤 영향을 주는지 모른 채 가볍게 누르면 매칭 생태계가 망가진다.
- 미팅 시간·장소가 명확하지 않으면 현장에서 헤맨다.

## Solution

참가사/바이어 입장에서:

- **보낸 요청 / 받은 요청** 을 한 화면에서 본다. "내가 신청한 것"과 "상대가 신청해서 내 응답을 기다리는 것"을 구분해 보여줘, 지금 할 일이 분명해진다.
- 받은 요청 중 **응답 대기(`proposed`)** 건수를 배지로 띄워, 처리할 일이 즉시 눈에 띈다.
- 받은 요청에는 **수락/거부**, 내가 보낸 요청과 확정 미팅에는 **취소** 버튼이 상태와 방향에 맞게 노출된다. 상태흐름은 ADR-0005를 따른다 — 일반 바이어/Exhibitor가 받는 건은 `proposed`로 시작해 수락이 필요하고, 초청 바이어가 받는 건은 거부 단계 없이 `accepted`로 바로 확정된다.
- 미팅을 수락(또는 확정)할 때 **우리 쪽 참석 Member를 지정**한다(ADR-0002). 매칭 단위는 기업이고, 나갈 사람은 기업 내부에서 정한다.
- 취소 시 넛지(취소가 매칭 추천 우선순위에 영향을 줄 수 있다는 안내)를 보여 가벼운 취소를 억제하되, 양쪽 누구나 취소는 가능하다.
- 각 미팅의 **시간·장소(Meeting Venue)** 와 상대 기업 정보를 패널에서 확인한다.

## User Stories

1. As a 참가사/바이어, I want 내가 보낸 미팅 요청 목록을 조회하기를, so that 내가 신청한 미팅이 지금 어떤 상태(대기/확정/거절됨)인지 추적한다.
2. As a 참가사/바이어, I want 상대가 나에게 보낸 미팅 요청 목록을 조회하기를, so that 내 응답을 기다리는 건이 무엇인지 놓치지 않는다.
3. As a 참가사/바이어, I want 받은 요청 중 응답 대기(`proposed`) 건수를 배지로 보기를, so that 지금 처리해야 할 일이 얼마나 남았는지 즉시 안다.
4. As a 참가사/바이어, I want 네비게이션 "내 미팅" 메뉴에 전체 응답 대기 건수가 표시되기를, so that 다른 화면에 있어도 처리할 요청이 있음을 인지한다.
5. As a (일반 바이어 또는 참가사로서) 요청을 받은 쪽, I want 받은 요청을 수락하기를, so that 미팅을 `accepted`로 확정한다.
6. As a (일반 바이어 또는 참가사로서) 요청을 받은 쪽, I want 받은 요청을 거부하고 사유를 남기기를, so that 원치 않는 미팅을 확정 전에 정리하고 상대에게 사유가 전달된다.
7. As a 미팅을 신청한 쪽, I want 아직 확정 전(`proposed`)인 내 요청을 취소하기를, so that 더 이상 원치 않는 신청을 회수한다.
8. As a 참가사/바이어, I want 이미 확정(`accepted`)된 미팅을 취소하기를, so that 사정이 생긴 미팅을 무를 수 있다 — 단 취소 넛지를 보고 신중히 결정한다.
9. As a 미팅을 수락(또는 확정)하는 쪽, I want 우리 기업에서 나갈 참석 Member를 지정하기를, so that 현장에서 누가 미팅에 들어갈지 명확해진다.
10. As a 참가사/바이어, I want 지정한 참석 Member를 나중에 변경하기를, so that 담당자가 바뀌어도 미팅 배정에 반영된다.
11. As a 참가사/바이어, I want 각 미팅의 일정(날짜·시간)과 장소(Meeting Venue)를 확인하기를, so that 현장에서 제때 올바른 위치로 간다.
12. As a 참가사/바이어, I want 상대 기업 정보(기업명·로고·한줄소개·키워드)를 미팅 패널에서 보기를, so that 어떤 미팅인지 맥락을 잡고 준비한다.
13. As a 참가사/바이어, I want 날짜별로 미팅을 나눠 보기를, so that "오늘 내 미팅이 뭐지?"를 가장 빠르게 답한다.
14. As a 참가사/바이어, I want 미팅 상태가 색/라벨로 구분되기를, so that 확정·대기·거절됨·취소됨·노쇼를 한눈에 식별한다.
15. As a 참가사/바이어, I want 완료(`completed`) 미팅에서 회의록 작성으로 이동하기를, so that 미팅 후 마무리(회의록 + 미팅 리뷰, F-MY-002)를 남긴다. 불참(노쇼)도 `completed`라 동일하게 진입한다.
16. As a 참가사/바이어, I want 상대가 내 요청을 수락/거부하거나 미팅이 취소되면 화면이 실시간으로 갱신되기를, so that 새로고침 없이 최신 상태를 본다.
17. As a 참가사/바이어, I want 미팅이 하나도 없을 때 적절한 안내와 다음 행동(기업 탐색 등)을 받기를, so that 빈 상태에서 무엇을 할지 안다.

## Implementation Decisions

**보낸/받은 요청 구조 (구 EX-003 흡수)**
- **D1 — 참가사·바이어 전원 공용 단일 라우트(`/meetings`).** Role-based Route의 예외로, 미팅 타임라인은 전원 공용으로 둔다(CONTEXT.md). 구 EX-003 `/exhibitor/meetings`는 MY-001로 흡수됐다. 화면 안에서 역할별 뷰로 분기한다.
- **D2 — 보낸 요청 / 받은 요청을 구분해 조회.** "내가 신청한 미팅"과 "상대가 신청해 내 응답을 기다리는 미팅"을 사용자가 구분할 수 있게 한다. 방향(신청 주체)은 `meetings.requested_by`로 판단한다. 타임라인 표면에서 방향 라벨을 강조하지 않더라도, 노출되는 **액션 버튼은 방향+상태로 시스템이 판단**해 적절한 것만 보여준다.

**상태 라벨 / 슬롯 색상 (ADR-0005 상태흐름)**

상태값은 `meetings.status` — `proposed / accepted / rejected / cancelled / completed`. **노쇼는 상태가 아니라 `completed` 미팅의 결과 속성**(`attended=false`, 진실원천=`post_meeting_reviews`)이다(ADR-0010 보정 — `meetings.status`에서 noshow 제거).

**슬롯 색은 "상태색"이 아니라 끝난 미팅의 "다음 할 일"을 나타낸다**(색 재정의). 색은 status + `attended` + `hasReview` + 종료경과로 파생한다.

| 색상 | 케이스 | 의미 |
|------|------|------|
| 그린 | `accepted`(예정/진행) | 확정 — 아직 안 끝남 |
| 레드 | `proposed` | 응답 대기 — 받은 쪽에 액션 필요 |
| 오렌지 | `completed`+참석+회의록 미작성, `accepted` 종료경과(종료시각 지남·미전이) | **회의록 작성 필요** |
| 블루 | `completed`+참석+회의록 작성완료 | **회의록 작성 완료(보관)** |
| 그레이 | `completed`+노쇼(`attended=false`), `rejected`, `cancelled`, 만료, 빈 슬롯 | 할 것 없음 |

- **D3 — 상태 진입은 ADR-0005를 따른다.** 일반 바이어/Exhibitor가 받는 건은 `proposed`로 시작(수락 필요), 초청 바이어가 받는 건은 `accepted`로 바로 진입(거부 단계 없음). MY-001은 이 상태를 표시·조작할 뿐 진입 규칙을 새로 만들지 않는다.
- **D3-1 — 확정 종료경과.** `accepted`인데 종료시각이 지나고 아직 `completed`로 전이 안 된 윈도우는 회의록 미작성과 동치로 보고 오렌지로 표시한다(`isEndedAccepted`). 백엔드 스케줄러가 `completed`로 전이하면(ADR-0010) 일반 완료 케이스가 된다.

**액션 (수락 / 거부 / 취소 / 회의록 / 참석여부 수정)**

| 슬롯 상태 | 받은 쪽(상대가 신청) | 신청한 쪽(내가 신청) |
|-----------|------------|--------------|
| `proposed` | 수락 / 거부 | 취소 |
| `accepted` | 취소 | 취소 |
| `completed` + 참석 | 회의록 작성/보기(MY-002) | 회의록 작성/보기(MY-002) |
| `completed` + 노쇼 | 참석여부 수정 (회의록 불가) | 참석여부 수정 (회의록 불가) |
| `rejected` / `cancelled` | 버튼 없음 | 버튼 없음 |

- **D14-1 — 회의록 작성과 참석여부 수정 버튼은 공존하지 않는다.** 참석 완료는 **회의록 작성/보기**만(상대 불참 표시는 회의록 작성 흐름 안의 입력값으로 받는다 — ADR-0010). 노쇼(`attended=false`)는 회의록 대상이 아니라(상단 '회의록' 스트립·`pendingReview`에서 제외) **참석여부 수정**만 노출하며, 참석으로 정정하면 회의록 작성 흐름으로 들어간다. (회의록 작성완료 시 버튼은 "회의록 보기".)
- **D14-2 — 빈 시간대 선택.** 타임라인의 빈 슬롯도 선택할 수 있고, 선택하면 우측 패널/바텀시트에 그 시간을 채울 **기업 탐색(`/discover`) 안내**를 띄운다.

- **D4 — 거부(reject)는 `proposed`에서만, 받는 쪽에만.** 거부 시 사유 키워드(관심 분야 불일치 / 일정 불가 / 기타) + 자유 입력을 받고 상대에게 거절 알림. 슬롯 → 그레이(`rejected`). 역제안(counter-proposal) 없음 — 빈 슬롯 교집합 기반 신청이라 거절 후 재신청으로 충분.
- **D5 — 취소(cancel)는 양쪽 누구나, 모든 출처에서.** `accepted`된 미팅을 무르는 행위(ADR-0005). 취소 시 넛지("특별한 사유 없이 취소하면 AI 매칭 추천에서 우선순위가 낮아질 수 있습니다") + 사유(키워드 + 자유 입력) → 상대에게 취소 알림. 슬롯 → 그레이(`cancelled`). v1에서는 넛지 문구 + 취소 이력 수집까지, 알고리즘 반영은 이후.
- **D6 — 액션 버튼은 방향+상태로 시스템이 판단해 노출.** 사용자가 "내가 받은 건지 신청한 건지" 따지지 않아도 할 수 있는 행동만 보인다.

**참석 Member 지정 (ADR-0002)**
- **D7 — 수락/확정 시 참석 Member 지정.** 매칭 단위는 Organization이고, 미팅에 나갈 사람은 기업 내부에서 정한다. `meeting_participants`(meeting_id × member_id)에 우리 기업 Member를 연결한다. 같은 기업 Member는 동일 권한(플랫)이라 누구나 지정·변경 가능.
- **D8 — 참석 Member는 사후 변경 가능.** 확정 이후에도 담당자 교체를 반영한다.

**기타 화면 결정**
- **D9 — 일별 탭 + 가로 스크롤 타임라인.** 09:00~18:00의 30분 단위 슬롯을 전부 표시(빈 시간 인식 = 일정 관리·노쇼 방지). 모바일 우선, PC는 별도 뷰 검토(프로토타입에서 구체화).
- **D10 — 하단 패널은 상대방 프로필 기반.** 내 역할이 아니라 상대가 가진 정보(기업명·로고·상태 배지·시간·장소·참석 Member·한줄소개·키워드 — DV-001 카드와 동일)를 보여준다.
  - 상대가 기업 탐색 목록에 없으면(승인 전 바이어 등 — 탐색은 승인 기업만 보여준다) 미팅 정보의 기업명·역할만으로 패널을 띄운다. 한줄소개·AI 매칭 적합도·"기업 상세 보기"는 생략하고, 상태·시간·장소·액션([회의록 작성] 포함)은 같다. 운영자 배정 미팅의 상대가 승인 전이면 패널이 아예 안 떠 회의록에 들어갈 수 없던 문제의 수정(2026-10-26 발주사 피드백).
- **D11 — 응답 대기 배지 이중 노출.** 네비게이션 "내 미팅" 항목에 전체 `proposed` 건수, 일별 탭에 날짜별 `proposed` 건수("9/17 (2)").
- **D12 — 실시간 갱신.** Schedule Table 상태 변경이 즉시 타임라인에 반영(예: 상대 수락 시 레드→그린).
- **D13 — 빈 상태별 안내.** 참가사: "AI 추천 바이어 확인"(→DV-001) / 바이어: "관심 기업 탐색"(→DV-001). (미인증 사용자는 이 화면에 진입하지 못한다 — 라우트 가드 → `/login`.)
- **D14 — 완료/노쇼 → 회의록(MY-002) 진입.** `completed`/`noshow` 슬롯의 "회의록 작성" 버튼 → `/meetings/:meetingId`. 상세는 F-MY-002. (용어: 미팅 후 산출물의 사용자 노출 라벨은 "회의록"으로 통일 — CONTEXT.md "미팅 후 마무리". 미팅 리뷰 신호는 그 흐름에 흡수.)

**상단 액션 스트립 (현황 숫자판 재정의)**

"내 미팅"의 1차 기대는 *내 일정*(타임라인 본문)이다. 상단은 일정을 밀어내는 현황 숫자판이 아니라, 일정 위에 얇게 얹힌 **"나를 기다리는 액션"** 스트립으로 둔다.

- **D15 — 상단 = 슬림 예외 스트립.** 액션이 필요한 항목만, 건수 있는 것만 노출. **둘 다 0이면 스트립 전체를 숨긴다**(평소엔 깔끔한 일정). 기존 항상 떠 있던 4칸(확정/응답 필요/완료/전체)은 폐기.
- **D16 — 스트립 항목은 "나를 기다리는 액션" 둘뿐.** ① **받은 미팅요청**(`receivedRequests` = 받은 `proposed`) → 수락/거부, ② **회의록**(`pendingReview` = 완료·노쇼 & 미작성) → MY-002. **받은 미팅요청만 alert 액센트**(상대가 나를 기다리는 유일한 건). 확정·완료·노쇼·보낸 요청은 스트립에 두지 않고 타임라인 본문이 담당(보낸 `proposed`는 슬롯 "응답 대기" 라벨로 인지). 다음 미팅 "준비"도 타임라인이 이미 패널로 띄우므로 스트립서 제외.
- **D17 — 탭하면 타임라인 안에서 다음 처리 대상으로 점프.** 스트립 행 탭 → 가장 이른 해당 미팅을 선택해 그 날짜 탭으로 전환 + 패널을 연다. 수락/거부·회의록 진입은 **패널 한 곳**에만 둬 분기·중복을 막는다. 별도 목록/시트 화면은 만들지 않는다(다건 훑기는 날짜 탭 배지 D11로 보조).
- **D18 — 단일 소스 집계.** 상단 스트립과 홈(HM-001) 미팅 현황은 **모두 `rollupMeetingStatus`(ADR-0005) 하나에서 파생**한다. 기존 `TimelineSummary`의 bespoke 집계(confirmed/pending/completed/total)는 폐기. **같은 개념은 같은 정의·라벨** — 받은 미팅요청(`receivedRequests`)·회의록(`pendingReview`)을 두 화면이 동일 라벨로 쓴다.

**접근 권한**

| 사용자 유형 | 접근 | 액션 |
|------------|------|------|
| Buyer (Hosted/Pre-registered/On-site) | O | 전체 기능 |
| Exhibitor | O | 전체 기능 |
| Visitor | X | 미인증 접근 불가 → 딥링크 로그인 필요(라우트 가드 → `/login`) |
| Organizer | X | OP-* 대시보드에서 전체 미팅 관리 |

**아키텍처 경계 (ADR-0008, 경계 B)**
- Next.js는 RDS에 직접 접속하지 않는다. 미팅 조회·수락/거부/취소·참석 Member 지정 등 모든 읽기/쓰기는 **FastAPI API 경유**. 권한검사(내가 이 미팅의 당사자인가)는 FastAPI 한 곳에 집중하고, Cognito JWT를 FastAPI가 JWKS/RS256으로 검증.
- 실시간 갱신은 API 위의 구독 채널로 표면화(구현 기술은 외주사 선택 — 결정은 "상태 변경 즉시 반영").

**식별된 deep modules** (격리 테스트 대상 후보)
- `my-meetings-list` — 한 사용자의 미팅을 보낸/받은 요청으로 분류하고 날짜별로 묶어, 각 슬롯의 상태·색상·노출 가능 액션을 산출하는 조회/투영 모듈. 입력(미팅·방향·상태·역할)에서 "무엇이 보이고 무엇을 누를 수 있는가"를 결정.
- `meeting-action-handler` — 수락/거부/취소 액션을 받아 ADR-0005 상태흐름에 맞는 전이만 허용하고(불법 전이 차단), 사유·넛지·알림·참석 Member 지정을 함께 처리하는 전이 모듈.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부(컴포넌트 내부 상태)가 아니라 **외부 동작**만 검증한다. 예: "상대가 보낸 `proposed` 건에는 수락/거부 버튼이 보이고, 내가 보낸 `proposed` 건에는 취소만 보인다", "거부하면 상태가 `rejected`로 가고 상대에게 알림이 나간다".
- **테스트 대상 모듈:**
  - `my-meetings-list` — 방향(보낸/받은)×상태별로 올바른 색상·라벨·노출 액션이 산출되는지. 빈 슬롯·빈 상태(역할별 안내) 분기.
  - `meeting-action-handler` — ADR-0005 전이 규칙 준수: `proposed`에서만 거부 가능, `accepted`는 취소만, `rejected`/`cancelled`에서 추가 전이 불가. 수락/확정 시 참석 Member 지정 경로. 취소 넛지·사유 수집.
- **Prior art:** 앱 코드가 아직 0인 그린필드라 기존 테스트 선례 없음. F-BM-001이 첫 테스트 패턴 기준선을 세웠고(외부 동작 검증 + 트랜잭션 경계), MY-001의 두 모듈은 같은 원칙(외부 동작·상태 전이 규칙 검증)을 따른다.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 타임라인·보낸/받은 목록·액션 버튼 UI 시연만. 실제 상태 전이·알림·참석 Member 저장은 본 슬라이스 구현 범위.
- **역제안(counter-proposal)** — 빈 슬롯 교집합 기반 신청이라 도입하지 않음(거절 후 재신청으로 대체).
- **취소의 알고리즘 반영** — v1은 넛지 문구 + 취소 이력 수집까지. 매칭 추천 우선순위 페널티 반영은 이후 과제.
- **매칭 로직·배정 자체** — 적합도·배정은 ADR-0006 / OP-* 소관. MY-001은 결과(Schedule Table)를 조회·조작만.
- **미팅 신청(보내기) 플로우** — F-MT-001 소관. MY-001은 이미 존재하는 요청의 조회·관리.
- **미팅 리뷰 상세** — F-MY-002 소관.
- **Organizer의 전체 미팅 관리** — OP-* 대시보드 소관.
- **AI 추천/검색으로 새 미팅 채우기** — Open Matching 보정 경로(F-DV-001/F-MT-001)로 진입. MY-001은 진입점만 제공.
