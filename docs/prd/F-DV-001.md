# F-DV-001: 기업 탐색

> 기업 발견(discovery)의 단일 허브. **3탭**(AI 추천 · 전체 기업 · 관심기업)으로 AI 매칭 제안 확인 + 직접 검색/필터 + 관심기업 관리를 한곳에 묶고, 어느 탭에서든 **상세 조회 → 미팅 신청(Open Matching)** 으로 흐른다. 구 BM-003(매칭 제안) + CL-001(참여자 탐색: 카드)을 통합.

## Problem Statement

참가사·바이어 입장에서:

- 전시회에는 참가사 103개·바이어 178명 규모의 상대가 있는데, 그중 **나에게 맞는 상대를 어떻게 찾아야 할지** 막막하다. 처음부터 검색창만 주면 무엇을 쳐야 할지 모르고, 방산 도메인 전문용어와 부스 위치까지 일일이 훑기엔 부담이 크다.
- AI가 적합도 높은 상대를 골라줘도, 그게 **검색/관심기업과 따로 떨어진 화면에 있으면** 두 곳을 왔다갔다 해야 하고 발견의 흐름이 끊긴다.
- 마음에 드는 기업을 발견해도 **나중에 다시 찾기 어렵다** — 즉시 미팅을 신청할 단계가 아니어도 일단 담아두고 비교하고 싶다.
- 카드 한 장에 정보가 너무 많으면 인지가 안 되고, 너무 적으면 미팅 가치를 판단할 수 없다 — **요약(카드)과 상세(프로필)** 사이의 정보 밀도 차이가 필요하다.

## Solution

참가사·바이어 입장에서:

- 발견을 **한 페이지 3탭**으로 묶는다. **AI 추천(기본 탭)** 이 적합도 높은 순으로 한 장씩(스와이프) 상대를 제시하고 — NABI의 차별점 — , **전체 기업** 탭에서 직접 검색·필터하며(Open Matching 경로), **관심기업** 탭에 양쪽에서 담은 기업을 모아본다. 탭을 옮겨도 발견의 맥락이 끊기지 않는다.
- AI 추천 카드에는 **적합도 %와 추천 이유**가 붙어 "왜 이 상대인가"가 보이고, 카드에서 바로 **미팅 신청 / 관심기업 등록 / 관심없음 / 상세보기** 4가지로 행동한다.
- 어느 탭에서든 **관심기업으로 담아** 두면, 담은 출처(AI 추천 / 전체 기업)와 무관하게 관심기업 탭에 모인다.
- 카드를 누르면 **상세 페이지(DV-002)** 로 들어가 전시 제품·실적·기업 정보 등 카드엔 없던 정보까지 보고, 거기서 **미팅 신청**으로 이어간다. 사용자가 직접 신청하는 이 경로는 출처가 **Open Matching(자율 매칭)** 으로 기록된다.

## User Stories

1. As a 바이어, I want 로그인 직후 내 미팅(랜딩)에서 "기업 탐색" 버튼으로 탐색 허브에 들어가기를, so that 어디서 시작해야 할지 헤매지 않는다.
2. As a 바이어, I want AI 추천 탭이 기본으로 먼저 열리기를, so that 무엇을 검색할지 고민하기 전에 적합도 높은 상대를 바로 받아본다.
3. As a 바이어, I want AI 추천을 한 장씩(스와이프) 적합도 높은 순으로 보기를, so that 한꺼번에 쏟아지는 정보에 압도되지 않고 한 명씩 집중해 판단한다.
4. As a 바이어, I want 각 추천 카드에서 적합도 %와 추천 이유를 보기를, so that 이 상대가 왜 추천됐는지 납득하고 미팅 가치를 가늠한다.
5. As a 바이어, I want 추천 카드에서 바로 미팅 신청·관심기업 등록·관심없음·상세보기 중 하나를 고르기를, so that 카드를 떠나지 않고 즉시 행동한다.
6. As a 바이어, I want "관심없음"으로 표시한 카드가 다시 안 뜨기를, so that 이미 거른 상대를 반복해 보지 않는다.
7. As a 바이어, I want 모든 추천 카드를 다 본 뒤 "관심기업 N개 / 미팅 신청 N건" 요약과 전체 기업으로 더 찾아보라는 안내를 받기를, so that 추천을 다 소진한 뒤 다음 행동을 안다.
8. As a 참가사, I want AI 추천 탭에서 바이어를 한 장씩 받아보기를, so that 바이어 발견 경험이 바이어 측과 완전히 대칭이라 따로 배울 게 없다.
9. As a 참가사, I want 바이어 추천 카드에서 직접 바이어에게 먼저 미팅을 신청하기를, so that 참가사도 수동적으로 기다리지 않고 능동적으로 미팅을 만든다.
10. As a 바이어, I want 전체 기업 탭에서 키워드 검색과 카테고리 필터로 직접 상대를 찾기를, so that AI 추천 밖의 상대도 내 기준으로 탐색한다.
11. As a 바이어, I want 전체 기업 탭 카드에서 기업명·키워드 태그·한줄 소개·부스 위치를 보기를, so that 리스트만으로 누구인지 빠르게 훑는다.
12. As a 참가사, I want 전체 기업 탭에서 참가사·바이어를 세그먼트로 구분해 모두 보기를, so that 상대(바이어)뿐 아니라 함께 참가하는 동종 참가사 동향까지 살핀다. (2026-06-21 갱신 — 기존 "상대 역할만" 폐기)
13. As a 바이어/참가사, I want AI 추천·전체 기업 어느 탭에서든 관심기업으로 담기를, so that 지금 신청하지 않아도 마음에 둔 상대를 잃지 않는다.
14. As a 바이어/참가사, I want 담은 출처와 무관하게 관심기업 탭에 한곳으로 모이기를, so that 흩어진 후보를 모아 비교한다.
15. As a 바이어/참가사, I want 관심기업 탭에서 담은 기업을 해제하기를, so that 더는 관심 없는 후보를 정리한다.
16. As a 바이어/참가사, I want 어느 탭에서든 카드를 눌러 상세 페이지로 들어가기를, so that 카드엔 없던 전시 제품·실적·기업 정보까지 보고 결정한다.
17. As a 바이어/참가사, I want 상세 페이지 하단에서 관심기업 토글과 미팅 신청 버튼을 보기를, so that 정보를 다 본 그 자리에서 바로 행동한다.
18. As a 바이어, I want 상세에서 "미팅 신청"을 누르면 신청 모달(F-MT-001)이 그 자리에서 열리기를, so that 탐색 흐름을 끊지 않고 신청을 마친다.
19. As a 참가사 카드를 보는 바이어, I want 상대 개인명·직급이 카드/상세에 안 보이기를, so that 미팅이 성사되기 전 상대 프라이버시가 지켜진다(개인명은 미팅 수락 후 공개).
22. As a 운영팀, I want 사용자가 탐색에서 직접 신청한 미팅이 출처(Open Matching)로 구분돼 기록되기를, so that AI 추천군과 자율 발생군을 비교해 매칭 효과를 입증한다.
23. As a 바이어/참가사, I want 매칭 신청기간(~9/11)엔 안내만 보이고 매칭 후(9/12~) AI 추천 탭이 켜지기를, so that 아직 매칭이 돌지 않은 시점에 빈 추천에 혼란스럽지 않다.

## Implementation Decisions

**3탭 구조 (단일 발견 허브)**

| 탭 | 기본 | UI 패턴 | 내용 |
|----|------|---------|------|
| AI 추천 | 기본 | 스와이프(한 장씩) | AI 매칭 제안. 적합도 높은 순. NABI 차별점 |
| 전체 기업 | | 리스트 + 검색/필터/정렬 | 키워드 검색 + 카테고리 필터 + 정렬(적합도순·이름순·전시장 위치순). **Open Matching** 경로 |
| 관심기업 | | 리스트 | AI 추천/전체 기업 양쪽에서 담은 기업 모아보기 |

- **D1 — BM-003 + CL-001을 DV-001 한 페이지로 통합.** 발견은 본질적으로 한 기능이라 분리하면 사용자가 두 곳을 오가야 한다.
- **D2 — AI 추천이 기본 탭.** NABI 차별점을 직접 검색보다 먼저 경험시킨다.
- **D3 — AI 추천은 스와이프(한 장씩).** 발견 집중 + 인지 부하 최소화. 스와이프 제스처↔액션 매핑은 프로토타입에서 확정.
- **D4 — AI 추천 카드 4액션:** ① 미팅 신청(F-MT-001 모달) ② 관심기업 등록 ③ 관심없음(카드 숨김) ④ 상세보기(DV-002). 추천 소진 시 "관심기업 N개 / 미팅 신청 N건" 요약 + 전체 기업 유도.
- **D5 — 카드 vs 상세의 정보 밀도 차이가 상세의 존재 이유.** 카드엔 요약만, 상세엔 카드에 없는 필드가 추가로 드러난다.

**매칭 단위 = Organization (ADR-0002)**
- 카드·상세·관심기업·추천 모두 **기업(Organization) 단위**로 다룬다. 미팅 참석자(Member)는 기업 내부에서 지정. 상세 라우트 키도 `:organizationId`.

**카드 필드 (그룹 구조)**

| 방향 | 그룹 | 노출 필드 |
|------|------|-----------|
| 바이어 → 참가사 | 회사정보 | 회사명 · 강점/차별점(`strength`) · 부스 위치 |
| | 상품정보 | 전시제품(`exhibits`) |
| | 매칭률 | 적합도 %(AI 매칭 점수) · 추천 이유(AI 추천 탭·상세) |
| 참가사 → 바이어 | 바이어정보 | 기관명 · 바이어 유형(`buyer_subtype`: 초청/사전등록/현장) · 기업 소개(`description`) |
| | 관심정보 | 관심 분야 키워드 · 예산 범위 · 도입 시기 |
| | 매칭률 | 적합도 %(AI 매칭 점수) · 추천 이유(AI 추천 탭·상세) |

- **D6 — 적합도(매칭률)는 전 탭 카드에 노출, 추천 이유는 AI 추천 탭/상세에만.** (2026-06-21 갱신: 기존 "전체 기업 탭은 검색결과라 점수 없음" 가정을 폐기.) 전체 기업·관심기업 카드도 동일한 AI 매칭 점수(`ai-engine`/`ai_match_suggestions`)를 **재사용**해 적합도 %를 표시한다. 추천 이유(`ai_score_reasons`)만 AI 추천 탭과 상세에 한정. 적합도는 바이어↔참가사 **양방향 카드 모두**에 표시(매칭은 대칭).
- **D6a — 참가사 카드는 키워드 대신 전시제품을 노출.** 전시품목 키워드는 검색·필터·상세에서 쓰고, 카드 본문은 상품정보(전시제품)로 대표. 바이어 카드는 관심 분야 키워드를 그대로 노출.
- **D6b — 부스 위치는 3계층(Hall/Booth) 파생 표시.** `{Hall 이름} {Booth code}`(예 "제1전시관 A-12")로 표시(평문 저장 아님 — CONTEXT 전시장 부스 계층, halls/booths 정규화). 정렬 "전시장 위치순"은 Hall → 부스코드 순.
- **D7 — 개인명/직급 비노출.** 참가사→바이어 카드/상세는 기관명까지만. 개인명·직급·연락처는 미팅 수락 후 공개(프라이버시).
- 도입 시기 값은 6개월 내 / 1년 내 / 2년 내 / 미정 4종(buyer_profiles.adoption_timeline 도메인).

**기업 상세 (DV-002) — 공유 모달 (+ 딥링크 폴백 풀페이지)**
- **D8 — 상세는 여러 화면이 공유하는 모달 + 딥링크 폴백 풀페이지.** (2026-07-01 갱신 — 기존 "별도 페이지 전용" 폐기.) 상세를 보여주는 곳이 기업 탐색·내 미팅 등 여러 페이지라, 페이지마다 노출 필드를 따로 정의하던 중복을 없애기 위해 **공통 본문 + 공유 모달**로 통일한다. 본문(`OrgDetailBody`)·하단 액션(`OrgDetailActions`)은 한 곳에서만 정의하고, 어느 페이지든 `useOrgDetail().open(org, …)`로 같은 상세를 모달로 연다(호스트 `OrgDetailProvider`를 app-shell에 1회 마운트). 라우트 `/discover/:organizationId` 풀페이지는 **딥링크 폴백**(공유·새로고침·수식키/새 탭 클릭)으로 유지하며 같은 본문을 재사용한다. 진입: AI 추천 카드의 상세보기 · 전체 기업/관심기업 카드 클릭 · 내 미팅(MY-001) 미팅 카드의 "기업 상세 보기". 바텀시트는 여전히 배제(정보량이 많아 부족). 운영사(OP-003) 기업 상세는 PII 노출 규칙이 달라 이 모달을 재사용하지 않고 별도 구현한다.
- 미팅 신청 가용성(슬롯·장소·AI 초안)은 풀페이지는 서버에서 미리 읽어 내려주고, 모달은 미팅 신청을 누르는 순간에만 route handler `GET /api/discover/availability`로 lazy-fetch한다(읽기 seam은 server-only, ADR-0008 경계 B).
- 정보 구조(상단→하단): ① 적합도 배너(적합도 % + 추천 이유 1줄) ② AI 추천 이유 전문 ③ 부스 위치 ④ 전시 제품(3개 권장) ⑤ 분야 키워드 ⑥ 강점 ⑦ 주요 실적(3건) ⑧ 기업 정보(소개 + 설립연도·직원수).
- 카드 대비 추가 필드: `exhibits`(전시 제품), `achievements`(주요 실적), `founded`(설립연도), `employees`(직원 규모), 회사 소개 — 카드→상세 전환의 정보 밀도 차이를 만드는 필드.
- 하단 액션 바: 관심기업 등록/해제(secondary, 토글) · 미팅 신청(primary → F-MT-001 모달).
- 디자인 원칙: 이모지 금지, 타이포·여백으로만 위계 표현, 방산 전문용어는 문맥에서 이해되게 자연 노출(별도 설명 UI 없음).

**AI 추천 (provenance / 데이터)**
- **D9 — AI 추천 카드 덱은 `ai_match_suggestions`에서 적합도 높은 순으로 제공.** `ai_score`(적합도) + `ai_score_reasons`(추천 이유)를 그대로 카드/상세에 표시. 적합도 기준 이상 전부 제공(수량 제한 없음).
- 카드 액션은 추천 레코드 상태로 반영: 미팅 신청 → `requested`, 관심기업 등록 → `bookmarked`, 관심없음 → `dismissed`(이후 덱에서 제외), 기본 `pending`.
- **D10 — 사용자가 탐색에서 직접 신청한 미팅의 출처(provenance)는 Open Matching.** 추천 카드/상세의 미팅 신청은 모두 사용자 능동 신청 → Schedule Table에 `matching_type='open'`으로 기록(ADR-0004, 발생 시점 영구 보존). AI가 추천했더라도 **운영자 AI 전체 포화배정(provenance=AI)** 과는 별개 채널 — 이 화면에서 발생하는 미팅은 자율 신청이다. provenance(누가 만들었나)와 수락 규칙(받는 쪽이 누구냐)은 독립 축(ADR-0005).
- **D11 — 9/12 이전엔 AI 추천 비활성.** 9/11 마감 후 일괄 매칭이 1차이므로, ~9/11엔 "비즈매칭 신청을 받고 있습니다" 안내. 전체 기업 탭은 ~9/11에도 활성(사전 탐색 가능). 9/12~ 전체 기능 활성.

**관심기업(북마크)**
- **D12 — 관심기업은 `interested_organizations`에 owner_org→target_org로 저장, 담은 출처를 `source`에 기록**(`ai` = AI 추천 탭, `all` = 전체 기업 탭). 출처와 무관하게 관심기업 탭 한곳에 모인다. `(event, owner_org, target_org)` 유니크 — 같은 기업 중복 담김 없음.

**노출 범위 / 권한 (ADR-0009)**
- **D13 — 탐색/추천에 노출되는 상대는 `organization_event_roles.application_status='approved'` 인 비즈매칭 참가자뿐.** import eager 생성으로 만들어진 미로그인 "유령 org"(`registered`)나 제출·검토 대기(`submitted`)는 카드/추천/검색에 안 보인다. 매칭 엔진·기업 목록 노출 대상은 `approved`만(참가자 판정 = `application_status='approved'`, ADR-0009 — 제출만으론 부족, 운영 승인 필요).
- **D13a — 방향별 가시성 (2026-06-21 갱신, 기존 "양측 완전 대칭" 일부 폐기):**

  | 뷰어 | 전체 기업 탭 | AI 추천 탭 | 관심기업 탭 |
  |------|-------------|-----------|------------|
  | 바이어 | 참가사만 | 참가사(상대) | 사용 |
  | 참가사 | **참가사 + 바이어** (세그먼트 토글) | 바이어(상대) | 사용 |

  - **미인증 사용자는 이 화면에 진입할 수 없다** — `/discover`·`/discover/:id`는 인증 전용(nav-attached). 라우트 가드가 미인증 접근을 `/login`으로 보낸다(게스트 탐색 없음, 정책 변경 2026-07-02). 아래 가시성은 모두 인증 참가자 기준.
  - **AI 추천은 여전히 완전 대칭** — 상대 역할만(바이어↔참가사). 비대칭은 **전체 기업 탭에 한정**: 참가사 뷰어만 전체 기업 탭에서 `[바이어 | 참가사]` 세그먼트로 양 진영을 모두 본다(기본 세그먼트=바이어=상대). 바이어는 참가사만.
  - 적합도(매칭률)는 매칭 대상(상대)에만 존재 — 참가사 뷰어가 같은 진영(참가사) 세그먼트를 볼 때는 적합도 배지가 표시되지 않는다.

**아키텍처 경계 (ADR-0008, 경계 B)**
- **D14 — 화면은 Next.js, 모든 조회/저장은 Next.js → FastAPI API → RDS.** Next.js는 DB에 직접 접속하지 않는다. 추천 덱·검색/필터·관심기업 토글·상세 조회 전부 FastAPI 엔드포인트 경유, 권한검사는 FastAPI 한 곳(Cognito JWT 검증).

**채팅 배제 (ADR-0003)**
- **D15 — 카드 모드에서는 채팅(NABI 에이전트 대화) 동선 없음.** 카드 탐색과 채팅 탐색은 상호 배타. 이 화면은 카드 모드.

**식별된 deep modules** (격리 테스트 대상 후보)
- `org-listing/filtering` — 전체 기업 탭의 키워드 검색 + 카테고리 필터 + 역할 필터(상대 역할만) + submitted 노출 게이트를 캡슐화. 입력(검색어·필터·내 역할) → 노출 대상 목록.
- `ai-suggestion-deck` — AI 추천 덱의 적합도 정렬·카드 4액션(requested/bookmarked/dismissed)·dismissed 제외·소진 요약을 캡슐화. `ai_match_suggestions` 상태 전이를 단일 인터페이스로.
- `bookmark-store` — 관심기업 담기/해제, source(ai/all) 기록, 중복 방지, 출처 무관 단일 목록 집계를 캡슐화.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다(탭 컴포넌트 내부 상태가 아니라 "관심없음 표시한 카드는 덱에서 다시 안 나온다", "AI 탭에서 담든 전체 기업 탭에서 담든 관심기업 탭에 한 번만 나타난다" 같은 관찰 가능한 결과).
- **테스트 대상 모듈:**
  - `org-listing/filtering` — 검색/필터 결과, 상대 역할만 노출, **registered org는 안 보이고 submitted만 노출**(ADR-0009).
  - `ai-suggestion-deck` — 적합도 내림차순 정렬, 4액션의 상태 전이(requested/bookmarked/dismissed), dismissed 카드 재노출 안 됨, 소진 시 "관심기업 N개 / 미팅 신청 N건" 집계 정확.
  - `bookmark-store` — 담기/해제 토글, source 기록(ai/all), 동일 기업 중복 담김 불가, 출처 무관 단일 목록 집계.
  - 미팅 신청 출처: 이 화면에서 발생한 신청이 `matching_type='open'`(Open Matching)으로 기록되는지(ADR-0004 발생 시점 박제).
- **Prior art:** 앱 코드가 아직 0인 그린필드라 기존 테스트 선례 없음. F-BM-001이 첫 수직 슬라이스의 테스트 패턴 기준선을 제시했고, 본 PRD의 세 모듈은 그 패턴을 발견(읽기 중심) 영역으로 확장하는 기준선이 된다.

## Out of Scope

- **6/17 컨셉 데모는 데모용 5개 기업 완성 · 나머지 카드만.** 5개 기업은 카드→상세까지 풀 완성도, 나머지 45개는 카드만(상세 미완). 실제 추천/저장/검색 동작은 이 슬라이스 구현 범위.
- **키워드 카테고리 체계 미정** — CTO 협의 필요. 현재 프로토타입 가정(방산 8개 + 기술/소재 6개)이 있으나 키워드 그룹핑·가중치·유사어 처리 미정. 6/17 데모는 현재 목록으로 진행. `keywords.category`는 확정 전이라 잠정 자유 텍스트.
- **적합도(fit score) 정의 미정** — AI 매칭 우선순위·룸 배정 우선순위의 선행 조건(CONTEXT.md flagged). 점수 산식은 매칭 엔진(ADR-0006/OP-005) 소관.
- **매칭 엔진 자체** — AI 전체 포화배정·배정·적합도 계산은 ADR-0006 / OP-005 소관. 이 화면은 그 결과(`ai_match_suggestions`)를 표시·소비할 뿐.
- **스와이프 제스처↔액션 매핑** · **관심없음 UI 처리 방식** — 프로토타입에서 테스트 후 확정.
- **상세 내 AI 협업 제안 · 과거 미팅 이력 · 연락처 · 제품 사진/스펙** — 1차 데모 범위 밖, 이후 구체화(연락처는 미팅 수락 후 공개).
- **채팅(에이전트 대화) 탐색 동선** — ADR-0003으로 카드 모드와 상호 배타. v1 카드 모드 범위 밖.

## Further Notes

- **진입 동선:** 이메일(매칭 완료 안내 / 미팅 신청 알림)은 모두 내 미팅(MY-001)으로 유도하고, 내 미팅에서 "기업 탐색" 버튼으로 `/discover` 진입. 첫 진입 시 온보딩 2~3장(브랜드 각인 + 기능 소개), 재방문 시 스킵.
- **카드→상세→미팅 신청**이 핵심 전환 퍼널. 상세의 미팅 신청은 F-MT-001 모달(시간→장소→확인+사유)을 그 자리에서 연다.
- **취소로 빈 슬롯이 생기면** 사용자가 이 화면(AI 추천/검색)에서 능동적으로 채우는 것이 Open Matching의 운영상 역할(CONTEXT.md). 즉 탐색 화면은 사후 보정 채널의 사용자 측 진입점이기도 하다.
