# F-OP-003: 단일 기업 빈슬롯 보충 (운영자용 기업 디테일)

> 운영자가 **기업 한 곳을 깊이 들여다보는 관리 뷰**. 그 기업의 프로필과 미팅 일정을 조회하고, **그 기업의 빈 슬롯만 골라 보충**한다(단일 기업 재트리거 — 추가 전용·비파괴). F-OP-002(목록)와 F-OP-005(배정 허브) 양쪽에서 같은 라우트로 진입하는 공유 상세.

| 메타 | |
|------|------|
| Page ID / 기능 ID | OP-003 / F-OP-003 |
| 라우트 / 형태 | `/organizer/members/:organizationId` / 페이지 |
| 상태 / 디바이스 | confirmed / 데스크톱 + 모바일 반응형(배정 작업이 있어 **데스크톱 우선**) |
| 가설 | 한 기업의 프로필·일정·빈 슬롯을 한 화면에서 처리하면 운영자가 개별 대응(빈 슬롯 보충)을 빠르게 한다 |
| 관리지표 | 기업별 미팅 보유 수, 빈 슬롯 수, 단일 재트리거 실행 건수(모드①/②별), 보충 후 채워진 슬롯 수 |
| 관련 ADR | ADR-0005(유형별 수락), ADR-0006(배정 정책 — 단일 재트리거=별개 액션), ADR-0008(경계 B), ADR-0007(Registrant 상태) |
| 관련 PRD | F-OP-002(목록·진입), F-OP-005(전체 포화배정·배정 허브), F-MT-001(상태 흐름), F-DV-001/DV-002(참가측 기업 상세 — 구분 대상) |

---

## Problem Statement

운영자 입장에서:

- 9/11 마감 후 AI 전체 포화배정(OP-005)을 한 번 돌렸어도, **특정 한 기업의 일정이 비어 있는 경우**가 생긴다 — 취소가 났거나, 지각 합류한 기업이거나, 중요 참가사인데 슬롯이 덜 찼다. 이 한 기업만 빠르게 채우고 싶은데, 전체 포화배정을 다시 돌리는 건 과하고 다른 기업 일정에 영향이 갈까 불안하다.
- 한 기업을 대응하려면 그 기업의 **프로필(어떤 기업인지)과 현재 미팅 일정(어디가 비었는지)을 한자리에서** 봐야 하는데, 정보가 흩어져 있으면 판단이 느리다.
- 빈 슬롯을 채울 때 **AI에게 알아서 채우게** 하고 싶을 때도 있고, **AI 추천을 보고 내가 직접 상대를 고르고** 싶을 때도 있다. 두 방식이 필요하다.
- 운영자가 채운 미팅이 **상대(받는 쪽)에게 어떻게 통지될지**(즉시 확정인지, 수락대기인지)를 실행 전에 알아야 안심하고 누른다.

## Solution

운영자 입장에서:

- 목록(OP-002)에서 기업 행을, 또는 배정 허브(OP-005)에서 대상 기업을 클릭하면 **그 기업의 디테일 한 화면**으로 들어온다. 프로필, 이 기업 전체 미팅 일정, 빈 슬롯이 한자리에 보인다.
- 그 화면에서 **이 기업의 빈 슬롯만** 골라 보충한다(단일 기업 재트리거). **다른 기업·기존 미팅은 건드리지 않는다**(추가 전용·비파괴) — 전체 포화배정을 다시 돌릴 필요가 없다.
- 보충은 두 모드 중에 고른다:
  - **모드① 자동 채움(AI 재트리거)** — AI가 적합도 순으로 이 기업의 빈 슬롯을 채운다. provenance는 'AI 매칭'으로 기록(성과측정). **운영사 전용 액션**.
  - **모드② 추천 → 선택(Forced)** — AI 추천/검색으로 상대+슬롯을 운영자가 **직접 골라** 지정한다. provenance는 'Forced'.
- 실행 전에 **받는 쪽 유형 뱃지 + 결과 상태(즉시 확정 / 수락대기)** 를 미리 보여준다. 운영자는 confirmed/proposed를 손으로 고르지 않는다 — 받는 쪽 유형이 자동 결정한다.

## User Stories

1. As an 운영자, I want OP-002 목록에서 기업 행을 클릭해 그 기업 디테일로 들어가기를, so that 목록(데이터 관리)에서 곧장 단일 기업 대응으로 넘어간다.
2. As an 운영자, I want OP-005 배정 허브에서 대상 기업을 골라 같은 디테일 화면으로 들어가기를, so that 전체 관점에서 발견한 빈 기업을 바로 개별 보충한다.
3. As an 운영자, I want 그 기업의 프로필 전체(참가사/바이어 역할, 키워드, 니즈)를 조회하기를, so that 어떤 기업인지 파악하고 보충 판단을 한다.
4. As an 운영자, I want 그 기업이 등록자(Registrant)인지 비즈매칭 참가자(승인 완료=`approved`)인지 상태를 보기를, so that 매칭 대상 자격이 되는지 확인한다.
5. As an 운영자, I want 그 기업의 슬롯별 미팅 배정 상태(proposed/accepted/completed/noshow/cancelled)와 **빈 슬롯**을 한눈에 보기를, so that 어디를 채워야 하는지 즉시 안다.
6. As an 운영자, I want 모드① 자동 채움으로 이 기업의 빈 슬롯을 AI가 보충하게 하기를, so that 적합도 순으로 빠르게 일정을 채운다.
7. As an 운영자, I want 모드② 추천 → 선택으로 AI 추천/검색에서 상대를 직접 골라 슬롯을 지정하기를, so that 특정 상대를 의도적으로 붙인다.
8. As an 운영자, I want 보충이 **이 기업의 현재 빈 슬롯만** 채우고 기존 accepted/proposed 미팅·다른 기업을 건드리지 않기를, so that 부작용 없이 안심하고 재실행한다.
9. As an 운영자, I want 실행 전에 각 후보의 **받는 쪽 유형 뱃지와 결과 상태(즉시 확정/수락대기)** 를 미리 보기를, so that 통지 결과를 예측하고 실행한다.
10. As an 운영자, I want 모드①/모드②로 만든 미팅의 provenance가 각각 'AI 매칭'/'Forced'로 기록되기를, so that 누가 만든 매칭인지 성과측정에서 구분된다.
11. As an 운영자, I want 일반 바이어·Exhibitor가 받는 건은 수락대기(proposed), 초청 바이어가 받는 건은 즉시 확정(accepted)으로 처리되기를, so that 내가 confirmed/proposed를 손으로 고르지 않아도 규칙이 일관되게 적용된다.
12. As an 운영자, I want 실행 직후 그 기업의 미팅 일정에 보충 결과가 반영되어 보이기를, so that 무엇이 채워졌고 무엇이 수락대기인지 바로 확인한다.
13. As an 운영자, I want 단일 기업 화면에 **전체 포화배정 버튼이 없기를**, so that 전체 대상 액션(OP-005)과 단일 기업 보충을 혼동하지 않는다.
14. As an 운영자(sub, 무역관), I want 이 배정 화면이 master 전용임이 분명하고 내겐 국내기업 열람만 열리기를, so that 내 관할(내가 관리하는 바이어) 밖의 배정을 시도하지 않는다. (ADR-0012/0013)
15. As a 참가사/바이어(받는 쪽), I want 운영자가 보충한 미팅이 내 유형에 맞는 상태로(즉시 확정 또는 수락대기) 통지되기를, so that 내 수락권이 유형 규칙대로 보호된다. (간접 — 규칙의 수혜자)

## Implementation Decisions

**진입 경로 (공유 상세)**
- OP-002 목록에서 기업 행 클릭 → `:organizationId`로 진입.
- OP-005 배정 허브에서 배정 대상 기업 선택 → 같은 라우트로 진입.
- "양쪽 진입"은 URL 종속이 아니라 네비게이션 사실 — 라우트는 하나(`:organizationId`)이고 두 화면이 같은 페이지로 보낸다. 하위 페이지로 가두지 않는 공유 상세.

**화면 구조 (3 영역)**
| 영역 | 역할 |
|------|------|
| 1. 프로필 (조회) | 기업 프로필 전체(참가사/바이어 역할, 키워드, 니즈) + 등록자 vs 비즈매칭 참가자 상태(참가자=`approved`, ADR-0009). 이 화면의 프로필은 조회 전용이다 — 신청서 정정은 OP-002의 "신청서 조회·심사"(행 "수정")와 `/admin/organizations`의 "신청서 편집"에서 한다(F-OP-002 D26, 2026-10-08) |
| 2. 미팅 일정 (조회) | 이 기업의 슬롯별 미팅 배정 상태 + **빈 슬롯 가시화** |
| 3. 단일 기업 빈슬롯 보충 (액션) | 모드① 자동 채움 / 모드② 추천→선택 |

- **D1 — 기업 디테일을 단일 공유 페이지로 분리, OP-002·OP-005 양쪽 진입(Q6, 2026-06-14).** 목록(데이터)·배정 허브(액션) 양쪽이 같은 기업 뷰를 필요로 하므로 하위 페이지로 가두지 않는다.
- **D2 — 단일 기업 재트리거는 별개 액션(ADR-0006).** 전체 포화배정(OP-005)과 다른 액션으로, **한 기업만 골라 그 기업의 빈 슬롯만** 보충한다. 같은 매칭 엔진을 쓰되 진입 관점이 "한 기업"이다.
- **D3 — 보충은 두 모드(ADR-0006).**
  - **모드① 자동 채움(AI 재트리거)** — AI가 적합도 순으로 이 기업 빈 슬롯을 채운다. **운영사 전용**. provenance = 'AI 매칭'(성과측정 기록).
  - **모드② 추천 → 선택(Forced)** — AI 추천/검색으로 운영자가 상대+슬롯을 직접 지정. provenance = 'Forced'. 동일 인터랙션이라도 **주체의 권한이 provenance를 결정**(운영자=Forced)한다(ADR-0005).
- **D4 — 추가 전용·비파괴(ADR-0006).** 재트리거는 재실행해도 기존 `accepted`/`proposed` 미팅·다른 기업을 이동·취소하지 않고 **현재 빈 슬롯만** 채운다. 취소로 다시 빈 슬롯이 생기면 재실행으로 보충(AI 자동 재충전은 아님 — 운영자가 트리거).
- **D5 — 유형별 수락, provenance와 독립(ADR-0005).** 수락 상태는 **받는 쪽 유형**이 자동 결정한다 — 초청 바이어 수신 = `accepted` 즉시 확정 / 일반 바이어·Exhibitor 수신 = `proposed` 수락대기. (단일 재트리거에선 Exhibitor도 수락대기 — 전체 포화배정의 참가사 자동확정 예외는 여기 적용 안 됨.) 운영자는 confirmed/proposed를 손으로 고르지 않으며, **일반 바이어 강제 확정 권한은 없다**. provenance(누가 만들었나)와 수락 규칙(받는 쪽이 누구냐)은 별개 축.
- **D6 — 실행 전 결과 미리보기.** 각 후보에 받는 쪽 유형 뱃지 + 결과 상태(즉시 확정/수락대기)를 미리 표시.
- **D7 — 전체 포화배정은 제외.** 전체 참가사 대상이라 OP-005 전용. 단일 기업 화면엔 부적합 — 여기는 단일 기업 빈슬롯 보충 전용.
- **D8 — OP-003 ID 재배정.** 구 OP-003(바이어 목록)은 OP-002 탭으로 통합되며 비었음 → ID 재사용.
- **접근 권한(ADR-0012/0013 — 확정):** Organizer(**master-for-this-event**) O(전체 기능) · Organizer(sub) **X** · Buyer/Exhibitor/Visitor X.
  - 이 화면의 핵심 행위인 **배정**(모드① AI 재트리거 · 모드② Forced)은 그 행사 전역 admin 행위라 **master-for-this-event**로만 게이트한다. sub(무역관)는 **국내기업을 열람만** 할 수 있고 포화배정·배정 권한이 없다(ADR-0012). 운영자 콘솔(`/organizer/*`)의 기본선은 master 전용이고, sub에게 **관할 한정** 뷰를 여는 예외는 명단 관리(OP-002 D20)에 한한다 — 배정 화면인 본 페이지엔 적용되지 않는다. sub 전용 콘솔은 별도 라우트 네임스페이스의 후속 슬라이스다.
  - sub가 **자기 관할 바이어를 대신해** 참가사에 신청하는 경로는 배정이 아니라 **대리신청**이며, 신청자는 바이어로 기록되고 받는 쪽이 참가사이므로 `proposed`(참가사 수락 필요)로 들어간다 — **Forced와 구분된다**(ADR-0013).
- **아키텍처 경계(ADR-0008):** 화면은 Next.js, 조회·보충 실행은 Next.js → FastAPI API → RDS(경계 B, Next.js는 DB 직접 접속 안 함). 권한검사·매칭 엔진(배치잡)은 FastAPI에 집중.

**식별된 deep modules** (격리 테스트 대상 후보)
- `retrigger-fill(single-org)` — 한 기업의 현재 빈 슬롯만 적합도 순으로 채우는 모드① 엔진. 입력: organizationId. 보장: 추가 전용·비파괴(기존 미팅·타 기업 불변), 결과 미팅의 수락 상태는 받는 쪽 유형으로 결정.
- `recommendation-pick` — 모드② 추천/검색 후보 생성 + 운영자가 고른 상대·슬롯을 Forced로 지정하는 모듈. 보장: 동일 비파괴 규칙, 수락 상태 유형별, provenance='Forced'.
- `acceptance-resolver` — 받는 쪽 유형 → `accepted`/`proposed` 결정(ADR-0005). 두 모드가 공유하며 OP-005와도 공유. provenance와 독립.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다. UI 위젯 내부 상태가 아니라 "재트리거 후 그 기업의 빈 슬롯만 채워지고 기존 accepted/proposed·다른 기업 일정은 그대로다" 같은 관찰 가능한 결과를 본다.
- **테스트 대상 모듈:**
  - `retrigger-fill(single-org)` — **비파괴성**: 실행 전후로 기존 `accepted`/`proposed` 미팅과 다른 기업의 일정이 불변임을 검증(추가된 슬롯만 차이). 빈 슬롯이 없으면 무변경(idempotent). 결과 미팅의 수락 상태가 받는 쪽 유형과 일치.
  - `recommendation-pick` — 운영자가 고른 상대+슬롯이 Forced provenance로 들어가고, 동일 비파괴 규칙·유형별 수락이 적용됨. 운영자가 일반 바이어 건을 강제 `accepted`로 만들 수 없음(권한 부재).
  - `acceptance-resolver` — 초청 바이어=`accepted` / 일반 바이어·Exhibitor=`proposed`. provenance를 바꿔도 결과 불변(provenance 독립성).
- **Prior art:** 앱 코드가 0인 그린필드라 기존 테스트 선례 없음 → F-BM-001과 마찬가지로 본 PRD의 모듈이 **테스트 패턴의 기준선**이 된다. `acceptance-resolver`·비파괴성 검증은 OP-005(전체 포화배정)와 공유 가능한 첫 매칭측 테스트 자산.

## Out of Scope

- **6/17(컨셉 데모)은 목업** — UI 흐름만 시연, 배정 로직 미연동.
- **적합도(fit score) 정의** — 미해결(키워드 카테고리 체계, CTO 협의 필요 — ADR-0006 선행 의존성). 두 모드의 후보 정렬은 fit score 확정 후 완성.
- **전체 포화배정** — 전체 참가사 대상이라 **OP-005 소관**. 단일 기업 화면엔 없다.
- **Forced 일반 바이어 강제 확정** — 의도적으로 제거(ADR-0005). 운영자에게 일반 바이어 강제 확정 권한 없음.
- **프로필 정정** — 위치 확정(2026-10-08): 이 화면이 아니라 **OP-002**(`/organizer/members` "신청서 조회·심사" 다이얼로그)와 관리자 콘솔(`/admin/organizations` "신청서 편집")이 같은 신청서 편집 패널로 맡는다. 운영자는 신청서의 모든 항목을 고칠 수 있고(master + 관할 안의 sub, 부스·미팅 불가 시간은 master만) 직접 수정은 승인 상태를 바꾸지 않는다 — 범위·권한·데이터 규칙은 F-OP-002 D26. 이 화면(OP-003)의 프로필 영역은 조회 전용으로 남는다.
- **Meeting Venue(룸) 배정 연동** — 장소 확정 후.
- **sub(무역관) 콘솔** — sub 권한 모델은 **ADR-0012/0013으로 확정**됐다(계정×행사 master/sub + 바이어 소유권 관할, 대리신청·체류정보). 다만 sub의 국내기업 열람·대리신청 화면은 별도 라우트 네임스페이스의 후속 슬라이스 소관이며, 본 화면(배정)은 master 전용이다.
