## Problem Statement

미팅을 마친 참가사/바이어 입장에서:

- 미팅이 끝나면 어차피 **내부 보고 문서를 만들어야 한다**(방산 보고 관행). 그런데 논의 내용을 정리해 보고서로 옮기는 일이 매번 시간이 든다.
- 좋은 상대를 만나도 **후속 거래로 잇는 장치가 없다** — "다시 거래하고 싶다"는 신호를 상대에게 전할 방법이 마땅치 않다.
- 미팅이 실제로 진행됐는지(노쇼 여부)나 상대가 우리와 맞았는지를 **남길 곳이 없으면**, 나중에 의사결정할 때 기억에만 의존하게 된다.

NABI 입장에서:

- NABI가 가진 다른 모든 데이터는 자기 신고("나는 이걸 원한다")다. **"실제로 만나보니 어땠나"라는 검증된 현실**을 줄 수 있는 데이터가 없으면, 매칭이 정말 효과가 있었는지 *증명*할 길이 없다.
- 점수(`ai_score` 등)는 **사후 소급이 불가능**하다. 미팅 발생 시점에 출처 메타를 박아두지 않으면 성과를 영영 측정할 수 없다.

## Solution

참가사/바이어 입장에서:

- 사용자가 미팅 내용을 입력하면 **AI가 핵심 논의사항 / 합의 사항 / 후속 액션으로 구조화**해, 그대로 **내보낼 수 있는 보고 문서**(PDF + 편집 가능 파일)를 만든다 — 보고 시간이 줄어든다. 이것이 리뷰를 쓰는 진짜 엔진.
- **2-step 리뷰**로 부담을 낮춘다. Step 1은 미팅 후기(진행 여부·만족도·Follow-up Intent·Love Call), Step 2는 AI 보고 문서 작성 + Fit Assessment. 정량 라벨은 AI가 추론해 제안하고 사용자는 검수만 한다.
- 좋은 상대에게는 **Love Call**(공개 신호)을 보내 후속 거래 희망을 알린다. 양측이 서로 보내면 Mutual Love Call로 격상되어 NABI가 추가 매칭을 검토한다.
- 비공개 항목(Follow-up Intent·Fit Assessment)은 조용히 기록되어 **상대에게 보이지 않고**, 보고 문서에도 섞이지 않는다.

NABI 입장에서:

- 모든 미팅 레코드에 매칭 출처 메타(`matching_type`/`ai_score`/`ai_score_reasons`)를 발생 시점에 보존하고, 리뷰 저장 시 **Fit Assessment를 그 레코드에 결합**한다. 이를 통해 AI 매칭의 precision을 재고, Open/On-site를 대조군 삼아 효과를 준실험으로 비교한다(ADR-0004).

## User Stories

1. As a 리뷰 작성 기업, I want 완료/노쇼된 미팅을 한 페이지에서 정리하기를, so that 미팅이 끝난 뒤 흩어진 결과를 한곳에 남긴다.
2. As a 리뷰 작성 기업, I want MY-001의 "리뷰 대기 N건" 섹션에서 원탭으로 리뷰에 진입하기를, so that 시간에 민감한 *할 일*을 타임라인(현황 조회)과 섞지 않고 바로 처리한다.
3. As a 리뷰 작성 기업, I want MY-001 슬롯을 눌러 그 자리에서 리뷰를 시작하기를, so that 타임라인에서 상대 기업을 확인한 흐름 그대로 작성한다.
4. As a 리뷰 작성 기업, I want 먼저 "미팅이 진행되었나"를 답하기를, so that 노쇼/정상 완료가 구분되어 진행 안 된 미팅에 불필요한 평가를 강요받지 않는다.
5. As a 리뷰 작성 기업, I want 미팅 만족도를 별점으로 남기기를, so that 매칭 품질을 간단히 평가한다. (비공개)
6. As a 리뷰 작성 기업, I want Follow-up Intent(없음/검토중/있음)를 선택하기를, so that 후속을 진행할 의향이 조용히 기록되어 매칭 효과 측정에 들어간다. (비공개)
7. As a 리뷰 작성 기업, I want Follow-up Intent가 상대에게 보이지 않기를, so that 내 속마음을 솔직히 남겨도 관계가 어색해지지 않는다.
8. As a 리뷰 작성 기업, I want 좋은 상대에게 Love Call을 보내기를, so that "실제 거래를 희망한다"는 신호가 상대 Organization에 즉시 전달된다. (공개 단방향)
9. As a Love Call 수신 기업, I want 상대가 보낸 Love Call을 배지·알림으로 받기를, so that 누가 후속 거래를 원하는지 알고 내 리뷰 작성·화답의 유인이 생긴다.
10. As a 리뷰 작성 기업, I want 양측이 서로 Love Call을 보내면 "상호 관심"으로 격상되기를, so that NABI가 후속 미팅 추가 매칭을 검토하는 신호가 된다.
11. As a 리뷰 작성 기업, I want 미팅 내용을 입력하면 AI가 핵심 논의사항/합의 사항/후속 액션으로 구조화해주기를, so that 내가 보고서를 처음부터 쓰지 않아도 된다.
12. As a 리뷰 작성 기업, I want 완성된 보고 문서를 PDF와 편집 가능 파일로 내보내기를, so that 최종 보고에 첨부하거나 회사 양식에 맞춰 수정해 제출한다.
13. As a 리뷰 작성 기업, I want AI가 미팅 내용에서 Fit Assessment(잘맞음/보통/안맞음)를 추론해 제안하기를, so that 정량 라벨을 직접 고르는 부담 없이 검수만 한다. (비공개)
14. As a 리뷰 작성 기업, I want 적합도 사유를 자유 입력으로 적기를, so that 정해진 태그에 갇히지 않고 풍부한 판단 근거를 남긴다. (비공개)
15. As a 리뷰 작성 기업, I want Fit Assessment가 상대에게 절대 공개되지 않기를, so that 솔직한 내부 판단을 안심하고 기록한다.
16. As a 리뷰 작성 기업, I want 비공개 평가(Follow-up Intent·Fit Assessment)가 보고 문서에 포함되지 않기를, so that 내부 보고용 문서에 NABI용 데이터가 새지 않는다.
17. As a 리뷰 작성 기업, I want 리뷰 완료 후 같은 페이지에서 구조화된 결과를 다시 열람하기를, so that 나중에 결과와 보고 문서를 재확인한다.
18. As a 리뷰 작성 기업, I want 재진입 시 작성 내용을 보고 수정하기를, so that 잘못 적었거나 추가할 내용이 생겨도 다시 처음부터 쓰지 않는다.
19. As a 리뷰 작성 기업, I want "상대방 불참"을 선택하면 만족도·Follow-up Intent·Love Call·Fit Assessment·보고 문서가 모두 건너뛰어지기를, so that 진행되지 않은 미팅에 평가가 강요되지 않는다.
20. As an Organizer, I want noshow가 OP-* 대시보드에서 최종 확인 가능하기를, so that 한쪽이라도 "상대방 불참"이면 noshow로 잡혀 운영 집계가 정확해진다.
21. As NABI, I want 모든 미팅에 매칭 출처 메타가 발생 시점에 보존되고 리뷰 저장 시 Fit Assessment가 결합되기를, so that AI 매칭 precision과 대조군 비교로 매칭 성과를 입증한다.

## Implementation Decisions

**리뷰 플로우 — 2-step**

- **D1 — Step 1: 미팅 후기(intake).** ① 미팅 진행 여부(진행됨/상대방 불참/내가 불참 — noshow 판정) ② 미팅 만족도(1~5 별점, 비공개) ③ Follow-up Intent(없음/검토중/있음, 비공개, 핵심 KPI) ④ Love Call 토글(공개). Q1에서 "불참" 선택 시 → noshow 플래그, 나머지 건너뛰고 저장.
- **D2 — Step 2: AI 보고 문서 작성 + Fit Assessment.** Q1 "진행됨"일 때만. 사용자가 미팅 내용 입력 → AI가 핵심 논의사항/합의 사항/후속 액션으로 구조화 → 내보내기 가능한 보고 문서. 동시에 AI가 Fit Assessment(잘맞음/보통/안맞음, 비공개)를 추론해 제안하고 사용자는 검수, 적합도 사유는 자유 입력. 확인/수정 후 저장 = 최종 결과 기록 + 보고 문서 확정.
- **D3 — Step 3: 리뷰 완료 후.** 같은 페이지에서 구조화된 결과 열람 + 보고 문서 내보내기. 재진입 시 작성 내용 표시·수정 허용.
- **D4 — AI는 요약이 아니라 능동 작성 도우미.** "내가 쓴 걸 AI가 요약"은 가치가 불명확 → AI가 구조화·제안을 능동 수행. 리뷰 폼 + AI 어시스턴트는 단일 페이지(쓰기→확인이 하나의 흐름). 기본 문항은 최소화하고 AI 장문으로 완료율을 확보한다.

**1차 산출물 = 내부 보고 문서**

- **D5 — 보고 문서가 사용자측 핵심 산출물(엔진).** 화면 안 기록에 그치지 않고 **밖으로 꺼낼 수 있어야** 보고 시간 절감이 실현된다. 형태: **PDF 다운로드**(최종 보고 첨부) + **편집 가능 파일**(회사 양식 수정 후 제출 — 구체 형태는 프로토타입에서: docx/pptx/마크다운 등).
- **D6 — 문서 내용 = AI 구조화 본문(핵심 논의사항/합의 사항/후속 액션) + 미팅 메타(상대 기업·일시·장소).** 비공개 항목(Follow-up Intent·Fit Assessment)과 **전사 원문(Transcript)**은 보고 문서에 **포함하지 않는다**(D21) — 내부 보고용이지 NABI 데이터 노출용이 아니며, raw 전사는 검수 참고일 뿐 산출물이 아니다. (전사 부록 포함 토글은 후속 옵션, 기본 미포함.)

**비공개 항목 vs 공개 Love Call**

- **D7 — 상대측 평가를 Love Call(공개)과 Fit Assessment(비공개) 2종으로 분리.** 청중·공개 여부·수집 단계가 다르다. Love Call은 상대 Organization에 가는 액션, Fit Assessment는 본인 의사결정 + NABI 성과 측정용 비공개 판단.
- **D8 — Follow-up Intent(측정)와 Love Call(액션)은 별개 항목으로 유지.** Follow-up Intent는 조용히 기록되는 내 속마음(비공개 KPI, 누락 없이 받음), Love Call은 상대에게 날아가는 메시지(선택적 공개).
- **D9 — Love Call은 단방향 통지.** 보내면 상대에게 즉시 전달(화답 불요). 단방향이어야 "상대 리뷰 미작성 시 화답 유인"이 성립한다. 양측이 서로 보내면 **Mutual Love Call**로 격상 → NABI가 추가 매칭(후속 미팅) 검토 신호로 사용. 연락처 공개는 제외.
  - 러브콜 메일(회의록 기반 AI 초안 → 검토 → '보내기', `POST /meetings/{id}/love-call/mail/send`)은 행사 설정 "참가사·바이어 알림 메일"이 꺼진 행사에서는 보내지 않는다 — 409 `PARTICIPANT_EMAIL_DISABLED`, 메일·발송 기록 없음, 화면은 '발송하기'를 잠그고 안내(AI 초안 작성·확인은 그대로). 2026-10-16 발주사 요구("참가기업·바이어에게 어떠한 메일도") — 결정·세부는 F-NT-001 "행사별 참가자 알림 메일 스위치" 절.
- **D10 — Fit Assessment 3점 = AI 추론 + 사용자 확인.** 정량 라벨의 부담을 0으로. 적합도 사유는 **자유 입력** + AI가 사후에 카테고리로 태깅(성과 분석 보조). AI 분류 시드 카테고리: 예산/기술 성숙도/도입 시기/생산능력/인증·규격/제품 적합성 + (검토) 보안등급/수출통제 등 방산 특수 축. 시드는 출발점일 뿐 사용자 입력은 갇히지 않는다. ⚠ 일회성 이벤트라 이 사유는 매칭 피처 개선용이 아니라 성과 분석·자산의 보조 재료.

**녹음 전사 입력 + 결과 표시 (2026-06 확정)**

- **D20 — 입력 = 녹음 업로드(주) + 텍스트 폴백, 전사는 비동기.** 30분 분량을 동기로 못 묶으므로 transcribe는 **접수(202)+job_id → 백그라운드 전사·구조화 → 폴링**으로 처리하고, 완료 시 **"회의록 정리 완료" 알림**(`review_ready`)으로 알린다. 화면을 벗어나도 됨. (구현됨)
- **D21 — 결과 표시 = 회의록 본문 3섹션(편집) + 전사 원문(읽기전용·사이드 시트).** 사용자가 보는 결과는 두 층: ① **Report Sections**(핵심 논의사항/합의 사항/후속 액션 — 편집 대상, 산출물) ② **Transcript**(전사 원문 — 읽기전용 검수 참고). **편집은 3섹션에서만**(전사를 직접 교정하지 않음 — 산출물은 요약이지 원문이 아니며, 30분 raw 전사 편집은 보고시간 절감 취지와 충돌). 전사가 무언가 놓쳤으면 사용자는 3섹션에 보완한다. **표시 방식 = 사이드 시트(드로어)** — 긴 전사에서 ① 페이지를 안 늘리고(시트 내부 스크롤) ② 요약을 안 가려 대조하며 교정 가능 ③ 모바일선 바텀시트. (프로토타입으로 시트/아코디언/모달 비교 후 시트 확정 — 아코디언은 인라인이라 긴 전사 시 페이지 폭증, 모달은 요약을 가려 대조 불가.)
- **D22 — 화자 구분 = Claude 텍스트 추정("AI 추정 화자").** 음성 기반 diarization(pyannote/Deepgram 등) 대신 전사 텍스트를 Claude가 우리/상대로 추정. 2인 B2B 미팅이라 역할이 뚜렷해 충분하고 추가 인프라·비용 최소. **"AI 추정 화자"로 명시**(음성 분리 아님 → 검수 보조용이지 증빙 아님). 정확도가 핵심이 되면 음성 diarization으로 후속 업그레이드(원본 녹음 보관되어 재처리 가능).
- **D23 — 녹음 원본·전사는 업로더 전용 비공개(ADR-0004 유지).** 한 미팅을 양사가 함께 진행해도 **녹음/전사는 공유하지 않는다**(올린 쪽 전용, 상대 비노출). "사실(녹음·전사) 공유 / 판단(Fit·Follow-up) 비공개" 분리도 검토했으나, 녹음 동의(consent)·신뢰 리스크가 커 ADR-0004 비공개 경계를 **유지**하기로 결정. 녹음 원본 보관 목적은 NABI의 **전사·구조화 성능 검증 + 재처리 원천**(서비스 제공자 관점)이며 사용자 표시와 별개.

**provenance 결합 저장 (ADR-0004)**

- **D11 — 미팅 리뷰 ↔ 매칭 출처 결합 저장.** 모든 미팅 레코드에 `matching_type`(ai/open/forced/on_site)/`ai_score`/`ai_score_reasons`를 **발생 시점에 영구 보존**하고, 리뷰 저장 시 Fit Assessment를 결합한다. AI Matching은 `(ai_score, 실제 적합도)` 페어로 precision 측정(성과 입증). Open/On-site는 AI 점수가 없지만 **대조군** — "AI 추천군 vs 자율 발생군" 적합도·전환율을 준실험으로 비교. `matching_type`은 모든 리뷰의 1급 분석 축. 점수는 사후 소급 불가 → 발생 시점 결합 저장 필수.
- **D12 — 일회성 이벤트 → 보정 루프 폐기, 성과 측정·입증 + 자산화로.** 같은 코호트 재집결 없음. precision은 "다음에 더 잘하려고"가 아니라 "잘했다고 증명하려고" 잰다. 적합도 자유 사유는 분석·자산의 보조 재료로 격하.

**진입 경로 / 접근 권한 / 아키텍처 경계**

- **D13 — 진입 = MY-001 "리뷰 대기" 섹션 주 경로 + 슬롯 보조.** 리뷰 미작성 completed/noshow 미팅을 묶어 노출 → 원탭. 보조로 MY-001 슬롯 터치 → 하단 패널 "리뷰 작성". 푸시/이메일 딥링크(미팅 completed 전환 시 발송)는 nice-to-have(지금 구현 대상 아님, 가능하면 제공). MY-001 타임라인(현황 조회)과 "리뷰 대기"(할 일)를 분리해 진입 어색함 해소.
- **noshow 판정:** Q1 "상대방 불참" 응답 → noshow 플래그. 한쪽이라도 "상대방 불참"이면 noshow. noshow 시 만족도/Follow-up Intent/Love Call/Fit Assessment/보고 문서 모두 건너뜀. Organizer가 OP-* 대시보드에서 최종 확인.
- **접근 권한:** 참가사·바이어 공용 단일 라우트(`/meetings/:meetingId`). 본인이 참석한 미팅의 본인측 리뷰만 작성·열람. Organizer는 OP-* 대시보드에서 집계 확인(본 페이지 직접 작성 대상 아님).
- **아키텍처 경계(ADR-0008, 경계 B):** 폼·내보내기 UI는 Next.js, 저장/조회·AI 보고 문서 생성·Love Call 전송은 Next.js → FastAPI API → RDS. **Next.js는 DB에 직접 접속하지 않으며** 권한검사는 FastAPI 한 곳에 집중. AI 구조화는 backend의 Claude API(키는 backend에만). 비공개/공개 노출 규칙도 FastAPI가 강제한다(상대 조회 응답에서 Follow-up Intent·Fit Assessment를 절대 내보내지 않음).

**식별된 deep modules** (격리 테스트 대상 후보)

- `review-capture` — 2-step 리뷰 진행/단계별 저장/noshow 분기/재진입 수정/Fit Assessment 검수를 캡슐화. Step 1 응답에 따라 Step 2~ 건너뛰기를 결정하는 상태 모듈.
- `love-call-signal` — Love Call 단방향 전송, 양방향 성립 시 Mutual Love Call 격상 판정, 공개 신호(Love Call) vs 비공개 항목(Follow-up Intent·Fit Assessment)의 노출 경계.
- `review-provenance-binding` — 미팅 발생 시점 출처 메타 보존 + 리뷰 저장 시 Fit Assessment 결합을 원자적으로 수행하는 경계(precision·대조군 분석의 전제, 사후 소급 불가).

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다. 폼 컴포넌트 내부 상태가 아니라 "Q1에서 '상대방 불참'을 고르면 만족도/Follow-up Intent/Love Call/Fit Assessment 입력이 노출되지 않고 noshow로 저장된다" 같은 관찰 가능한 결과를 본다.
- **테스트 대상 모듈:**
  - `review-capture` — 2-step 진행과 저장/재진입 수정, noshow 분기(불참 선택 시 후속 항목 스킵), AI 제안 Fit Assessment 검수 후 저장.
  - `love-call-signal` — **노출 규칙 검증(핵심):** Love Call은 상대 조회 응답에 보이고(공개 단방향), Follow-up Intent·Fit Assessment는 상대 응답에서 **절대 노출되지 않는다**(비공개). 양측이 서로 Love Call을 보내면 Mutual로 격상된다. 보고 문서 산출물에 비공개 항목이 포함되지 않는다.
  - `review-provenance-binding` — **원자성·결합:** 미팅 발생 시점 `matching_type`/`ai_score`가 보존되고, 리뷰 저장 시 Fit Assessment가 그 레코드에 결합된다. AI 매칭 건은 `(ai_score, 적합도)` 페어가 측정 가능하게 남고, Open/On-site는 `ai_score` 없이 대조군으로 분류된다.
- **Prior art:** 앱 코드가 아직 0인 그린필드라 기존 테스트 선례 없음 → F-BM-001과 함께 본 PRD의 모듈이 첫 테스트 패턴의 기준선이 된다. 특히 노출 규칙(공개/비공개)은 **권한·노출 경계 테스트의 첫 사례**로, FastAPI 응답 계약을 외부 동작으로 검증하는 패턴을 세운다.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 리뷰 폼·AI 어시스턴트·보고 문서 내보내기 UI 시연만, 실제 AI 구조화 생성·저장·결합·Love Call 전송은 이 슬라이스 구현 범위.
- **인앱 1:1 대화창(사람↔사람)** — v1 제외(backlog). 풀 메시징은 무게가 크다. Love Call의 가치는 배지/이메일/운영사 집계로 9월에 완결한다.
- **Mutual Love Call의 대화 채널 자동 개설** — v1 범위 밖(backlog). 상호 관심 시 v1 처리는 **NABI가 추가 매칭(후속 미팅 배정)을 검토**하는 신호로만 사용하며, 채널 자동 개설은 하지 않는다(D9·CONTEXT.md Love Call과 일관).
- **실거래 전환 추적** — 방산 거래는 전시 후 수개월. 9월엔 Follow-up Intent/Love Call/Mutual까지만 잡고 실거래 추적은 이후 과제(ADR-0004 범위 경계).
- **적합도 사유 카테고리 체계 확정** — 시드 카테고리는 AI 사후 태깅의 출발점일 뿐. 분류 체계 고정은 범위 밖(일회성 이벤트라 피처 개선 목적 아님).
- **미팅 중 실시간 데이터(채팅/녹음) 연동·참가사 서류 플로우 연계** — 향후 고도화. (녹음 *업로드*는 주 입력으로 포함 — 실시간 연동과 별개)
- **원본 녹음 재생(audio playback)** — 범위 밖(D21·Q5). 전사 텍스트만으로 검수 충분. 재생하려면 S3 보관 + 인증 조회 경로 필요 → 필요해지면 후속.
- **음성 기반 화자 분리(diarization)** — 범위 밖. Claude 텍스트 추정으로 시작(D22), 정확도 핵심 시 후속(원본 보관되어 재처리 가능).
- **녹음 원본 바이트 영구보관(S3) 실연동** — 데모는 인메모리(FakeStorage)라 키만 기록·바이트 미보관. 실 S3(보관 목적=성능 검증/재처리) 연동은 후속(별도 인프라).
- **연락처 공개** — 제외.

## Further Notes

- **구 EX-002/EX-005 흡수.** 구 EX-005(참가사 미팅 결과)는 본 페이지로 통합되어 **참가사·바이어 공용 단일 라우트**(`/meetings/:meetingId`)가 되었다. 구 EX-002(참가사 미팅 결과 요약)의 결과 요약은 본 페이지의 "리뷰 완료 후 열람 + 보고 문서 내보내기"로 흡수 — "결과 요약"은 일부 산출물일 뿐이라 페이지명을 "미팅 리뷰"로 통일했다.
- **2026-06-14 갱신:** Mutual Love Call = NABI 추가 매칭 검토 신호로 확정, 대화창 자동 개설은 v1 제외. schema.sql의 `conversation_channels` 테이블은 향후(backlog) 대비 산출물이며 v1에서 채워지지 않는다.
- **핵심 통찰:** NABI의 다른 모든 데이터는 자기 신고("나는 이걸 원한다"). 미팅 리뷰만이 "실제로 만나보니 어땠나"라는 검증된 현실을 준다 — 매칭 성과를 *증명*할 유일한 데이터.
- **프로토타입에서 확정할 사항:** AI 어시스턴트 인터랙션(채팅형/에디터형/하이브리드), 장문 입력 가이드(플레이스홀더/구조화 서브필드/AI 질문형), Love Call UI 배치(Step 1 내 토글/버튼), Fit Assessment 검수 UX, 적합도 사유 입력 + AI 태깅 칩, 보고 문서 내보내기 형태·동선(PDF/편집 파일/미리보기·다운로드).
