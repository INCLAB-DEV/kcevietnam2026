# F-BM-001: 바이어 프로필 작성

> 딥링크 로그인으로 인증된 바이어가 비즈매칭을 위해 **프로필을 작성·제출하는 3단계 폼**(기본정보 · 관심분야·소개 · 확인·제출 — 2026-06-29 단순화. 참가사 BM-002는 5단계). 매칭 정확도의 입력이 되는 구조화된 니즈 수집. (구버전의 미등록 Visitor→On-site Buyer 자기전환 게이트는 폐지됨 — 정책 변경 2026-07-02.)

## Problem Statement

바이어 입장에서:

- 비즈매칭에서 나에게 맞는 참가사를 만나려면 내 니즈(찾는 제품·용도·예산·도입시기)를 충분히 전달해야 한다. 그런데 한 화면에서 한꺼번에 다 요구하면 부담스러워 중간에 포기하게 된다.
- 이미 작성한 내용을 나중에 일부만 고치고 싶은데, 처음부터 다시 쓰게 만들면 안 된다.

## Solution

바이어 입장에서:

- 작성을 **3단계로 쪼갠 폼**으로 받는다. 단계마다 저장되어 중간에 나가도 **이어서 쓸 수 있다**. 부담이 줄고 완성도가 올라간다. **폼은 '저장'만 한다**(마지막 버튼 `저장하고 나가기` → `/welcome`) — 작성·저장과 제출을 구분한다(2026-06-30, FE ADR-0002 §4).
- 작성을 마치면 **`/welcome`에서 제출**한다(필수 충족 시 `제출하기`, 확인 다이얼로그 후). 제출하면 **운영 검토(승인) 대기**(`submitted`) 상태가 되고, 주최사/KOTRA 승인을 받으면 **비즈매칭 참가자로 승격**되어 매칭 대상이 된다(ADR-0009 2단계 게이트). 제출 후(`submitted`/`approved`/`rejected`)에 폼에 들어오면 **읽기전용 "신청서 보기"**(요약 + 돌아가기, 수정 차단)로 렌더된다.
- 작성 후에는 내 프로필(F-BM-004)에서 **특정 단계만 골라 바로 수정**할 수 있다.

## User Stories

1. As a 바이어, I want 프로필 작성이 여러 단계로 나뉘어 있기를, so that 한 번에 너무 많은 입력을 강요받지 않는다.
2. As a 바이어, I want 각 단계가 자동 저장되기를, so that 중간에 나가도 처음부터 다시 쓰지 않고 이어쓸 수 있다.
3. As a 바이어, I want 기관/담당자 등 기본정보가 가능한 한 미리 채워져 있기를, so that 이미 등록 때 준 정보를 다시 입력하지 않아도 된다.
4. As a 바이어, I want 관심 분야를 키워드로 선택/입력하기를, so that 내가 찾는 영역이 매칭에 반영된다.
5. As a 바이어, I want 찾고 있는 제품/기술·운용 환경·요구 스펙·도입 단계를 자유롭게 적기를, so that 정형 항목으로 다 담기 어려운 구체 니즈를 전달한다.
6. As a 바이어, I want 예산 범위·도입 시기·현재 도입 현황을 입력하기를, so that 조건에 맞는 기업이 우선 매칭된다.
7. As a 바이어, I want 마지막 단계에서 입력 내용을 요약 확인하고 제출하기를, so that 잘못 적은 부분을 제출 전에 바로잡는다.
8. As a 바이어, I want 제출하면 운영 승인 대기 상태가 되었음을 안내받기를, so that 승인을 거쳐 비즈매칭 참가자(매칭 대상)가 된다는 흐름을 이해한다.
10. As a 현장(On-site) 바이어, I want 사전등록·초청 바이어와 동일한 화면·플로우를 쓰기를, so that 바이어 유형(subtype)에 따라 기능이 제한되지 않는다.
11. As a 바이어, I want 내 프로필에서 특정 단계만 골라 수정 화면으로 바로 진입하기를, so that 전체를 다시 거치지 않고 일부만 고친다.
12. As a 바이어, I want 작성 중인 프로필이 아직 매칭에 노출되지 않기를, so that 완성되지 않은 정보로 매칭되지 않는다.
13. As a 바이어, I want 작성을 모바일에서 편하게 하기를, so that 현장에서 휴대폰으로도 막힘없이 입력한다.
14. As a 참가사(상대측), I want 바이어 프로필이 충분히 구조화되어 있기를, so that 어떤 바이어인지 판단해 미팅 가치를 가늠한다. (간접 — 수집 품질의 수혜자)

## Implementation Decisions

**진입 경로**
- 딥링크 로그인 후(사전등록·초청·현장 바이어) — 프로필 미작성 시 안내.
- BM-004 내 프로필 — 항목별 수정 시 `/apply?step=N&from=profile` 딥링크로 특정 단계 진입.

**폼 구성 (실제 DX Korea 바이어 등록폼 기준)**

>   `budget_range`, `adoption_timeline`. (이름·직위 국/영은 확정결정 #3 "바이어=영문"을 **갱신** — 바이어

> - **바이어 자가등록 폼에서 제외**: `buyer_attendees`(담당자 복수)·`buyer_recommended_buyers`(추천)·
>   `participation_route`·`kst_available_time`·`kotra_member`·`note`·`files`. 이들은 **KOTRA 상담주선
>   요구항목**이라 폐기가 아니라 **운영/무역관 슬라이스로 이관**(바이어 본인 폼 밖). 컬럼은 유지.
> - **정합 작업(후속)**: bm-profile-fields §3 + schema.sql 재동기화는 db-schema-keeper로, backend #26
>   Pydantic/모델/Alembic은 backend 세션에서. (이 프런트 워크트리 밖.)
>
> 📝 **메모(#1, 별도 세션 진행 중) — 승인 후 수정 불가 정책.** 현재 store/PRD는 "approved 후 수정 시 멱등
> 유지"(§6)지만, **승인(approved)·제출(submitted) 종단 상태에서는 수정 불가**로 정책 변경이 다른 세션에서
> 진행 중. 확정되면 §6과 buyer-profile-store(saveStep/submitProfile 가드)를 갱신한다(codex P1 #1).

- **D1 — 3단계 분할 폼.** 한 번에 받기엔 많아 단계별로 이탈을 줄이고 완성도를 확보한다. **당초 5단계였으나 입력 부담 최소화를 위해 담당자(복수)·참가정보/추천 단계를 폼에서 덜어 3단계로 단순화**(2026-06-29, 위 "폼 구성" 참조). 참가사(F-BM-002)는 5단계 유지 — 두 폼의 단계 수는 다르다.
- **D2 — 단계별 저장(이어쓰기).** 각 단계 완료 시 서버에 저장, 중간 이탈 후 재개 가능.
- **D3 — 항목별 수정은 `/apply?step=N&from=profile` 딥링크.** BM-004에서 특정 단계만 바로 연다.
- **D4 — (구) Visitor 자기전환 게이트 폐지(정책 변경 2026-07-02).** 과거엔 미등록 방문자(Visitor)가 미팅 신청 시 게스트 폼 없이 이 폼을 거쳐 On-site Buyer로 자기전환했으나, 미인증 사용자의 서비스 페이지 진입 자체가 막히면서(라우트 가드 → `/login`, FE ADR-0002) 이 자기전환 경로는 폐지됐다. BM-001은 **딥링크 로그인으로 인증된 바이어의 프로필 작성·제출 폼**이다. 현장(On-site) 바이어는 자기전환 폐지로 **생성 경로가 없어져 현재 만들지 않는다**(별도 정책 변경 전까지) — subtype `on_site`는 데이터 값으로만 남는다.
- **D5 — 제출 → 운영 승인 → 매칭 노출(ADR-0009 갱신, 2단계).** 제출 시 `application_status`를 `submitted`로 전환(사용자 작성 완료). **제출은 폼이 아니라 `/welcome`의 액션에서 트리거**(저장/제출 분리, FE ADR-0002 §4). KOTRA 요구사항 "관리자 승인을 통해 최종 등록"에 따라 **주최사/KOTRA 승인 시 `approved`**로 전환되고, **매칭 엔진·기업 목록은 `approved`만 대상**으로 한다(작성 중·미승인 프로필 비노출). 상태머신·감사컬럼은 `bm-profile-fields §6`.
- **D6 — 제출은 원자적 트랜잭션(ADR-0009).** 프로필 데이터 최종 저장과 `submitted` 전환을 하나의 트랜잭션으로 묶어, "status는 submitted인데 데이터 불완전"인 반쪽 상태를 구조적으로 막는다(승인은 별도 운영 슬라이스).
- **접근 권한:** Buyer(사전등록·초청·현장) O(본인 프로필, 딥링크 로그인 인증) · Exhibitor X(참가사는 F-BM-002) · Organizer X. 미인증 사용자는 진입 불가(라우트 가드 → `/login`).
- **아키텍처 경계(ADR-0008):** 폼은 Next.js, 저장/조회는 Next.js → FastAPI API → RDS(경계 B, Next.js는 DB 직접 접속 안 함). 진입 전 인증 게이트(딥링크 + DX Korea 인증 + 최초 시 NABI 약관동의·계정 발급, ADR-0007).

**식별된 deep modules** (격리 테스트 대상 후보)
- `profile-form-state` — 3단계 진행/단계별 저장/재개/단계 검증을 캡슐화하는 상태 모듈.
- `participant-promotion` — 제출 시 프로필 저장 + `application_status=submitted`를 원자적으로 수행하는 트랜잭션 경계.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다(폼 컴포넌트 내부 상태가 아니라 "3단계까지 쓰고 나갔다 들어오면 1~3단계 값이 보존된다" 같은 관찰 가능한 결과).
- **테스트 대상 모듈:**
  - `profile-form-state` — 단계별 저장/재개, 미완 단계 검증, `/apply?step=N` 진입.
  - `participant-promotion` — **원자성**: 저장 또는 status 중 하나라도 실패하면 둘 다 롤백(반쪽 제출 불가). 매칭 노출은 `approved`에서만(제출=submitted → 운영 승인=approved, D5).
- **Prior art:** 앱 코드가 아직 0인 그린필드라 기존 테스트 선례 없음 → 본 PRD의 모듈이 **첫 테스트 패턴의 기준선**이 된다. (외부 의존 없는 첫 수직 슬라이스라 통합 테스트 출발점으로 적합.)

## Out of Scope

- **6/17 컨셉 데모는 목업** — 폼 UI 시연만, 실제 저장/제출(`submitted`)은 이 슬라이스 구현 범위. 운영 승인(`approved`)은 별도 운영 슬라이스.
- **(해결됨) 관심분야 분류체계** — 실제 등록폼이 **방산 13분야 고정 리스트**로 확정(`bm-profile-fields §1.1`). (구) "잠정 자유입력" 종료 — 시드 keywords + 조인.
- **바이어용 문서 업로드 Smart Fill** — Smart Fill(문서 업로드 추출)은 참가사 측(F-BM-002)에 한정. 바이어 측 자동완성은 v1 범위 밖.
- **매칭 로직 자체** — 배정·적합도는 OP-005 / ADR-0006 소관.
- **실제 명단 컬럼 기반 prefill 매핑** — 주관사 명단 컬럼 구조 확정(선행 블로커) 후.
