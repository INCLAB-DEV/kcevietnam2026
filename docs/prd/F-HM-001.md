# F-HM-001: 홈 대시보드

> **승인된(`approved`)** 참가사·바이어가 본 서비스(nav)에 들어와 **처음 만나는 공용 허브**. "지금 내 미팅이 어떤 상태인지"와 "지금 무엇을 해야 하는지"(받은 요청·후기 입력·확정 미팅)를 한 화면에 모아 각 기능으로 분기하는 액션 허브. 구 EX-000(참가사 전용 홈)을 참가사/바이어 공용으로 일반화·부활. **로그인 직후 첫 랜딩은 `/welcome`(HM-002)** 이고, 승인 + 신청기간 종료 게이트를 통과해야 이 `/`에 진입한다(FE ADR-0002).

## Problem Statement

참가사·바이어 입장에서:

- 로그인했는데 내 미팅이 지금 어떤 상태인지(몇 건이 확정됐고, 몇 건이 내 응답을 기다리고, 오늘 누구를 언제 만나는지) 한눈에 보이지 않으면, 매번 여러 화면을 돌며 직접 확인해야 한다.
- 받은 미팅 요청에 응답하지 않으면 매칭이 성사되지 않고, 끝난 미팅의 후기를 입력하지 않으면 보고 문서도 성과 데이터도 남지 않는다. 그런데 이 "놓치면 손해인 할 일"이 어딘가 묻혀 있으면 그냥 지나친다.
- 행사 당일에는 휴대폰으로 빠르게 "다음에 뭘 하면 되지"를 확인하고 싶은데, 정보가 흩어져 있으면 현장에서 막힌다.
- 참가사와 바이어는 보는 데이터의 결이 조금 다른데(받는 요청의 수락 규칙·프로필 형태), 화면이 한쪽 역할만 가정하면 다른 역할은 어색하게 쓴다.

## Solution

참가사·바이어 입장에서:

- 승인·신청기간 게이트를 통과해 본 서비스에 들어오면 `/` 대시보드에 닿는다(로그인 직후 첫 랜딩은 `/welcome`). **미팅 현황 요약(상태별 건수) · 오늘 미팅 일정 · 알림(할 일)** 세 블록이 한 화면에 모여, 지금 내 상태와 다음 액션을 즉시 파악한다.
- 놓치기 쉬운 액션(받은 요청·후기 입력·내 요청 수락됨)은 **알림 블록**으로 따로 모아 보여주고, 누르면 처리 화면(MY-001/MY-002)으로 바로 데려간다.
- 같은 라우트·같은 레이아웃을 참가사·바이어가 **공용**으로 쓰되, 데이터는 **내 역할에 맞게** 채워진다(수락 규칙 차이).

## User Stories

1. As a 참가사/바이어, I want 로그인하면 곧장 내 홈 대시보드로 떨어지기를, so that 어디로 갈지 고르지 않고 바로 내 상태를 본다.
2. As a 참가사/바이어, I want 내 미팅을 상태별 건수(예정·수락대기·완료·노쇼)로 요약해서 보기를, so that 전체 일정 흐름을 한눈에 가늠한다.
3. As a 참가사/바이어, I want 오늘 잡힌 미팅을 시간순으로 보기를, so that 오늘 누구를 언제 어디서 만나는지 즉시 안다.
4. As a 참가사/바이어, I want 오늘 일정 항목을 누르면 내 미팅(MY-001)의 해당 슬롯으로 이동하기를, so that 상세 확인·조치를 이어서 한다.
5. As a 일반 바이어/참가사, I want 내가 응답해야 하는 수락대기(`proposed`) 건이 따로 강조되기를, so that 응답을 빠뜨려 매칭을 놓치지 않는다.
6. As a 참가사/바이어, I want 끝난 미팅(완료/노쇼) 중 후기 미작성 건이 "후기 입력 대기"로 모이기를, so that 보고 문서·성과 데이터를 남기는 일을 빠뜨리지 않는다.
7. As a 참가사/바이어, I want 후기 입력 대기 항목을 누르면 미팅 리뷰(MY-002)로 바로 가기를, so that 곧장 후기를 작성한다.
8. As a 참가사/바이어, I want 받은 미팅 요청 알림을 보기를, so that 누가 나를 만나고 싶어 하는지 알고 수락/거절로 이어간다.
9. As a 참가사/바이어, I want 내가 보낸 요청이 수락되어 확정됐다는 알림을 보기를, so that 새로 잡힌 미팅을 인지하고 일정을 챙긴다.
10. As an 초청 바이어, I want 내가 받는 미팅이 거부 단계 없이 바로 확정으로 보이기를, so that 일반 바이어와 다른 내 수락 규칙이 화면에 맞게 반영된다.
11. As a 참가사/바이어, I want 모바일에서 대시보드를 막힘없이 쓰기를, so that 행사 현장에서 휴대폰으로도 다음 할 일을 빠르게 확인한다.
12. As a 참가사/바이어, I want 글로벌 네비게이션의 "홈"으로 언제든 대시보드로 돌아오기를, so that 깊은 화면에서도 다시 허브로 복귀한다.
13. As an 운영사, I want 내 랜딩이 이 화면이 아니라 운영 대시보드(OP-001)이기를, so that 권한·지표가 다른 운영 업무를 별도 화면에서 본다.

> 내 프로필 요약·완성도·작성 유도 관련 스토리는 블록 ③ 제거(2026-06-22, 이슈 #16)로 삭제. 프로필 조회·수정은 BM-004/005가 담당한다.

## Implementation Decisions

**진입 경로**

| 진입점 | 트리거 |
|--------|--------|
| 로그인(AU-001) → 비즈매칭 모집(HM-002) | 역할이 참가사/바이어면 로그인 직후 `/welcome`(HM-002)으로 분기. `/welcome`이 **승인(`approved`) AND 신청기간 종료**면 본 서비스 `/`으로 진입시킨다(FE ADR-0002). 운영사는 `/organizer`(OP-001) |
| 글로벌 네비게이션 | "홈" 메뉴 → `/` (이미 본 서비스에 들어온 승인 참가자만 nav 노출) |

**화면 블록 구성** — 세 블록으로 고정. (구 블록 ③ "내 프로필 요약"은 제거 — D5 참조.)

| 블록 | 내용 | 이동 |
|------|------|------|
| ① 미팅 현황 요약 | 상태별 건수 카드: 미팅 예정(`accepted` 진행 전) · 수락 대기(`proposed`) · 미팅 완료(`completed`) · 노쇼(`noshow`) · 후기 입력 대기(completed/noshow인데 리뷰 미작성) | 카드별 → MY-001 / MY-002 |
| ② 오늘 미팅 일정 | 오늘 날짜 미팅을 시간순. 상대 기업·시간·장소(Meeting Venue) | 항목 → MY-001 해당 슬롯 |
| ④ 알림(할 일) | 받은 미팅 요청(`proposed` 수신) · 후기 입력 필요(completed/noshow 미작성) · 내 요청이 수락됨(`proposed`→`accepted`) | 각 → MY-001 / MY-002 |

- **D1 — 본 서비스 진입 후 허브를 HM-001 대시보드로** (2026-06-14, 2026-06-29 게이트 반영). "오늘 할 일 + 일정" 액션 허브가, 미팅 타임라인만 있는 MY-001보다 본 서비스 진입 직후 첫 화면으로 강하다. **단, 로그인 직후 첫 랜딩은 `/welcome`(HM-002)** 이고 HM-001은 승인 + 신청기간 종료 게이트를 통과한 참가자가 닿는 화면이다(FE ADR-0002). 미팅 타임라인(MY-001)은 전원 공용 단일 라우트(CONTEXT.md Role-based Route 예외).
- **D2 — 참가사/바이어 공용 단일 라우트 `/`.** 구 EX-000(`/exhibitor`)은 참가사 전용을 암시했으나 바이어도 같은 허브가 필요하다. 한 라우트·한 레이아웃을 쓰고 데이터만 역할별로 채운다(역할 분기는 화면 안에서). MY-001(`/meetings`)도 동일하게 공용.
- **D3 — 현황(상태 건수)과 할 일(알림)을 분리.** 현황은 전체 그림(②④의 원천인 미팅 타임라인은 MY-001), 알림은 "지금 내가 직접 손대야 하는 것"만 추린다. 알림 3종 = 받은 요청 · 후기 입력 필요 · 내 요청 수락됨 — 참가측이 놓치기 쉬운 액션 항목.
- **D4 — 상태값·수락 규칙은 ADR-0005를 그대로 따른다.** 건수·알림은 Schedule Table의 상태(`proposed`/`accepted`/`completed`/`noshow`/`cancelled`)로 집계한다. "수락 대기"(`proposed`)는 **일반 바이어·Exhibitor가 받는 건**에만 생기고, **초청 바이어가 받는 건은 거부 단계 없이 바로 `accepted`** 로 보인다(받는 쪽 유형이 규칙을 정함; provenance와 독립). 따라서 같은 화면이 내 역할·유형에 따라 다른 건수 분포를 보여준다.
- **D5 — 내 프로필 요약 블록(구 ③) 제거** (2026-06-22, 이슈 #16). 당초엔 `application_status`를 반영해(ADR-0009) 미제출자에겐 작성 유도를, 참가자에겐 완성도·핵심 요약을 보였다. 그러나 HM-001은 승인(`approved`) + 신청기간 종료라야 진입하는 화면(FE ADR-0002)이라 "작성 유도"는 도달 불가능하고 "요약·완성도"는 BM-004/005(내 프로필)와 중복이다. 따라서 블록과 읽기 측 게이트(`participant-gate-view`)를 함께 들어내고, 프로필 조회·완성도·수정 진입은 BM-004/005로 일원화한다. (`application_status` 게이트 자체는 BM-001/002 제출 흐름·ADR-0009에 그대로 남는다 — 데이터 모델 변경 없음.)
- **D6 — 운영사 제외.** 권한·지표가 달라 운영사 랜딩은 OP-001 별개. HM-001은 참가측(참가사/바이어) 전용.
- **접근 권한:** Exhibitor / Buyer O(본인 기업 데이터) · Visitor X(미인증 접근 불가 — 딥링크 로그인 필요; 라우트 가드 → `/login`) · Organizer X(OP-001로).
- **아키텍처 경계(ADR-0008):** 화면은 Next.js, 대시보드 데이터(건수 집계·오늘 일정·알림)는 Next.js → FastAPI API → RDS(경계 B, Next.js는 DB 직접 접속 안 함). 권한검사(내 기업 데이터만)는 FastAPI 한 곳에서 Cognito JWT 검증으로 처리. 진입 전 인증 게이트(딥링크 + DX Korea 인증 + 최초 시 약관동의·NABI 계정 발급, ADR-0007).

**식별된 deep modules** (격리 테스트 대상 후보)
- `home-dashboard-data` — 한 사용자의 역할·유형을 입력받아 ①②④ 세 블록(상태별 건수·오늘 일정·알림 3종)을 조립해 반환하는 읽기 전용 집계 모듈. 화면은 이 결과를 그리기만 한다.
- `meeting-status-rollup` — Schedule Table 행들을 상태(`proposed`/`accepted`/`completed`/`noshow`)별 건수와 "후기 입력 대기"(완료/노쇼 AND 리뷰 없음)로 집계하는 규칙. ADR-0005 수락 규칙(받는 쪽 유형)에 따른 분포를 반영.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다(컴포넌트 내부 상태가 아니라 "노쇼 1건·완료 2건 중 1건만 리뷰가 있으면 후기 입력 대기 2건으로 집계된다" 같은 관찰 가능한 결과).
- **테스트 대상 모듈:**
  - `meeting-status-rollup` — 같은 미팅 집합이라도 **받는 쪽이 초청 바이어면 수락대기 0건**(즉시 `accepted`), **일반 바이어/Exhibitor면 수락대기로 집계**되는지(ADR-0005). 후기 입력 대기 = 완료/노쇼 AND 리뷰 미작성.
  - `home-dashboard-data` — 역할(참가사/바이어)·유형(초청/일반)별로 세 블록이 올바른 데이터로 조립되는지. 내 기업 데이터만 포함(권한 경계).
- **Prior art:** 앱 코드가 아직 0인 그린필드 → 기존 테스트 선례 없음. F-BM-001의 모듈(`participant-promotion` 등)이 첫 테스트 패턴의 기준선이며, 본 PRD의 읽기 측 집계 모듈이 그 위에 얹힌다. 외부 의존 없는 읽기 전용 집계라 단위 테스트 출발점으로 적합.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 요약 카드·알림 UI 시연만(실데이터 미연동). 실제 집계·연동은 이 슬라이스 구현 범위.
- **알림 실시간 갱신/푸시** — v1은 진입 시점 스냅샷. 실시간 갱신·푸시 연동은 범위 밖(backlog).
- **내 프로필 요약 블록** — HM-001에서 제거(2026-06-22, 이슈 #16, D5 참조). 프로필 조회·완성도·수정은 BM-004(`/profile`)·BM-005(`/exhibitor/profile`) 소관.
- **비즈매칭 기간 vs 행사 중 뷰 차이** — 신청기간(미팅 미배정)과 행사 중(미팅 활성)의 화면 분기는 필요 시 후속. v1은 단일 뷰.
- **운영사 대시보드** — OP-001 소관(별도 PRD).
- **미팅 상태 전이·수락/거절·취소 처리 자체** — MY-001 / ADR-0005 소관. HM-001은 읽기·요약·진입만.

## Further Notes

- **구 EX-000 흡수 기록:** 구 EX-000(참가기관 홈, `/exhibitor`)을 참가사/바이어 공용 HM-001(`/`)로 일반화·부활(2026-06-14). 함께 구 EX-003(`/exhibitor/meetings`)은 MY-001(`/meetings`)로 흡수(CONTEXT.md Role-based Route 예외 참조). EX-000의 "참가측 액션 허브" 의도는 보존하되 라우트·페르소나만 공용화.
- 상태별 건수·알림은 Schedule Table 단일 원천을 집계하므로, MY-001 타임라인과 항상 같은 데이터를 다른 각도로 보여준다(중복 저장 없음).
