# F-OP-002: 참가기업/바이어 목록 관리

> 운영자가 **주관사 명단 스냅샷을 업로드**해 등록자를 동기화하고, 참가기업/바이어를 탭으로 조회·정정하며, 신청기간 마감 후 **초기 일괄배정(Draft 검토 → 확정 시 전원 즉시)을 1회 선행 실행**하는 운영 데이터 페이지. 명단 적재와 목록 관리의 단일 거점.

## Problem Statement

운영자 입장에서:

- 참가사·바이어 명단은 주관사(KADEX with DX Korea 2026)가 갖고 있고, NABI는 그걸 받아와야 한다. 그런데 주관사가 변경분만 골라주는 건 비현실적이라 매번 **전체 스냅샷**을 받게 되는데, 같은 파일을 또 올리면 명단이 중복될까 봐 겁난다. 신청기간(8/26~9/11)엔 명단이 계속 늘어 **여러 번 재업로드**해야 한다.
- 명단에 올라온 기업과 실제로 비즈매칭 프로필을 작성해 매칭 대상이 된 기업이 **한 화면에서 구분이 안 되면**, 누가 아직 참가자가 아닌지(독려 대상인지) 알 수 없다.
- 명단에 오타·중복·잘못된 분류가 섞여 들어와도 한 곳에서 빠르게 정정할 수단이 없다.
- 신청기간이 끝나면 빈 일정을 채워 매칭을 시작해야 하는데, AI가 만든 배정을 **검토 없이 그대로 확정**하면 억지 매칭·노쇼 위험을 운영자가 거를 길이 없다. 첫 배정은 임팩트가 가장 크므로 한 번은 꼭 **사람이 본 뒤** 내보내고 싶다.
- 수동 재배정(특정 기업 빈자리 보충)까지 이 목록 화면에 다 몰아넣으면 "데이터를 본다"와 "배정을 한다"가 뒤섞여 화면이 복잡해진다.

## Solution

운영자 입장에서:

- 주관사가 준 **전체 신청자 스냅샷 파일을 이 페이지에서 업로드**하면, NABI가 **회원ID를 키로 멱등 upsert**한다 — 같은 파일을 몇 번 올려도 중복이 안 생기고 최신값으로 덮어쓴다. 업로드 후 **신규/갱신/무변경 건수**를 결과로 확인한다.
- 명단 한 줄이 들어올 때 등록자(Registrant)뿐 아니라 기업·멤버·역할까지 함께 생성(eager)되고, **원본 전체가 raw로 보존**되므로 주관사 컬럼 구조가 아직 확정 전이어도 데이터를 잃지 않는다.
- 목록은 **참가기업/바이어 탭**으로 나뉘고, 각 행에 **"등록자 / 검토대기 / 비즈매칭 참가자"** 구분이 표시된다 — 프로필 제출은 `submitted`(운영 승인 대기)이고, 운영 승인으로 `approved`가 된 기업만 매칭 참가자로 본다(ADR-0009).
- 신청기간 마감(9/11) 후, 운영자는 이 페이지에서 **초기 일괄배정을 1회 선행 실행**한다 — AI가 빈 슬롯을 채운 결과가 **Draft로 먼저 생성**되고, 운영자가 개별 미팅을 **수정/삭제**한 뒤 **일괄 확정**하면 그 순간 양측에 통지된다. (확정 시 수락 규칙은 받는 쪽 유형 따라 — 참가사 자동확정 / 초청 바이어 즉시 / 일반 바이어 수락대기.)
- **수동 재트리거(특정 기업 빈슬롯 보충)는 기업 상세(F-OP-003)의 매칭 스케줄**에, **전체 반복 재실행은 배정 허브(F-OP-005)**에 둔다 — 이 페이지의 일괄배정은 **최초 1회 선행분**에 집중한다.

## User Stories

1. As an Organizer, I want 주관사가 준 전체 신청자 스냅샷 파일을 이 페이지에서 업로드하기를, so that 라이브 API 없이도 명단을 NABI에 적재한다.
2. As an Organizer, I want 같은 파일을 다시 올려도 중복 레코드가 안 생기기를, so that 신청기간 중 매일 받는 전체 스냅샷을 안심하고 반복 업로드한다.
3. As an Organizer, I want 업로드 후 신규/갱신/무변경 건수를 결과로 보기를, so that 이번 업로드가 무엇을 바꿨는지 멱등 결과를 확인한다.
4. As an Organizer, I want 명단의 모든 신청자(비즈매칭 신청 여부 무관)가 등록자로 적재되기를, so that 지각 신청 기업도 이미 DB에 있어 로그인 후 바로 합류한다.
5. As an Organizer, I want 명단 원본이 통째로 보존되기를, so that 주관사 컬럼 구조가 확정되기 전에 올린 데이터도 나중에 매핑할 수 있다.
6. As an Organizer, I want 참가기업/바이어를 탭으로 나눠 보기를, so that 두 모집단을 섞지 않고 각각 관리한다.
7. As an Organizer, I want 각 행에서 등록자·검토대기·비즈매칭 참가자(승인 완료)인지 구분해 보기를, so that 아직 프로필을 안 쓴 기업이나 승인 대기 기업을 독려·처리 대상으로 식별한다.
8. As an Organizer, I want 기업명·업종·프로필 완성 여부·매칭 보유 여부로 검색/필터하기를, so that 큰 명단에서 원하는 기업을 빠르게 찾는다.
9. As an Organizer, I want 기업명·매칭 건수·프로필 완성률로 정렬하기를, so that 우선 관리할 기업을 위로 올린다.
10. As an Organizer, I want 목록에서 프로필 오류(오타·잘못된 분류 등)를 빠르게 정정하기를, so that 적재 과정에서 섞인 데이터 오류를 바로잡는다.
11. As an Organizer (master), I want 참가자를 삭제하기를, so that 중복·철회·테스트용 레코드를 명단에서 정리한다. 미팅 이력이 있어도 취소·거절된 미팅뿐이면 지울 수 있다(D27). ("비활성화"는 서버에 저장되지 않던 기능이라 2026-10-08 제거 — D27.)
12. As an Organizer, I want 목록을 CSV/Excel로 내보내기를, so that 외부 보고·검토에 명단을 활용한다.
13. As an Organizer, I want 신청기간 마감 후 초기 일괄배정을 한 번 실행하기를, so that 수집된 프로필 위에서 빈 일정을 채워 매칭을 출발시킨다.
14. As an Organizer, I want 초기 일괄배정 결과가 곧바로 확정되지 않고 Draft로 먼저 생성되기를, so that 억지 매칭·노쇼 위험을 확정 전에 거른다.
15. As an Organizer, I want Draft 상태에서 개별 미팅을 수정하거나 삭제하기를, so that 부적절한 배정을 손본 뒤 내보낸다.
16. As an Organizer, I want Draft를 일괄 확정하면 그 순간 양측에 한꺼번에 통지되기를, so that 검토를 마친 배정을 한 번에 발효한다.
17. As an Organizer, I want 초기 일괄배정의 최소 보장 슬롯 수(N)·운영 시작/종료 시각·점심 블록·슬롯 길이를 실행 전에 설정하기를, so that 모든 참가사가 최소한의 미팅을 보장받고 일정이 운영 현실에 맞는다.
18. As an Organizer, I want 단일 기업 빈슬롯 보충(재트리거)이 이 화면이 아니라 기업 상세에 있기를, so that 목록(데이터)과 배정(액션)의 관심사가 섞이지 않는다.
19. As an Organizer (sub, 무역관), I want 내 관할(내가 관리하는 바이어)에 맞춰 액션·컬럼이 노출되고 국내기업은 열람만 되기를, so that 승인·전체삭제·포화배정처럼 내 권한 밖 조작을 시도하지 않는다. (매트릭스 D20, ADR-0012/0013)
20. As an Organizer, I want 비즈매칭 참가자만 매칭/배정 대상으로 노출되기를, so that 명단에만 있는 미작성 기업이 배정에 섞이지 않는다.

## Implementation Decisions

**진입 경로**
- 좌측 네비게이션 "목록 관리" 메뉴.
- OP-001 대시보드 지표 클릭 시 상세 이동(선택적).
- 목록 행 클릭 → **OP-003 기업 디테일**(프로필 전체·미팅 일정·단일 기업 배정)로 이동.

**화면 구조 — 리스트는 A층(등록 정보)만, 신청서(B층)는 "신청서 조회"로 분리 (D16)**
- 탭: **참가사**(Exhibitor) / **바이어**(Buyer — Hosted/Pre-registered/On-site 전부 포함). (글로서리: "참가기업"은 Organization avoid-term이므로 역할 탭은 **참가사**로 표기한다.)
- **목록의 행 단위 = `organization_event_roles`(회사×행사 역할), `registrants` 아님 (codex P1).** A층 표시값은 registrant가 있으면 거기서 읽고, **무역관 직접등록 바이어**(ADR-0013, registrant·organizer_member_id 없음)는 역할 행 + 운영자 직접입력분(`created_by_organizer_id`)에서 채워 **리스트에서 누락되지 않는다**.
- **목록 컬럼은 A층 표시값 + 운영지표, 탭별로 갈린다 (D18 — KOTRA 소스 ② 등록 필수정보·별첨2 양식 기반).**
  - **공통**: 기업명(**국문·영문 병기**) · 담당자(참가자 성명) · 전화번호 · 이메일 · **비즈매칭 상태**(단일 컬럼) · 신청서 조회(모달).
  - **참가사 전용**: 부스정보(홀·관·부스번호, `booths` 3계층) · 전시품목 카테고리 · KOTRA 회원여부.
  - **바이어 전용**: 바이어 하위유형(초청/사전등록/현장) · 관심품목 카테고리 · 언어(통역) · 체류정보(항공·숙박·통역, 한 셀) · 등록주체(무역관명; 연락처는 hover/툴팁).
  - 전화·이메일까지 독립 컬럼 — 가로 스크롤 허용. **비즈매칭 신청서(B층) 선언 내용 전체**(주소·연매출·회사소개·참석자 등)는 리스트에 섞지 않고 모달에서만 본다.
- **전시품목 카테고리는 채택, 자유텍스트 "업종"은 폐기 (D18 — D16 정정).** 구 자유텍스트 `industry`는 A층에 없어 폐기하나, **KOTRA 별첨2 참가기업 리스트 양식은 "제품 카테고리(국/영)"를 A층 명단 컬럼으로 포함**한다 — 따라서 구조화된 **전시품목 카테고리**는 A층 값으로 컬럼·필터에 채택한다(자유텍스트 업종과 구분).
- **비즈매칭 상태 = 단일 컬럼, 운영자 라벨 (D18).** `application_status` 정본에 운영자 컨텍스트 라벨을 입힌다 — 미신청(`registered`) · 승인대기중(`submitted`) · 수정요청중(`changes_requested`) · 승인됨(`approved`) · **반려(`rejected`, 회색 표시·목록에 남김)**. 로직 분기는 단일정본(`lib/application-status`) 술어로, **라벨만 운영자 오버라이드**(참가자측은 등록자/검토 대기/비즈매칭 참가자 유지).
- **신청서(B층) 열람·심사는 모달 (D18).** 신청서를 제출한 기업(`submitted` 이상)의 행에만 "신청서 조회" 버튼 → **모달**로 B층 전체(국영문) 표시. 미작성 행엔 버튼이 없어 "명단만" vs "신청서 작성"이 한눈에 갈린다. **이 모달이 곧 승인 심사 화면**(D19).
- 검색/필터: 기업명 · 역할(탭) · 비즈매칭 상태 · 전시품목 카테고리 · 매칭 보유 여부. 정렬: 기업명 · 매칭 건수 · 비즈매칭 상태.
- 이 화면의 데이터 액션: 신청서의 모든 항목 수정(신청서가 있는 행 — D26), 미신청 행의 대리작성, 단건 등록, 삭제(master 전용 — D27), CSV/Excel 내보내기. (개인화 링크 재발송은 ADR-0007 인증·정책 실무 검토 후.)

**운영자 핵심기능·권한·승인 — KOTRA 소스 ②③④ 기반 (D18~D21, 2026-06-30 grill)**
- **D18 — 핵심기능 정의 (소스 ③ 주최사/KOTRA 관리자).** 등록 관리(조회·**입력**·변경·삭제) + 모든 정보 조회 + **승인 기능** + 상담주선 관리가 소스 요구다. 이 중 **상담주선 관리는 비즈매칭 배정(F-OP-005) 소관**으로 분리하고, OP-002는 **등록관리 + 승인심사 + 정보조회(모달) + 체류정보**에 집중한다. ②④ "관리자가 설정한 기간에만 입력/신청/수락" 게이트(신청기간)는 운영사 설정(별도)·route-guard 소관.
- **D19 — 승인 심사는 신청서 조회 모달에서 (master).** 제출 내용(국영문 전체)을 확인한 뒤 **승인 / 반려 / 수정요청**. 승인 대상 = **국내기업 신청서 + 무역관(sub)이 등록한 바이어 둘 다**(ADR-0013). 전이는 `submitted→{approved|changes_requested|rejected}`(ADR-0009). 미심사 큐는 목록에서 "승인대기중" 필터로 모은다.
- **D20 — 권한 매트릭스 (master/sub, ADR-0012/0013).**

  | 기능 | master(주최/KOTRA) | sub(무역관) |
  |---|---|---|
  | 조회 | 전체(국내기업·바이어) | **본인등록 바이어만** (대리신청 탐색은 배정탭 별도) |
  | 등록 | 국내기업·바이어 다량+단건 | **바이어 다량+단건** |
  | 수정·삭제 | 전체 | 본인등록만 |
  | 비즈매칭 신청서 등록 | O(대리 입력) | O(대리) |
  | 승인/반려/수정요청 | **O** | ✗ (제출만, master 승인 대상) |
  | 체류정보 입력 | 가능(선택값, 거의 미입력) | **본인 바이어 등록 시 입력** |

  권한검사는 FastAPI 단일 지점에서 capability(master/sub) + scope(소유 바이어)로 검사(ADR-0008/0012). 화면은 권한에 따라 액션·컬럼을 노출/숨김.
- **D21 — 체류정보는 이 화면 안에서.** 바이어 행에 체류정보(항공·숙박·통역) 컬럼. 입력은 **sub가 바이어를 등록할 때**(선택값) — 참석자(사람) 단위(ADR-0013, 글로서리 Stay Info). master도 입력 가능하나 실무상 거의 안 한다.
- **스핀오프 (별도 PRD/이슈):** ① sub 무역관 실무자 정보 입력(로그인 약관동의 후 온보딩 화면) + sub 프로필 조회 페이지, ② 배정탭의 대리신청 대상 탐색·국내기업 상담 수락·통합 상담 조회(F-OP-005/미팅).
- **D22 — 단건등록·수정 폼은 A층 등록정보 전체(2026-07-01). ⚠ 2026-10-08 D26으로 정정** — 이 폼의 칸 다수(사업분야·HS코드·KST·부스·바이어유형·체류·담당자 전화, 수정 모드의 기업명)는 서버에 저장되지 않았다. 지금은 모드마다 저장되는 칸만 받고, 신청서가 있는 행의 "수정"은 이 폼이 아니라 신청서 편집 패널을 연다(D26). 아래는 당시 결정의 기록이다. 단건 등록(생성)·수정(편집)은 **같은 폼** 공용 — KOTRA ②④ 등록 필수정보 + 별첨2(기업명 국/영·사업자등록번호·담당자·전화·대표전화·이메일·웹사이트·품목 카테고리·HS코드·KST 상담가능시간·주소 + 참가사 부스·KOTRA회원 / 바이어 유형·언어·체류정보)를 받는다. **B층 신청서 선언(연매출·관심분야·회사소개·예산·도입시기)은 폼에 없다** — 회사가 비즈매칭 신청서로 직접 작성(A/B 경계, D17). 따라서 단건등록 결과 status는 **`registered`(미신청)** — 운영자 등록은 명단(A) 적재일 뿐 신청(B)이 아니다. **수정 버튼은 행마다 노출**(⋯ 메뉴 숨김 아님).
- **D23 — 기본 정렬 = 비즈매칭 상태순(2026-07-01).** 가나다 기본은 미신청 stub이 1페이지를 덮어 처리 대상(승인대기중·신청서 조회)이 안 보이는 문제 → 기본 정렬을 승인 상태순(승인됨→대기중→수정요청중→미신청→반려)으로 바꿔 운영자가 처리할 것을 위에서부터 본다. 상태 컬럼 헤더는 "비즈매칭 상태".
- **D24 — 신청서 조회 모달 = 제출 B층 신청서(BM-001/002) 그대로 표시(2026-07-01, 전 필드 §3.1/§4.1). ⚠ 2026-10-08 D26으로 확장** — 조회 전용이던 모달 본문이 "전체 보기 + 구획별 수정" 패널이 됐고, 데이터는 목록과 함께 싣지 않고 열 때마다 서버에서 읽는다(아래 seam `getMemberProfiles` 서술은 목업 모드에만 해당). 모달은 A층 요약이 아니라 **회사가 제출한 비즈매칭 신청서 정본 전 필드**(bm-profile-fields §3.1 buyer_profiles·§4.1 exhibitor_profiles)를 섹션별로 렌더한다.
  - **참가사(BM-002)**: 기본정보(사업자번호·대표자 국/영·회사이메일·대표번호·팩스·주소·업태/종목·부스 홀·관·타입·개수) · 회사소개·규모(웹사이트·참가자구분·연매출·직원수·상담가능언어·KOTRA회원·소개 국/영) · 전시품목(13분야·제품 국/영·HS코드·설명·가격대) · 타겟·운영(선호 바이어 국가/구분·미팅 불가시간) · 담당자(복수).
  - **바이어(BM-001)**: 신청자(성명 국/영·직위 국/영·이메일·전화·상담언어·통역필요) · 기관(국가·참가자구분·**연매출·직원수**·사업자번호·웹사이트) · 관심분야(13)·소개 국/영 · 구매·참가(예산·도입시기·참가경로·KST시간·KOTRA회원) · 참석자·체류.
  - 데이터는 seam `getMemberProfiles`(실연동 시 FastAPI 제출 프로필) 경유. 미제출(미신청·반려)은 "신청서 없음". A층 등록정보는 리스트 컬럼·수정 폼이 담당(A/B 분리, D17).
- **D26 — 운영자는 신청서의 모든 항목을 두 콘솔에서 수정한다(2026-10-08, 고객 요청 — D22·D24 정정).**
  - **편집기는 한 벌.** `/admin/organizations`의 "신청서 편집" 시트와 이 화면(`/organizer/members`)의 "신청서 조회·심사" 다이얼로그가 **같은 패널**(`frontend/components/operator/application-panel.tsx`)을 본문으로 쓴다. 패널은 참가자 마이페이지의 "전체 보기 + 구획별 수정"(참가사 `ProfileView`+`ExhibitorSectionEditDialog`, 바이어 `StepReview`+`BuyerSectionEditDialog`)을 운영자 대상 기업에 대해 재조립한 것이라, **참가자 신청서에 있는 항목은 운영자 편집에서 빠질 수 없다**(항목이 늘면 같이 는다).
  - **운영자 전용 구획**(참가자 폼에 없거나 참가자는 못 고치는 것): 참가사 = 기업명 국/영 · 부스 5칸(Hall·관·부스위치·타입·개수, **master 전용**) · 담당자 추가 정보(성·부서·영문 직책·전화·메신저·상담 언어 — 참가자 폼은 이름·직책·이메일·휴대폰만 다룬다) · 미팅 불가 시간(**master 전용**, 전용 엔드포인트). 바이어 = 사업자등록번호 · 웹사이트 · 주소. 지금 양식에 없는 과거 항목(참가사 참가자구분·제품의 구 카테고리/HS 설명, 바이어 참가 경로·KST 상담시간·참석자·추천 바이어 등)은 값이 있을 때만 읽기 전용으로 보인다.
  - **데이터 경로 = 참가자 매핑 그대로.** 읽기는 `GET /api/admin/events/{e}/organizations/{o}`의 프로필(참가자 API와 같은 응답 모델)을 참가자 클라이언트의 변환으로, 쓰기는 같은 클라이언트의 본문 변환으로 만든 구획 전체를 `PATCH .../profile?role=`로 보낸다(운영자용 매핑을 따로 두지 않는다 — `frontend/lib/operator/application-client.ts`). 담당자·제품·분야는 백엔드가 전체 교체이므로 **항상 전체**를 보낸다. 미팅 불가 시간은 `PATCH .../unavailable-slots`(전체 치환).
  - **서버가 정본.** 패널은 **열 때마다 서버에서 새로 읽는다**(목록과 함께 실려 온 값을 편집 초깃값으로 쓰지 않는다). 저장은 서버 응답으로만 화면을 다시 그리고 목록을 다시 읽는다 — 낙관적 갱신 없음. 실패하면 토스트로 알리고 다이얼로그와 입력을 유지한다(403은 "수정할 권한이 없습니다").
  - **동시 수정 — 저장 직전에 다시 읽어 견준다(클라이언트 쪽 검사).** 목록 칸(담당자·제품·분야·구분·선호 국가/구분·상담 가능 언어·미팅 불가 시간)은 백엔드가 전체 교체하고 스칼라 칸도 보낸 값으로 덮는다. 화면을 열어 둔 사이 다른 운영자·참가자가 바꾼 것을 모른 채 "열 때의 값"에서 출발한 입력을 보내면 그 사이의 추가분이 지워진다. 그래서 저장 직전에 서버를 다시 읽어 **그 저장이 쓰는 칸**이 다이얼로그를 열 때의 값과 달라졌으면 보내지 않는다(다른 구획이 바뀐 것은 막지 않는다 — 구획 저장은 그 구획의 칸 전부를, 운영자 전용 구획은 바뀐 칸만 보내므로 **실제로 보내는 칸만** 견준다. 같은 다이얼로그의 옆 칸을 다른 사람이 고친 것은 충돌이 아니다). "달라졌다"는 값의 뜻으로 본다 — 서버에서 **비워진** 것도 달라진 것이다(본문 조립의 "빈 칸은 안 건드림"과 별개 규칙. 그렇게 보지 않으면 참가자가 지운 값을 운영자의 저장이 되살린다). 그때는 패널을 방금 읽은 최신으로 바꾸고, 다이얼로그와 입력은 남긴 채 "다른 곳에서 먼저 수정됐어요 — 창을 닫고 다시 열어 확인한 뒤 수정"이라고 일반 실패와 다른 문구로 알린다. 기준이 "열 때의 값"이라 같은 창에서 다시 눌러도 풀리지 않는다. 재조회가 실패하면 보내지 않는다. 미팅 불가 시간 격자(패널·대리작성·행사 설정 화면)는 누른 칸을 저장하지 않고 격자를 최신으로 바꾼 뒤 알린다. ⚠ **서버 검증이 아니다** — 백엔드에 리비전·`If-Match`가 없어 재조회와 저장 사이(요청 한 번, 밀리초)에 끼어든 수정은 여전히 덮인다. 위험 구간을 "화면을 열어 둔 시간"에서 "요청 한 번 사이"로 줄일 뿐이고, 완전히 막으려면 백엔드의 리비전 검사가 필요하다(후속).
  - **상태·검증.** 직접 수정은 `application_status`를 바꾸지 않는다(승인된 신청서도 승인 그대로 — 백엔드 `patch_profile`에 상태 조건이 없다). 필수 항목 누락으로 저장을 막지 않고(운영자는 일부만 아는 채로 채워 간다) 비어 있는 구획을 안내만 한다. 칸을 비워 저장하면 서버 값도 지운다(참가자 화면은 빈 칸을 "안 건드림"으로 다룬다 — 운영자 모드만 다르다). 예외 둘: ① 있던 기업명(국문·영문)을 **둘 다** 지우는 저장은 보내지 않는다(이름 없는 기업이 된다 — 하나만 지우는 것은 된다). ② 바이어 폼의 선택 칸(연매출·정직원 수·언어·예산·도입 시기)은 참가자 화면과 같은 컨트롤이라 한번 고르면 "선택 안 함"으로 되돌릴 수 없다(다른 값으로 바꾸는 것만 된다).
  - **권한(백엔드 규칙 그대로).** master = 전부. sub = 관할(이 화면에 보이는 자기 바이어, 관리자 콘솔에서는 참가사 전부 + 자기 바이어) 안에서 수정, **부스·미팅 불가 시간은 조회만**(sub의 저장 본문에는 부스 키를 넣지 않는다 — 섞이면 백엔드가 요청 전체를 403으로 거부한다. 미팅 불가 시간 격자는 패널과 관리자 콘솔 대리작성 다이얼로그 모두 sub에게 읽기 전용으로 그린다). 심사(승인·반려·수정요청)는 종전대로 master 전용이고 자리와 동작이 같다.
  - **미신청(`registered`) 행은 대리작성이 먼저다**(상태 전이: master 승인 / sub 승인 대기 — Further Notes 2026-09-16). 행의 "수정"은 미신청이면 간이 대리작성 폼, 그 밖의 상태(제출·보완요청·승인·반려)면 위 패널을 연다. 대리작성이 성공하면 곧바로 같은 기업의 패널이 열려 나머지 항목을 채운다. 미신청은 참가자가 신청서를 **작성하는 중**일 수 있는 상태다 — 그래서 대리작성 다이얼로그 두 곳(관리자 콘솔 `ProxyWriteDialog`, 이 화면의 간이 대리작성 폼) 모두 값의 기준이 목록 화면이 아니라 서버의 현재 프로필이다: ① **열 때 서버에서 새로 읽은 값이 그대로 초깃값이다** — 서버에 없는 칸은 빈 칸으로 보인다. 명단 행의 값으로 채우지 않는다: 명단 값은 같은 컬럼에서 온 것이 아니라(명단의 이메일은 "회사 이메일 or 담당자 이메일 or 회원 이메일"의 파생값이다) 빈 회사 이메일 칸을 그 값으로 채우면 담당자 개인 이메일이 `company_email`로 저장된다. 읽지 못하면 폼을 그리지 않고 저장을 막는다. ② 저장은 **열 때 읽은 서버 값과 달라진 칸만**(= 운영자가 입력하거나 고친 칸만) 보낸다 — 아무것도 안 고치면 본문이 비고 상태만 전이한다(예전 간이 폼은 값이 있는 칸을 전부 보내, 운영자가 손대지 않아도 참가자의 초안을 명단 값으로 덮었다). ③ 보내기 직전에 한 번 더 읽어, 보내려는 칸이 그 사이 서버에서 달라졌으면(비워진 것 포함) 보내지 않는다(위 "동시 수정"과 같은 검사). ④ 간이 폼은 서버의 기업명(국문·영문)이 둘 다 비어 있고 폼에도 입력이 없으면 보내지 않는다 — 대리작성은 저장과 함께 승인으로 전이하므로 이름 없는 기업이 매칭 대상에 들어간다.
  - **폼에 보이는 칸 = 저장되는 칸.** 간이 대리작성 폼은 기업명 국/영·사업자등록번호·웹사이트·대표 전화·이메일·주소 + [참가사] 카테고리 / [바이어] 담당자 성명만 받는다(`frontend/lib/organizer/member-profile-patch.ts`와 1:1). 단건 등록 폼은 등록 요청에 실리는 칸(기업명 국/영·담당자 성명·전화·이메일·비밀번호)만 받는다. 저장되지 않던 칸(사업분야 자유입력·HS코드·KST·부스·바이어유형·언어·체류정보)은 뺐다 — 해당 항목은 패널에서 선택지로 입력한다.
  - **범위 밖(후속).** 누가·언제 고쳤는지의 수정 이력 기록은 없다(대리작성 여부만 `proxy_written_by_organizer_id`에 남는다).
- **D25 — 바이어 탭 컬럼셋 = 사람(바이어) 중심 + 에이전트 + 신청서(2026-07-01).** 바이어 탭은 참가사와 다른 컬럼셋을 쓴다(사람 중심): **바이어 이름(국/영) · 소속(국/영) · 직위(국/영) · 이메일 · 유형 · 관심품목 · 언어 · 에이전트 · 에이전트 담당자 · 에이전트 전화번호 · 에이전트 이메일 · 체류정보 · 등록 주체 · 비즈매칭 상태 · 비즈매칭 신청서(조회 버튼)**. "에이전트"는 **바이어를 주선한 KOTRA 무역관 정보**(요구사항 ④: 무역관명·실무 담당자·전화·이메일) — 별개 신규 개념이 아니라 organizer(무역관) 엔티티 매핑(ADR-0012/0013). 무역관명은 등록 주체(무역관 등록분)와 연동되고, **무역관 실무자(이름/전화/이메일) 구조화는 organizer 엔티티 보강 = 스핀오프 ①(#110) 소관**(기존 deferred 갭, 신규 미정 아님). 직접등록(주최사) 바이어는 에이전트 없음. v1은 FE 표시(mock). "비즈매칭 신청서"는 신청서 조회 모달 진입 컬럼(제출 이력 행만). 참가사 탭은 기업명(국/영)·담당자·전화·이메일·부스(홀·관·번호)·전시품목·KOTRA 회원여부·비즈매칭 상태·비즈매칭 신청서.

**명단 import 흐름 (ADR-0007 / ADR-0009)**
- **D1 — 소스는 주관사 전체 신청자 스냅샷 파일(CSV/엑셀), 라이브 API 아님.** 운영자가 이 페이지에서 직접 업로드한다. 변경분이 아니라 매번 그 시점 전체를 받아 NABI가 흡수한다.
- **D2 — 멱등 upsert, 키는 회원ID(또는 신청ID).** 멱등 주키 `(event_id, organizer_member_id)`. 사업자등록번호는 키로 쓰지 않는다(해외업체·개인 바이어 결측) — 부가 속성으로만 저장, 이메일은 보조 대조용. 같은 파일 반복 업로드 시 중복 없이 최신값 덮어쓰기.
- **D3 — import 시점 eager 생성.** 명단 한 레코드를 흡수할 때 `registrants` + `organizations` + `members` + `organization_event_roles`를 함께 멱등 upsert한다. 로그인은 read-only(이미 있는 행만 읽음) — 동시 첫로그인 org 중복 레이스 방지.
- **D4 — 원본 raw 보존.** 명단 원본 전체를 `raw`로 통째 저장한다. 주관사 컬럼 구조 미확정(선행 블로커)이라, 어떤 스키마가 와도 추후 매핑 가능하게 손실 없이 적재한다.
- **D5 — role 출처유추.** 참가사/바이어 역할은 명시 컬럼이 없을 수 있어 출처 명단으로 유추(참가기업 목록=exhibitor, 참관객 목록=buyer). 모호하면 잠정으로 두고 프로필 작성 경로로 확정. 한 기업이 둘 다일 수 있다(ADR-0001).
- **D6 — 등록자 / 검토대기 / 비즈매칭 참가자 구분 표시.** `organization_event_roles.application_status` ∈ {`registered`, `submitted`, `changes_requested`, `approved`, `rejected`}로 구분. `registered`=명단만(매칭 대상 아님), `submitted`=프로필 제출·운영 승인 대기(아직 매칭 대상 아님), `approved`=주최사/KOTRA 승인 완료(매칭 진입·비즈매칭 참가자). eager로 생긴 미로그인 "유령 org"는 `registered`라 매칭/배정에 노출되지 않는다. **매칭/배정 노출 대상은 `approved`만**(ADR-0009).
- **D7 — 운영 방식.** 신청기간엔 주기적(예: 매일 1회), 이후엔 수시 재업로드. v1은 자동화·라이브 연동 없이 운영자 수동 업로드로 충분. 향후 주관사가 API를 제공하면 "운영자 파일 업로드" 부분만 "API pull"로 교체(뒷단 upsert·키·매칭 불변).
- **D17 — A층(등록)·B층(신청서) 2레이어, 겹침은 "박제 + 선언".** 엑셀 명단은 **전부 A층**으로 적재한다(`registrants.raw`에 통째 박제 + 매핑되는 식별·연락은 정규 컬럼). 명단에 이미 들어있는 신청서성 항목(주소·업태/종목·전시품목·부스 등)은 A층에 **원본 그대로 박제**로 남고, 비즈매칭 신청서를 열면 그 A값으로 **prefill**된 뒤 사용자가 확인·수정한 값이 **B층 프로필(정본)**에 저장된다. 같은 개념이 두 곳에 있으나 **의미가 다르다 — A=주관사가 준 사실, B=사용자 선언(매칭·표시 정본)**. 매칭·신청서 화면은 B 정본을 쓰고(없으면 미작성으로 본다), **OP-002 리스트는 A만** 쓴다(D16).
  - **불변과 정정의 경계 (codex P1 반영):** 영구 박제는 **`registrants.raw`(주관사 원본)에만** — 이 jsonb는 절대 손대지 않는다. 반면 `registrants` 정규 컬럼(`name`·`contact_email/phone` 등)과 `organizations`는 **운영자 정정·명단 재업로드(D2)로 갱신 가능**하다(틀린 명단 담당자명 등은 여기서 고친다). 즉 "주관사가 준 사실"의 *원본*은 raw에 불변 보존되고, *표시·운영용 값*은 mutable이다 — D16(빠른 정정)·D2(재업로드 덮어쓰기)와 충돌하지 않는다.
  - **org 갱신 범위:** 신청서 제출이 `organizations`를 건드리는 것은 **법인정체성**(`name_ko/en`·`business_reg_no`)에 한정하고, 행사별 선언값(위치·연락·연매출·소개)은 역할 프로필에 스냅샷한다(`bm-profile-fields.md` §5, codex P0). 단 공유 `organizations` 행 갱신은 **행사 간 공유 영향**이 있으므로 주의(NABI 일회성 단일행사라 실무 영향은 작다). `website`는 현재 폼 미수집(NULL).

**초기 일괄배정 (ADR-0006 / ADR-0005)**
- **D8 — 1회 선행 실행.** 신청기간 마감(9/11) 후 수집된 프로필 위에서 빈 슬롯을 채우는 **첫 배정**을 이 페이지에서 1회 돌린다. 임팩트가 가장 크므로 선행 위치에 둔다. 이후 반복 재실행은 F-OP-005, 단일 기업 보충은 F-OP-003.
- **D9 — Draft → 검토 → 전원 즉시 확정.** AI가 채운 결과를 **Draft로 생성**(`saturation_batch_runs.status='draft'`) → 운영자가 개별 미팅 수정/삭제 → **일괄 확정**(`confirmed`)하는 순간 양측에 발효 통지. 확정 시 수락 규칙은 받는 쪽 유형 따라(ADR-0005): **참가사 측 자동확정 / 초청 바이어 즉시 확정 / 일반 바이어 수락대기(`proposed`)**. 따라서 이 채널에서 수락대기는 일반 바이어 수신 건에만 발생. 운영자 검토 게이트가 억지 매칭·노쇼 위험을 거르는 마지막 관문이며, "전원 즉시"는 참가자의 수락 단계를 생략한다는 뜻이지 운영자 검토를 생략한다는 뜻이 아니다.
- **D10 — 배정 정책.** 참가사 우선 포화(Exhibitor 103 < Buyer 178). 2라운드: ① 보장 라운드(모든 참가사에 최소 보장 슬롯 N, 적합도 순 라운드로빈) → ② 최적화 라운드(남는 슬롯 전역 적합도 최대화). tie-break = 비즈매칭 신청 빠른 순. 추가 전용·비파괴(기존 `accepted`/`proposed` 미팅 이동·취소 안 함, 현재 빈 슬롯만 채움). 산출 미팅은 `saturation_run_id`로 실행 회차에 연결, provenance는 'AI 매칭'.

**스케줄/운영 변수 설정**
- **D11 — 운영 변수는 하드코딩하지 않고 운영자 설정.** 운영 시작/종료 시각, **점심 블록**, 슬롯 길이(기본 30분), **일일 최소 보장 슬롯 수 N(기본 10)**. N은 초기 일괄배정 실행 시 입력 파라미터로도 노출(실행마다 조정). 일일 슬롯 수·총 슬롯 수는 이 변수에서 파생.
- **D12 — "최대 미팅 수" 변수 삭제.** 구버전의 참가사당 최대 미팅 수 상한은 제거한다 — 정책은 "빈 슬롯을 최대한 포화"이며 상한 캡이 아니라 **최소 보장(N)** 으로 형평성을 잡는다(ADR-0006). 슬롯 총량은 운영 시각·슬롯 길이·점심 블록에서 파생되는 자연 상한이 대신한다.

**관심사 분리 / 아키텍처**
- **D27 — 참가기업 삭제: 미팅 이력이 있어도 닫힌 미팅뿐이면 지운다(2026-10-08, 고객 요청).** 예전 삭제는 상태와 무관하게 미팅이 1건이라도 있으면 막았다(409). 화면에는 미팅을 "취소"하는 기능만 있고 미팅 행을 지우는 기능이 없어, 한 번이라도 미팅이 잡혔던 기업은 안내("미팅을 먼저 정리해 주세요")대로 취소해도 영영 지울 수 없었다.
  - **규칙** — 이 행사에서 이 기업이 걸린 미팅 기준(참가사 축이든 바이어 축이든). master 전용이고(sub는 삭제 불가 — D20 매트릭스의 "수정·삭제: sub 본인등록만" 중 삭제는 구현된 적이 없다. 삭제 API는 처음부터 master 전용이다), 예정·완료 미팅까지 지우는 강제 삭제는 두지 않는다.

    | 미팅 없음 | 삭제 |
    | `cancelled`·`rejected`만 있음 | **삭제 — 그 미팅 행도 같은 트랜잭션에서 함께 지운다** |
    | `proposed` 또는 `accepted`가 하나라도 있음 | 막는다 — 먼저 취소. 취소하면 상대 기업에 알림이 가므로 이 단계를 건너뛰게 하지 않는다 |
    | `completed`가 하나라도 있음 | 막는다 — 상대 기업의 회의록·미팅 이력까지 사라지기 때문 |

  - **함께 지워지는 것.** 이 행사의 참가(role)와 그 아래 신청서·제품·담당자, 닫힌(취소·거절) 미팅과 그 미팅에 딸린 참석자·회의록·전사 작업·알림(양쪽 기업 인박스에 있는 그 미팅의 알림 포함), 이 행사의 일괄 배정 기록 중 이 기업을 가리키는 항목(초안·확정·건너뜀 모두). **상대 기업, 상대 기업의 다른 미팅, 무관한 미팅·기업은 건드리지 않는다.** 일괄 배정의 실행 이력(run 행)은 남긴다 — 항목은 조직을 필수 FK(삭제 규칙 없음)로 가리켜 기업을 지우려면 남길 수 없고, 초안 상태의 항목은 한쪽 기업이 빠지면 성립하지 않는 제안이다(남기면 확정할 때 참가가 없는 기업으로 미팅을 만들려 든다). 확정·건너뜀 항목은 이력이지만 화면이 읽지 않는다 — 항목을 돌려주는 조회 API(`GET .../saturation-runs/{run_id}`)는 있으나 프런트는 일괄 배정을 만들고 확정할 때만 부르고, 운영 대시보드의 실행 이력은 run 행만 본다.
  - **기업 정보(조직)와 로그인 계정은 이 행사 참가 밖에 이 기업의 흔적이 하나도 없을 때만 지운다(2026-10-09 교차 리뷰).** 흔적은 조직 행을 지우면 FK 삭제 규칙대로 함께 지워지거나(CASCADE) 삭제를 막는(규칙 없음) 행 중 이 행사 참가 몫이 아닌 것이다 — 다른 행사의 참가·알림·관심 표시·러브콜·AI 추천·대화 채널·통역 배정·일괄 배정 기록, 이 행사에서 이 기업이 당사자가 아닌 미팅(다른 행사의 미팅, 같은 행사의 무관한 미팅)이 이 기업을 가리키는 칸(참가사·바이어·응답 대기)과 그런 미팅에 이 기업이 남긴 회의록·전사 작업, 그리고 회원이 CASCADE로 지워지므로 회원을 가리키는 다른 미팅의 참석자·다른 알림의 발송 기록(명단 재업로드가 회원을 다른 조직으로 옮길 수 있다). 흔적이 하나라도 있으면 조직·계정과 그 흔적(다른 행사의 데이터, 무관한 미팅의 기록)은 그대로 두고 이 행사 참가와 이 행사의 닫힌 미팅·일괄 배정 기록만 지운다. SET NULL 칸(명단 원본·파일·방문자·추천 바이어 입력의 연결, 미팅의 취소·거절 기업)은 행이 남고 연결만 비워지므로 흔적으로 보지 않는다. 칸마다의 분류와 이유는 `backend/app/admin/service.py`의 흔적 검사 목록·제외 목록에 있고, 모델의 모든 FK가 둘 중 한 곳에 있는지와 제외 이유의 삭제 규칙이 실 DB와 같은지는 테스트가 확인한다(테이블이 늘면 목록에 넣어야 통과한다).
  - **지우기 전에 보여 준다.** 삭제 확인 다이얼로그는 열 때마다 `GET /api/admin/events/{e}/organizations/{o}/deletion-impact`(master 전용)를 읽어, 막는 이유(예정 N건·완료 N건)와 함께 지워지는 것의 건수를 보여 준다 — 건수는 실제로 사라지는 행 수다(테스트가 삭제 전후 DB를 견줘 확인한다). 기업 정보까지 지워질 때는 이 기업이 받은 알림 전부(미팅과 무관한 것 포함)가 알림 건수에 들고, 연결 기록(관심 표시·러브콜·AI 추천·대화 채널·통역 배정, 어느 축이든)은 "이 기업과 연결된 관심 표시·러브콜·AI 추천 등 N건도 함께 삭제됩니다" 한 줄로, 일괄 배정 항목은 "일괄 배정 기록 N건"으로 알린다. 막히면 삭제 버튼이 비활성이고, 읽지 못하면 실패를 알리고 다시 확인하게 한다 — 모르는 채로 "함께 지워지는 것 없음"처럼 보이지 않는다. 미리보기와 실제 삭제는 **같은 판정 함수**를 쓴다.
  - **미리보기 뒤에 상황이 바뀌면** 삭제(`DELETE`)가 다시 판정해 409 `ORG_HAS_MEETINGS`로 답하고 상태별 건수(`scheduled_count`·`completed_count`)를 싣는다. 화면은 그 건수로 안내하고 행을 그대로 둔다(목록에서 빼는 것은 서버가 삭제를 확인한 뒤뿐이다). 판정과 삭제 사이의 경합은 잠금으로 막는다 — 미팅 예약 락 → 조직 행 → 참가(role) 행 → 회원 행 → 이 기업의 미팅 행 순. 그래도 DB가 막으면 전부 되돌리고 409 `ORG_DELETE_CONFLICT`로 답한다(500으로 새지 않는다).
  - **다른 작업과 엇갈리면 삭제가 먼저 물러난다(2026-10-09).** 삭제는 어느 잠금이든 Postgres 교착 판정 시간(`deadlock_timeout`)의 절반까지만 기다리고, 넘으면 아무것도 지우지 않고 409 `ORG_DELETE_CONFLICT`("잠시 후 다시 시도")로 답한다. 명단 업로드는 한 트랜잭션에서 여러 기업의 회원·참가·기업 행을 파일의 행 순서대로 잠가 삭제의 잠금 순서와 엇갈릴 수 있고, 둘이 교착하면 예전엔 업로드가 희생자가 될 수 있었다 — 업로드 500, 적재 전체 롤백(실제 업로드 코드로 재현). 이제 교착이 생겨도 판정 전에 삭제가 물러나 업로드는 끝까지 진행된다. 미팅 예약·수락처럼 금방 끝나는 충돌은 그 시간 안에 풀리므로 종전처럼 기다렸다가 판정한다.
  - **이 행사 명단에 없는 기업(2026-10-09 최종 리뷰).** 삭제와 미리보기 두 엔드포인트는 이 행사에 그 기업이 없으면 구조화된 404 `{"detail": {"code": "ORG_NOT_FOUND", "message": "기업을 찾을 수 없습니다"}}`로 답한다(잠근 뒤 보니 먼저 지워진 경우도 같다). 다른 엔드포인트가 함께 쓰는 공용 404의 문자열 detail("기업을 찾을 수 없습니다")은 그대로다. "기업 없음"은 **이 코드로만** 판정한다 — BFF는 detail.code가 `ORG_NOT_FOUND`인 404만 `ORG_NOT_FOUND`로 옮기고, 그 밖의 404(평문 detail — 라우팅·배포가 어긋난 "Not Found" 등)는 일반 실패 `http_404`로 넘긴다(운영자에게 배정된 행사가 없는 `no_event`와도 섞지 않는다). 화면은 `ORG_NOT_FOUND`를 받아도 **그 행을 임의로 숨기지 않는다.** 404만으로는 "다른 운영자가 먼저 지웠다"와 "다른 탭에서 행사를 바꿔 요청이 다른 행사로 갔다"(운영자 콘솔은 선택 행사를 쿠키로 고른다)를 가를 수 없기 때문이다 — 숨기면 원래 행사에 멀쩡히 있는 기업이 사라져 보인다. 대신 실 세션이면 명단을 서버에서 다시 읽는다: 정말 지워졌으면 새 명단에서 빠지고, 행사가 바뀌었으면 바뀐 행사의 명단이 보인다. 삭제가 `ORG_NOT_FOUND`면 창을 닫고 "'X'을(를) 이 행사 명단에서 찾을 수 없어요"를 단정하지 않는 설명("다른 운영자가 먼저 삭제했거나 다른 탭에서 행사를 바꿨을 수 있어요. 명단을 새로 불러왔어요.")과 함께 띄운다(삭제 완료·실패와 다른 안내). 미리보기가 `ORG_NOT_FOUND`면 창에 "이 행사 명단에서 찾을 수 없는 기업이에요"와 같은 설명을 띄우고 삭제 버튼을 막는다(다시 읽어도 소용없으므로 "다시 확인" 버튼은 없다). 일반 실패 404는 다른 실패와 같다 — 창을 두고 다시 시도하게 하고 행은 그대로다.
  - **"비활성화" 제거.** 행 메뉴의 "비활성화"는 화면에서 행만 숨기고 서버에 아무것도 보내지 않았다 — 새로고침하면 돌아오고 배정 대상에서도 빠지지 않았다. 실제로 동작시키려면 참가(role)에 상태 칸이 필요한데 그 테이블은 바꾸지 않기로 했다. 저장되지 않는 기능은 남기지 않는다.
  - **범위 밖.** 녹음 원본(S3)과 로그인 계정의 외부 인증(Cognito) 정리는 하지 않는다(기존 삭제와 같다). DB 스키마는 바꾸지 않았다.
- **D13 — 데이터(여기) vs 배정(허브/상세) 분리, 단 초기 1회는 선행으로 여기.** OP-002는 명단·프로필 데이터 + **최초 일괄배정 1회**. 전체 반복 재실행은 F-OP-005, 단일 기업 빈슬롯 보충(재트리거)은 F-OP-003의 매칭 스케줄. (구 OP-003 바이어 목록은 본 페이지 탭으로 통합, OP-003 ID는 기업 디테일로 재배정.)
- **D14 — 기업 상세는 OP-003 단일 라우트, 양쪽 진입.** 같은 기업 디테일을 목록(OP-002)과 배정 허브(OP-005)에서 동일 라우트로 연다.
- **D15 — 경계 B(ADR-0008).** 화면은 Next.js, 모든 적재·조회·배정 실행은 Next.js → FastAPI API → RDS(Next.js는 DB 직접 접속 안 함). 권한검사는 FastAPI 단일 지점, 업로드 원본은 S3 보관. 운영사는 주관사 roster 밖 NABI 내부 계정으로 인증(import·딥링크·DX Korea 인증 대상 아님).
- **접근 권한(ADR-0012/0013 — 확정):** Organizer(**master-for-this-event**) O(전체) · Organizer(**sub**) **O, 단 관할 한정** · Buyer/Exhibitor/Visitor X.
  - sub(무역관)의 관할은 **자기가 현재 관리하는 바이어 집합**(`managing_organizer_id`)이다 — 그 바이어의 조회·등록·수정·삭제, 대리 신청서 입력, 체류정보 입력까지. **국내기업(참가사)은 열람만**, **승인/반려/수정요청·전체삭제·전체 포화배정은 불가**(제출만 하고 master 승인 대상). 상세 매트릭스는 D20.
  - 권한검사는 FastAPI 단일 지점에서 **capability(master/sub) + scope(소유 바이어)** 로 한다 — 맨 "운영자임"으로는 어떤 admin도 열지 않는다(ADR-0008 경계 B, ADR-0012). 화면은 권한에 따라 액션·컬럼을 노출/숨김.

**식별된 deep modules** (격리 테스트 대상 후보)
- `roster-import` — 스냅샷 파일을 회원ID 키로 멱등 upsert + eager 생성(org/member/role) + raw 보존 + role 출처유추를 캡슐화. 입력=파일, 출력=신규/갱신/무변경 집계.
- `batch-allocation` — 초기 일괄배정 엔진(참가사 우선·2라운드·보장 N·tie-break·비파괴). 입력=`approved` 참가자 + 운영 변수, 출력=Draft 미팅 집합.
- `draft-review` — Draft 생성 → 개별 수정/삭제 → 일괄 확정 시 수락 규칙(ADR-0005)대로 양측 발효를 묶는 상태 전이(`draft`→`confirmed`/`discarded`).

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부에서 관찰 가능한 동작**만 검증한다(내부 함수 호출이 아니라 "같은 파일을 두 번 올리면 두 번째는 무변경 0건 신규로 집계된다" 같은 결과).
- **테스트 대상 모듈:**
  - `roster-import` — **멱등성**: 동일 스냅샷 2회 업로드 시 레코드 수 불변·집계가 (1회차=신규 N, 2회차=무변경 N)으로 나온다. 회원ID 결측 행 처리, 같은 회사 다중 멤버가 org 중복을 만들지 않음(eager 레이스 방지), raw 보존 round-trip.
  - `batch-allocation` — **집계/형평성 외부 동작**: 모든 참가사가 최소 N슬롯을 받는다(0건 참가사 없음), 재실행이 기존 확정 미팅을 건드리지 않는다(추가 전용·비파괴), tie 상황에서 신청 빠른 기업 우선.
  - `draft-review` — Draft 확정 시 받는 쪽 유형별 상태 전이(참가사=`accepted` / 초청 바이어=`accepted` / 일반 바이어=`proposed`), Draft 폐기 시 어떤 미팅도 발효되지 않음.
- **Prior art:** 앱 코드 0인 그린필드라 기존 테스트 선례 없음 → 본 PRD 모듈이 운영 측 첫 테스트 패턴 기준선. `roster-import`는 외부 의존(파일·DB) 있는 첫 통합 테스트 출발점으로 적합.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 업로드·목록·일괄배정 UI 시연만, 실제 적재/배정 실행은 이 슬라이스 구현 범위.
- **실제 명단 컬럼 구조 확정** — 미정(주관사 연동 합의, 선행 블로커). 그 전까지 raw 보존으로 손실 없이 진행, 컬럼별 매핑·prefill은 합의 후.
- **fit score(적합도) 정의** — 미정(키워드 카테고리 체계, CTO 협의). 보장/최적화 라운드와 룸 우선순위가 이 점수를 입력으로 쓰므로 배정 엔진 완성의 선행 조건.
- **DART/라이브 API 연동·URL 스크레이핑** — 없음(ADR-0008). v1은 운영자 수동 파일 업로드.
- **전체 반복 재실행·단일 기업 재트리거** — F-OP-005 / F-OP-003 소관. 본 페이지는 최초 1회 선행분만.
- **개인화 링크 재발송 정책** — 실무회의 검토 후 확정. (sub 권한 범위는 ADR-0012/0013으로 확정 — D20 매트릭스·접근 권한 참조.)

- 참가사 탭 필터 순서: 승인 상태 → 카테고리 → 사업분야 → 매칭 보유만. 카테고리는 `content_category`의 3종 단일 값이고 사업분야는 정규 8종 복수 값이다. 각 필터 안에서는 OR, 필터 사이에서는 AND로 결합한다. 바이어 탭에는 참가사 카테고리를 적용하지 않는다.
- 카테고리는 목록·상세·운영자 편집에서 같은 값을 사용한다. 업로드는 미입력 값만 채우고 기존 값과 충돌하거나 한 기업 내 입력이 상충하면 보존·경고한다. 자동 승인이나 사업분야 기반 추론은 하지 않는다.
- 엑셀은 현재 검색·탭·필터·정렬의 **전체 결과**를 내보낸다(화면 페이지 제한 없음). 카테고리와 사업분야/관심분야를 별도 컬럼으로 제공하고 결과 0건도 헤더를 유지한다. 서버는 행사 master 권한과 조회 범위를 검증하며 클라이언트 ID 목록은 정렬용으로만 사용한다.
- 매칭 보유는 해당 행사에서 proposed/accepted/completed/noshow 미팅이 1건 이상인 기업이다. canceled/rejected/expired는 제외한다.
