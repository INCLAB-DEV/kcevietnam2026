# F-MT-001: 미팅 신청

> 상대방에게 미팅을 신청하고, **받는 쪽 바이어 유형에 따라 즉시 확정(accepted)되거나 수락대기(proposed)로 들어가는** opt-out 수락 모델의 전체 상태 흐름. 신청은 장소+시간+사유를 3탭으로 완료하고, 확정 후 취소는 출처·유형 무관 양쪽 누구나 가능하다.

## Problem Statement

**신청자 입장에서:**

- 관심 가는 상대를 찾았지만 미팅을 잡으려면 장소·시간·이유를 일일이 정리해야 해서 번거롭고, 그 과정에서 신청을 포기하게 된다.
- 상대와 내 일정이 언제 겹치는지 알 수 없어, 잡아도 어긋나기 일쑤다.
- 일회성 전시회라 미팅마다 "요청→상대 수락"을 왕복하면 며칠을 기다리다 기회를 놓친다. "일단 잡혀 있는" 일정의 가치를 살리지 못한다.

**받는 쪽 입장에서:**

- 수백 건의 미팅을 일일이 수락하는 부담은 감당이 안 된다. 그러나 내 일정이 살아있는데 동의 없이 미팅이 잡히는 것도 곤란하다 — 어떤 건 자동으로 확정돼도 괜찮고, 어떤 건 내가 보고 결정하고 싶다.
- 확정된 미팅이 사정상 불가능해졌을 때 무를 방법이 없으면 노쇼가 된다.

## Solution

**신청자 입장에서:**

- 신청을 **3탭 모달**(시간→장소→확인+사유)로 받는다. 시간은 양쪽 빈 슬롯 교집합만 활성화돼 어긋나지 않고, 사유는 AI가 프로필 기반 초안을 만들어줘 그대로 보내거나 수정하면 된다.
- **opt-out 즉시 확정 모델**이라, 받는 쪽이 초청 바이어이거나 AI 전체 포화배정의 참가사 측이면 왕복 없이 그 자리에서 `accepted`로 확정된다 — 매칭 밀도가 올라간다.

**받는 쪽 입장에서:**

- **수락 여부는 출처(누가 만든 매칭인가)가 아니라 "내가 누구·언제 받느냐"로 정해진다.** 일정이 살아있는 시점에 일반 바이어가 받는 건은 `proposed`로 들어와 내가 수락/거절을 결정하고, 초청 바이어가 받는 건과 포화배정의 참가사 측은 즉시 확정된다.
- **취소는 출처·유형 무관 모든 미팅을 양쪽 누구나** 할 수 있어, 즉시 확정 모델의 안전판이 된다(취소 넛지로 남용은 억제).

## User Stories

1. As a 바이어, I want 미팅 신청을 시간→장소→확인의 3탭으로 끝내기를, so that 번거로움 없이 빠르게 신청한다.
2. As a 신청자, I want 시간 선택 시 양쪽 빈 슬롯 교집합만 활성화되기를, so that 상대와 어긋나지 않는 시간만 고른다.
3. As a 신청자, I want 30분 슬롯을 1~3개 연속으로 묶어 선택하기를, so that 미팅 성격에 맞춰 30분~1시간 30분으로 길이를 정한다.
4. As a 신청자, I want 시간을 먼저 고르면 그 시간에 가용한 장소(부스/매칭존 테이블/비즈니스 룸)만 보이기를, so that 못 쓰는 장소를 고르는 헛수고를 피한다.
5. As a 신청자, I want AI가 내 프로필 기반으로 신청 사유 초안을 만들어주기를, so that 빈 칸을 마주하지 않고 그대로 보내거나 다듬는다.
7. As a 신청자, I want 겹치는 빈 시간이 0개일 때 "관심기업으로 등록" 폴백을 제안받기를, so that 지금 못 잡아도 기회를 흘리지 않는다.
8. As an 초청 바이어(Hosted)에게 신청하는 사람, I want 내 신청이 받는 쪽 초청 바이어에게 즉시 `accepted`로 확정되기를, so that 수락 왕복 없이 일정이 바로 잡힌다.
9. As a 일반 바이어(사전등록·현장), I want 내가 받는 미팅이 `proposed`로 들어와 내 수락을 기다리기를, so that 내 일정이 살아있는 시점에 동의 없이 잡히지 않는다.
10. As an Exhibitor, I want 내가 받는 미팅이(전체 포화배정 외) `proposed`로 들어오기를, so that 받을 미팅을 내가 판단해 수락한다.
11. As an Exhibitor(전체 포화배정 대상), I want 운영자가 내 캘린더를 대신 채우는 포화배정 건은 자동 `accepted`되기를, so that 수백 건을 일일이 수락하지 않아도 된다.
12. As a 받는 쪽(proposed 건), I want MY-001에서 상대 프로필을 보고 수락 또는 거절하기를, so that 가치 있는 미팅만 확정한다.
13. As a 받는 쪽(proposed 건), I want 거절 시 사유 키워드와 자유 입력을 남기기를, so that 신청자가 이유를 알고 성과 데이터가 쌓인다.
14. As an 양쪽 누구든(accepted 건), I want 출처·유형과 무관하게 확정 미팅을 취소하기를, so that 불가능해진 일정을 무르고 노쇼를 막는다.
15. As a 취소하는 사람, I want 취소 시 "추천 우선순위 하락 가능" 넛지와 사유 입력을 거치기를, so that 신중히 취소하고 슬롯이 자동 해제된다.
16. As a 받는 쪽(초청 바이어·포화배정 참가사 측), I want 즉시 확정 건에는 거부 단계가 없기를, so that 자동 확정의 의도가 흐트러지지 않는다(취소로만 무름).
17. As a Forced 매칭 대상, I want 운영자 강제 배정이라도 받는 쪽 유형대로 수락 규칙이 적용되기를, so that 초청이면 즉시 확정, 일반 바이어/Exhibitor면 내 수락을 거친다.
18. As a 신청자/받는 쪽, I want 미팅 종료 후 "미팅이 진행되었나요?" 리뷰 폼을 받기를, so that noshow를 가려내고 후속 연결에 활용된다.
19. As a 신청자, I want 같은 상대 Organization에는 동시 활성 미팅이 1건만 잡히고 completed 후 추가 신청이 되기를, so that 슬롯 낭비 없이 후속 미팅을 이어간다.
20. As a 받는 쪽, I want 미팅 신청·확정·거절·취소·리뷰 시점마다 이메일 알림과 MY-001 딥링크를 받기를, so that 웹에서 처리하되 누락 없이 흐름을 따라간다.

## Implementation Decisions

**D1 — 수락 모델 = opt-out, 받는 쪽 유형으로 결정 (ADR-0005).** "제안→양측 수락(opt-in)"을 "즉시 확정→취소 가능(opt-out)"으로 뒤집는다. **수락 규칙은 provenance(Open/AI/Forced/On-site)와 독립**이며 오직 받는 쪽 바이어 유형으로 결정된다. 운영자가 confirmed/proposed를 수동으로 고르지 않는다. 유형-무관 전원 즉시확정 예외는 폐기됐다.

| 진입 상태 | 적용 케이스 |
|----------|------------|
| **`accepted` 즉시 확정** (거부 단계 없음) | ① **초청 바이어(Hosted)** 가 받는 모든 건 (전 채널) ② **AI 전체 포화배정에서 참가사 측**(운영자가 참가사 캘린더를 대신 채우므로 자동확정) |
| **`proposed` 수락대기** (받는 쪽 수락 필요) | ① **일반 바이어(사전등록·현장)** 가 받는 모든 건 (전 채널 — Open · AI 전체 포화배정 · 단일 재트리거 · Forced) ② **Exhibitor** 가 받는 건 (Open · 단일 재트리거 · Forced — **AI 전체 포화배정 제외**, 거기선 참가사 자동확정) |

- "즉시 확정"이 생략하는 것은 **참가자의 수락 단계**뿐이다. 운영자의 검토 게이트(전체 포화배정 Draft 검토)는 유지된다 → F-OP-005.
- 의무 미팅(Hosted 대상)은 받는 쪽이 초청 바이어라 자동으로 즉시 확정되므로 별도 강제 수단이 불필요.

**D2 — 상태 흐름은 받는 쪽 유형에 따라 두 갈래로 갈린다.** 캐노니컬 상태값은 schema.sql `meetings.status`(`proposed`/`accepted`/`rejected`/`cancelled`/`completed`, 5종)와 일치.[^noshow]

```
[일반 바이어 수신(전 채널) · Exhibitor 수신(전체 포화배정 제외)]
proposed → accepted → completed / cancelled
         → rejected
         → cancelled
[초청 바이어 수신(전 채널) · 전체 포화배정의 참가사 측]
accepted → completed / cancelled
```

| 상태 | 설명 |
|------|------|
| proposed | 신청됨, 받는 쪽 응답 대기. **일반 바이어 수신(전 채널)·Exhibitor 수신(전체 포화배정 제외) 건에만 존재** |
| accepted | 수락 확정. 일반 바이어/Exhibitor는 수락 후, 초청 바이어·포화배정 참가사 측은 즉시 진입 |
| rejected | 거절됨(사유 키워드+자유 입력). **`proposed`에서만 발생** (거절 ≠ 취소) |
| cancelled | 확정 후 취소. **출처·유형 무관 양쪽 누구나**. 사유 입력 필수, 슬롯 자동 해제 |
| completed | 미팅 진행 완료 |

[^noshow]: noshow는 `meetings.status` 값이 아니라 `post_meeting_reviews.counterpart_noshow`로 이전됨(F-NT-001 결정, ADR-0010 보정).

**D3 — 받는 쪽 유형별 진입점은 채널 무관하게 동일 규칙.** 신청 채널(Open 신청 모달 / AI 전체 포화배정 / 단일 기업 재트리거 / Forced)이 무엇이든 진입 상태는 D1 표로 결정된다. 진입점은 DV-001 AI 추천 카드와 DV-002 기업 상세의 "미팅 신청" 액션이며 둘 다 동일 모달을 연다. 미팅 신청은 인증 참가자 전용이다(미인증 사용자는 라우트 가드로 `/login`). AG-001(에이전트 대화) 진입은 이후 과제.

**D4 — 신청 모달 3탭 (Open Matching 사용자 주도 신청에 적용).** ①시간(날짜+30분 슬롯 1~3개 연속, 양쪽 빈 슬롯 교집합만 활성·0개 시 관심기업 폴백) → ②장소(시간 선택 후 가용 부스/매칭존 테이블/비즈니스 룸만, 부스는 하위 선택 없음·테이블/룸은 번호 선택 완료 필요) → ③확인+사유(AI 초안 사유 표시·수정 후 전송). 시간을 먼저 받는 이유는 가용 장소가 시간에 종속되기 때문.

**D4-a — 부스 옵션 문구의 번호 출처(2026-09-28, 발주자 요구).** 장소 탭의 부스 줄은 제목 `{참가사명} 부스` + 설명 `참가기업 부스 {번호} 미팅`이고, 번호는 ① 배정 부스(`exhibitor_profiles.booth_id → booths.code` + `halls.hall_name`, 예 "7홀 A-12") → ② **운영자가 지정한 부스번호**(`exhibitor_profiles.booth_location`, `/admin/organizations`에서 입력 — F-OP-002 2026-09-28) 순으로 쓴다. 둘 다 없으면 가짜 번호를 만들지 않고 "참가기업 부스에서 미팅"으로 바꾼다. ⚠ 이건 **화면 문구 전용**이다 — `meeting_venues` 저장 라벨(멱등키)은 배정값 규칙만 쓴다(신고/지정값이 라벨로 새면 같은 부스에 장소 행이 둘 생겨 중복예약 가드가 갈라진다).

**D5 — AI Matching 2액션 (ADR-0005/0006).** 같은 "AI가 빈 슬롯을 채운다"라도 채널에 따라 대상·수락 규칙이 다르다:

| 액션 | 대상 | 수락 규칙 |
|------|------|----------|
| ① 전체 포화배정 (반복 실행 가능) | 전체 참가사 | 참가사 측 자동확정 + 바이어 유형별(초청=즉시 / 일반=proposed). 운영자 Draft 검토 후 확정 → F-OP-005 |
| ② 단일 기업 빈슬롯 보충(재트리거) | 한 기업만 | 받는 쪽 유형별(초청=즉시 / 일반·Exhibitor=proposed). 추가 전용·비파괴 → F-OP-003 |

두 액션 모두 provenance는 'AI 매칭'으로 기록(성과측정). "AI는 제안만 한다"는 폐기.

**D6 — 거절은 `proposed`에서만, 취소는 always.** 거절(reject)은 일반 바이어 수신(전 채널)·Exhibitor 수신(포화배정 제외)의 `proposed` 건에만 — 즉시 확정 건엔 거부할 틈이 없다. 취소(cancel)는 이미 `accepted`된 건을 무르는 행위로 **출처·유형 무관 모든 미팅 양쪽 누구나**(즉시 확정 건 포함). 취소 시 "특별한 사유 없이 취소하면 AI 추천 우선순위가 낮아질 수 있습니다" 넛지 + 사유 입력(키워드+자유) → 슬롯 자동 해제. 당일 취소 포함 시간 제한 없음. 취소로 생긴 빈 슬롯은 AI가 자동 재충전하지 않고, 운영자가 포화배정 재실행/재트리거 또는 Open으로만 메운다(ADR-0006).

**D7 — Forced Matching도 받는 쪽 유형으로 수락 결정 (ADR-0005).** 구버전("accepted 직접 삽입, 거절 불가")은 폐기. 받는 쪽=초청 바이어 → 즉시 확정 / 받는 쪽=일반 바이어·Exhibitor → `proposed`. 운영자에게 **일반 바이어 강제 확정 권한은 없으며** provenance만 'Forced'로 기록. 배정 일원화 진입점은 F-OP-005.

**D8 — 미팅 신청은 인증 참가자 전용(전환 게이트 폐지).** 구버전의 "Visitor → On-site Buyer 자기전환 필수 게이트"(미팅 신청 시 BM-001로 유도)와 게스트 폼은 모두 폐기됐다(정책 변경 2026-07-02). 미인증 사용자는 nav/서비스 페이지에 진입할 수 없고 라우트 가드로 `/login`으로 보내진다 — 게스트 탐색·자기전환 경로 없음. 미팅 신청은 딥링크 로그인으로 인증된 바이어(초청/사전등록/현장)만 수행하며, 바이어 프로필 작성은 F-BM-001과 1:1.

**D9 — 복수 신청·재신청 규칙.** 같은 상대 Organization에 동시 활성 미팅은 1건만. completed 후 추가 신청 가능. 거절 후 재신청 횟수 제한 없음 — 빈 슬롯 교집합 기반이라 역제안(counter_proposed) 없이 새로 신청한다(역제안은 ADR-0005로 폐기).

**D10 — 수락/거절은 MY-001 웹에서, 이메일은 알림+딥링크만.** 신청(proposed 생성)·수락·즉시 확정 배정·거절·취소·리뷰 요청 각 시점에 이메일 발송. 신청 알림(proposed 생성)은 일반 바이어/Exhibitor 수신 건에만, 즉시 확정 배정 알림은 양쪽에 발송.

**D11 — 비즈니스 룸 우선순위·폴백 (ADR-0006).** 룸은 한정 자원(~50개). 자동 배정 시 ① 초청 바이어 미팅 → ② 적합도(fit score) 높은 미팅 → ③ 신청 빠른 순. 룸 미배정 시 매칭존 테이블 → 부스로 폴백. fit score 정의는 미해결(선행 블로커).

**D12 — 운영 슬롯 파라미터는 Organizer 변수 (ADR-0006).** 슬롯 길이·운영 시작/종료·점심 블록·일일 최소 보장 건수는 하드코딩 금지하고 Organizer가 설정. 일일/총 슬롯 수는 이 변수에서 파생.

**D13 — 아키텍처 경계 B (ADR-0008).** 모달은 Next.js, 슬롯 가용성 조회·미팅 생성/상태 전이·취소 처리는 모두 Next.js → FastAPI API → RDS(Next.js는 DB 직접 접속 안 함). 권한검사(누가 어떤 미팅을 수락/거절/취소할 수 있나)는 FastAPI 한 곳에 집중.

**식별된 deep modules** (격리 테스트 대상 후보)
- `meeting-state-machine` — 허용된 상태 전이(proposed→accepted/rejected/cancelled, accepted→completed/noshow/cancelled)와 금지 전이(예: accepted→rejected, 즉시확정 건의 reject)를 단일 인터페이스로 강제.
- `acceptance-policy` — 받는 쪽 유형(초청/일반/Exhibitor) × 채널(Open/포화배정/재트리거/Forced)을 입력받아 진입 상태(accepted vs proposed)를 결정. provenance와 독립.
- `cancel-handler` — 출처·유형 무관 취소 허용 판정 + 사유 검증 + 슬롯 해제를 원자적으로 수행(취소 후 AI 자동 재충전 없음).

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작**만 검증한다. 예: "초청 바이어가 받으면 채널과 무관하게 즉시 `accepted`로 진입한다", "일반 바이어가 받은 proposed 건을 거절하면 rejected가 되고 슬롯이 유지된다", "accepted 건을 어느 쪽이든 취소하면 cancelled가 되고 슬롯이 해제된다" 같은 관찰 가능한 결과.
- **테스트 대상 모듈:**
  - `acceptance-policy` — 받는 쪽 유형 × 채널 매트릭스 전수 검증. 핵심: provenance를 바꿔도 같은 받는 쪽 유형이면 진입 상태가 같다(독립성). 전체 포화배정에서 참가사=accepted·일반 바이어=proposed.
  - `meeting-state-machine` — 합법 전이는 통과, 불법 전이는 거부(즉시확정 건의 reject 불가, proposed에서 직접 completed 불가 등). 취소는 accepted 어느 출처에서나 가능.
  - `cancel-handler` — 취소 always 보장 + 슬롯 해제 + 자동 재충전 없음. 취소 사유 누락 시 거부.
- **Prior art:** 앱 코드가 아직 0인 그린필드 → 기존 테스트 선례 없음. 본 PRD의 세 모듈이 첫 상태머신 테스트 패턴의 기준선이 된다(F-BM-001의 participant-promotion 원자성 테스트와 같은 "외부 동작/원자성" 결.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 3탭 모달 UI 시연만, 실제 상태 전이·슬롯 가용성·알림은 이 슬라이스 구현 범위.
- **적합도(fit score) 정의** — 미정(CTO 협의, ADR-0006 선행 블로커). 룸 우선순위 ②에 입력으로 쓰이나 본 PRD에서 확정하지 않는다.
- **매칭 엔진 자체(배정·포화·재트리거 로직)** — F-OP-005 / F-OP-003 / ADR-0006 소관. 본 PRD는 그 결과가 어떤 진입 상태로 들어오는지(수락 규칙)와 이후 상태 흐름만 다룬다.
- **취소 이력의 알고리즘 반영** — 1차는 넛지 문구 + 이력 수집만. 추천 우선순위 가중은 이후 과제.
- **장소 수량·배정 방식·리뷰 폼 상세 문항** — 실무 확인 필요(매칭존 테이블/룸 수량, 선착순 vs 배정, 참가사 서류 연계).
- **AG-001 에이전트 대화에서의 미팅 신청 진입** — 이후 과제.

## Further Notes

- **Provenance와 수락 규칙은 별개의 축이다**(ADR-0005, CONTEXT). Open/AI/Forced/On-site는 "누가 만든 매칭인가"(성과측정용)일 뿐, "받는 쪽이 수락해야 하나"는 오직 받는 쪽 유형으로 정해진다 — 이 분리가 본 PRD 전체의 중심 불변식이다.
- 바이어 3유형의 "플랫폼 경험 동일" 원칙은 **매칭 수신 시 초청 vs 일반**에서만 깨진다(초청=즉시 확정 / 일반=본인 수락). 그 외 신청·탐색 경험은 전부 동일.
- 구버전 흔적(opt-in 제안→양측 수락, 역제안 counter_proposed, "AI는 제안만 한다", Forced=accepted 직접 삽입·거절 불가, 유형-무관 전원 즉시확정)은 모두 ADR-0005로 supersede되어 본 PRD에서 제거됐다.
