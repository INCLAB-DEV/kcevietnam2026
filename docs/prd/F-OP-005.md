# F-OP-005: 비즈니스 매칭 배정 (배정 허브)

> 운영사의 **전체/일괄 미팅 배정을 모은 단일 허브**이자 **Forced 배정의 일원화된 진입점**. 두 배정 방식을 제공한다:
> ① **AI 전체 포화배정** (전체 참가사 대상, 반복 실행 가능, 최소 N슬롯 운영자 설정) · ② **Forced** (운영사가 대상을 골라 지정).
> 핵심은 **운영사가 수락 상태(confirmed/proposed)를 더 이상 수동으로 고르지 않는다**는 것 — 받는 쪽 유형이 수락 규칙을 자동 결정한다(ADR-0005). OP-002 기업상세의 "개별 추천"이 여기로 딥링크해 들어온다. 단일 기업 빈슬롯 보충(재트리거)·한 기업만 배정할 땐 F-OP-003(기업 디테일)을 쓴다.

## Problem Statement

운영사 입장에서:

- 신청기간 마감(9/11) 후 빈 슬롯이 많고 노쇼·취소로 일정이 새는데, 특정 바이어와 특정 참가사를 **내가 직접 짝지어 미팅을 강제로 배정**할 수단이 흩어져 있거나 불명확하다. 어디서 시작해야 할지 진입점이 일관되지 않다.
- 예전 방식은 미팅을 강제 배정할 때 운영사가 **수락 상태(confirmed/proposed)를 손으로 골라야** 했다. 그런데 일반 바이어를 동의 없이 강제로 확정해 버리면 받는 쪽이 모르는 채 일정이 잡히는 부담이 생긴다. 운영사가 매번 "이건 확정, 저건 제안"을 판단하는 것도 실수의 여지가 크고 결과를 예측하기 어렵다.
- OP-002 기업 목록에서 한 기업을 보다가 "이 기업엔 이 상대를 붙이면 좋겠다"고 판단해도, 거기서 배정 화면으로 자연스럽게 이어지는 경로가 없으면 맥락이 끊긴다.
- 두 기업의 빈 시간을 일일이 대조해 겹치는 슬롯을 찾는 일이 번거롭고, 잘못 잡으면 충돌이 난다.

## Solution

운영사 입장에서:

- 전체/일괄 배정을 **한 허브(OP-005)에 모은다.** 전체 참가사를 한꺼번에 채우는 **AI 전체 포화배정**과, 대상을 골라 직접 짝짓는 **Forced**를 같은 화면에서 다룬다. Forced는 이 허브가 **유일한 일원화 진입점**이다(한 기업만 보충할 땐 OP-003).
- **수락 상태를 운영사가 고르지 않는다.** 미팅을 강제로 생성하면, 수락 규칙은 **받는 쪽 유형이 자동으로 결정**한다 — 초청 바이어가 받으면 즉시 확정(`accepted`), 일반 바이어·Exhibitor가 받으면 수락대기(`proposed`). 운영사는 **일반 바이어를 강제 확정할 권한이 없다.** 의무 미팅은 받는 쪽이 초청 바이어라 자동으로 즉시 확정되므로 별도 강제 수단이 필요 없다. 화면에는 받는 쪽 유형 뱃지와 예상 결과(즉시 확정/수락대기)를 **미리** 보여줘 운영사가 결과를 예측할 수 있다.
- OP-002 기업상세의 **"개별 추천"이 이 허브로 딥링크**해 들어온다 — 목록에서 본 기업이 Forced 플로우의 출발점으로 이어져 맥락이 끊기지 않는다.
- Forced에서는 두 기업의 **빈 슬롯 교집합**만 표시해 충돌 없이 가용 시간만 고르게 한다. 상대 선택 단계에서는 매칭율 높은 기업을 **AI가 추천**하되 직접 검색도 가능하다.

## User Stories

1. As an Organizer, I want 전체 포화배정과 Forced를 한 화면에서 다루기를, so that 전체/일괄 배정의 진입점이 한 곳으로 모여 어디서 시작할지 헷갈리지 않는다.
2. As an Organizer, I want 바이어와 참가사를 직접 골라 두 기업의 미팅을 강제로 생성하기를, so that 빈 슬롯이나 전략적 매칭을 내가 주도해 채운다.
3. As an Organizer, I want 미팅을 강제 배정할 때 수락 상태를 내가 고르지 않고 받는 쪽 유형으로 자동 결정되기를, so that 매번 confirmed/proposed를 판단하는 부담과 실수가 사라진다.
4. As an Organizer, I want 초청 바이어가 받는 강제 배정은 즉시 확정(`accepted`)되기를, so that 의무 미팅이 거부 단계 없이 바로 확정된다.
5. As an Organizer, I want 일반 바이어·Exhibitor가 받는 강제 배정은 수락대기(`proposed`)로 들어가기를, so that 받는 쪽 동의 없이 일정이 강제로 잡히지 않는다.
6. As an Organizer, I want 일반 바이어를 강제로 확정할 수단이 아예 없기를, so that 동의 없는 강제 확정으로 받는 쪽에 부담을 주는 일이 구조적으로 차단된다.
7. As an Organizer, I want 배정 전에 받는 쪽 유형 뱃지와 예상 결과(즉시 확정/수락대기)를 미리 보기를, so that 확정 버튼을 누르기 전에 결과를 예측한다.
8. As an Organizer, I want OP-002 기업상세의 "개별 추천"에서 이 배정 허브로 바로 진입하기를, so that 목록에서 본 기업을 출발점 삼아 Forced 플로우를 끊김 없이 이어간다.
9. As an Organizer, I want 상대 참가사를 고를 때 매칭율 높은 기업을 AI가 추천해 주기를, so that 적합한 상대를 빠르게 찾는다.
10. As an Organizer, I want 추천을 무시하고 직접 검색해 다른 기업을 지정하기를, so that AI 추천에 갇히지 않고 내 판단으로 상대를 정한다.
11. As an Organizer, I want 두 기업의 빈 슬롯 교집합만 표시되기를, so that 양쪽이 다 비어 있는 시간만 골라 일정 충돌을 피한다.
12. As an Organizer, I want 전체 참가사를 대상으로 AI 전체 포화배정을 실행하고 최소 N슬롯을 그때 설정하기를, so that 참가사 캘린더를 한꺼번에 포화시키되 보장 슬롯 수를 상황에 맞게 조정한다.
13. As an Organizer, I want 전체 포화배정을 빈 슬롯이 생길 때마다 반복 실행하기를, so that 취소분·지각 합류 기업을 다시 포화시킨다(추가 전용·비파괴).
14. As an Organizer, I want 전체 포화배정 결과를 Draft로 받아 확정 전 개별 수정/삭제하기를, so that 억지 매칭·노쇼 위험을 마지막으로 거른다.
15. As an Organizer, I want 강제 배정한 미팅의 출처가 'Forced'로, 전체 포화배정 산출 미팅이 'AI 매칭'으로 기록되기를, so that 성과 측정 시 출처별로 구분된다.
16. As an Organizer, I want 단일 기업의 빈슬롯만 보충할 땐 OP-003(기업 디테일)로 안내받기를, so that 전체/일괄(OP-005)과 한 기업(OP-003) 관점을 혼동하지 않는다.
17. As a 받는 쪽(일반 바이어/Exhibitor), I want 강제 배정도 수락대기로 들어와 내가 수락/거절하기를, so that 일반 신청과 동일하게 내 일정에 대한 통제권을 갖는다.
18. As a 받는 쪽(초청 바이어), I want 강제 배정이 즉시 확정되고 거부 단계가 없기를, so that 의무 미팅 일정이 바로 잡힌다(원치 않으면 취소).

## Implementation Decisions

**Forced 일원화 진입점 (OP-005가 소유)**
- **D1 — Forced 배정은 OP-005가 유일한 일원화 진입점.** 전체/일괄 관점의 강제 배정은 모두 이 허브에서 시작한다. 단일 기업 빈슬롯 보충(재트리거)·한 곳만 배정은 OP-003(기업 디테일)로 위임한다 — 같은 엔진, 진입 관점만 다름.
- **D2(폐기) — confirmed/proposed 운영사 수동 선택은 폐기됐다(ADR-0005).** 구버전에서는 운영사가 강제 배정 시 수락 상태를 손으로 골랐으나, 이제 **운영사는 수락 상태를 고르지 않는다.** 받는 쪽 유형이 자동 결정하며, **일반 바이어 강제 확정 권한은 없다.** ("긴급 강제 확정" 같은 일반 바이어 대상 수단은 의도적으로 제거 — 트레이드오프.)

**유형별 자동 수락 (ADR-0005)**
- **D3 — 수락 규칙은 받는 쪽 유형이 자동 결정.** Forced(②) 기준:

  | 받는 쪽 | 진입 상태 | 동작 |
  |---------|----------|------|
  | **초청 바이어(Hosted)** | `accepted` 즉시 확정 | 양쪽에 배정 확정 알림. 거부 단계 없음 |
  | **일반 바이어(사전등록·현장)/Exhibitor** | `proposed` 수락대기 | 받는 쪽이 수락/거절. 일반 신청과 동일 |

- **D4 — 결과 상태 미리 표시.** 운영사가 상태를 고르지 않으므로 화면에 받는 쪽 유형 뱃지 + 예상 결과(즉시 확정/수락대기)를 사전 노출한다.
- **D5 — 빈 슬롯 교집합 기반(Forced).** 양쪽이 다 비어 있는 시간만 표시해 충돌을 막는다. 상대 선택 단계는 AI 추천 목록 + 직접 검색 둘 다 지원하나, **주체가 운영사라 출처(provenance)는 'Forced'로 고정**(수락 규칙은 출처와 독립 — ADR-0005).
- **D6 — provenance와 수락 규칙은 별개 축.** 출처(Forced/AI/Open/On-site, 누가 만들었나)와 수락 규칙(받는 쪽이 누구냐)은 독립이다. 강제 배정 미팅은 `matching_type='forced'`로 기록(스키마 `meetings`)되며, 진입 상태(`accepted`/`proposed`)는 받는 쪽 유형으로 갈린다. 취소는 출처·유형 무관 양쪽 누구나 가능.

**OP-002 딥링크**
- **D7 — OP-002 기업상세 "개별 추천"이 이 허브로 딥링크.** 목록에서 본 기업이 Forced 플로우의 출발점(바이어 또는 참가사 사전 선택 상태)으로 이어져 맥락을 보존한다. 역방향(허브 → 대상 기업 → OP-003)도 가능.

**AI 전체 포화배정 (②와 함께 허브가 소유, ADR-0006)**
- **D8 — 전체 포화배정 = 반복 실행 + 최소 N슬롯 실행 시 설정 + 참가사 자동확정·바이어 유형별.** 전체 참가사 대상 참가사 우선 포화, 2라운드(보장→최적화), tie-break=비즈매칭 신청순. Draft 생성 → 운영자 검토(개별 수정/삭제) → 확정 시 양측 통지. **참가사 측은 자동확정**(운영자가 참가사 캘린더를 대신 채우는 구조), 바이어 측은 유형별(초청=즉시 / 일반=수락대기) → 전체 포화배정에서 수락대기는 일반 바이어 수신 건에만 발생.
- **D9 — 스케줄 설정(운영 변수) 이관.** 운영 시작/종료 시각(디폴트 09:00~18:00), 슬롯 길이(디폴트 30분), 점심 블록, 최소 보장 슬롯 수 N(디폴트 10)을 하드코딩하지 않고 배정 허브에서 설정. 구버전의 "최대 미팅 수 제한"은 삭제(ADR-0006은 상한 없이 빈 슬롯을 채우고 형평성은 최소 보장 슬롯 수로 확보).

**아키텍처 경계 (ADR-0008, 경계 B)**
- **D10 — FastAPI가 모든 DB 접근을 소유(경계 B).** 화면은 Next.js, 배정 생성/조회·매칭 엔진 실행은 Next.js → FastAPI API → RDS. Next.js는 DB에 직접 접속하지 않는다. 권한검사(Organizer master만 전체 기능)는 FastAPI 한 곳에 집중하고 Cognito JWT를 JWKS/RS256으로 검증한다. 매칭 엔진(ADR-0006)도 같은 FastAPI에 배치잡으로 합류.

**식별된 deep modules** (격리 테스트 대상 후보)
- `forced-assignment` — 운영사가 바이어+참가사+슬롯을 지정해 미팅을 생성하는 규칙. 핵심은 **수락 규칙 위임** — 진입 상태(`accepted`/`proposed`)를 직접 정하지 않고 받는 쪽 유형에 따라 위임하고, 일반 바이어 강제 확정은 거부한다. 출처는 'Forced'로 고정.
- `acceptance-rule` — 받는 쪽 유형 + 채널을 입력받아 진입 상태를 반환하는 순수 규칙(Forced·AI 재트리거·전체 포화배정·Open 공통). provenance와 독립. `forced-assignment`가 이를 호출(위임)한다.
- `slot-intersection` — 두 기업의 빈 슬롯 교집합을 계산해 가용 슬롯만 반환.
- `saturation-allocation` — 전체 포화배정 엔진(참가사 우선·2라운드·tie-break, 추가 전용·비파괴). 운영 변수(N·점심·슬롯 길이)를 입력으로 받음.

## Testing Decisions

- **좋은 테스트의 기준:** 구현 세부가 아니라 **외부 동작(관찰 가능한 결과)** 만 검증한다. 컴포넌트 내부 상태가 아니라 "초청 바이어를 받는 쪽으로 강제 배정하면 `accepted`로, 일반 바이어를 받는 쪽으로 하면 `proposed`로 기록된다", "일반 바이어 강제 확정 시도는 거부된다" 같은 결과를 본다.
- **테스트 대상 모듈:**
  - `acceptance-rule` — **유형별 수락 규칙(ADR-0005)의 외부 동작 검증**: 초청 바이어 수신 → `accepted`; 일반 바이어/Exhibitor 수신(Forced·Open·재트리거) → `proposed`; 전체 포화배정의 참가사 측 → `accepted`(예외). provenance를 바꿔도 같은 받는 쪽 유형이면 결과 동일(독립 축).
  - `forced-assignment` — **수락 규칙 위임**: 진입 상태를 직접 지정하지 않고 `acceptance-rule`에 위임함을 결과로 검증. **일반 바이어 강제 확정 권한 없음**: 운영사가 일반 바이어를 즉시 확정하려 해도 `proposed`로만 들어가고 강제 확정 경로가 없다. 출처는 항상 'Forced'.
  - `slot-intersection` — 양쪽 빈 시간만 가용으로 반환, 한쪽이라도 찬 슬롯은 제외.
  - `saturation-allocation` — 보장 라운드로 모든 참가사 최소 N 충족, 재실행 시 기존 미팅 불변(추가 전용·비파괴), 빈 슬롯만 채움.
- **Prior art:** 앱 코드가 아직 0인 그린필드라 기존 테스트 선례 없음 → 본 PRD의 모듈이 첫 테스트 패턴의 기준선이 된다. 특히 `acceptance-rule`은 여러 PRD(F-MT-001·F-OP-003·본 PRD)가 공유하는 규칙이라 **수락 규칙 단위 테스트의 공통 기준선**으로 적합하다.

## Out of Scope

- **6/17 컨셉 데모는 목업** — 실제 매칭 로직 없이 UI 흐름(전체 포화배정 실행·Forced 스텝·결과 상태 미리 표시)만 시연. 실제 배정 생성·수락 규칙 적용은 이 슬라이스 구현 범위.
- **fit score(적합도) 정의 미정** — 키워드 카테고리 체계가 미해결(CTO 협의)이라 AI 추천 순위·전체 포화배정의 보장/최적화 라운드·룸 우선순위가 모두 이 정의를 입력으로 쓴다. 정의 확정 전까지 배정 엔진은 완성 불가(ADR-0006 선행 블로커).
- **단일 기업 빈슬롯 보충(재트리거)** — 한 기업만 보충하는 액션은 F-OP-003 소관(같은 엔진, 진입 관점만 다름).
- **sub(무역관) 콘솔** — sub 권한 모델은 **ADR-0012/0013으로 확정**됐다(계정×행사 master/sub + 바이어 소유권 관할). 전체 포화배정·Forced 배정은 그 행사 전역 admin 행위라 **master-for-this-event 전용**이고 sub에겐 열지 않으며(ADR-0012), sub가 자기 관할 바이어를 대신하는 경로는 배정이 아니라 **대리신청**(`proposed`, 참가사 수락 필요 — ADR-0013)이다. sub 전용 콘솔은 별도 라우트 네임스페이스의 후속 슬라이스 소관.
- **Forced 일괄 배정(여러 건 한 번에)·배정 사유 기록·Meeting Venue 배정 연동** — 이후 과제(룸 우선순위는 fit score 선행).

## Further Notes

> ⚠ **정정(2026-09-15, 발주자 QA 지적 B3)**: 아래 D2·D3·D6·D8과 User Stories #5·#6·#17, Testing Decisions의 "일반 바이어 강제 확정 권한 없음" 서술은 **운영자 개입 채널(Forced·AI 전체 포화배정)에 한해 뒤집혔다.** 발주자가 QA 문서에서 "관리자가 강제 배정하면 각각 참가사·바이어에 알림이 가고 무조건 확정으로 바뀐다"를 명시 요구했고, 후속 확인에서 "운영자가 트리거하는 배정은 단건·일괄 모두 무조건 확정"이라고 범위를 못박았다 — **Forced(단건)·AI 전체 포화배정 확정(일괄)으로 받는 미팅은 받는 쪽 유형(초청/일반 바이어·Exhibitor) 무관하게 항상 `accepted`**이고, 확정과 동시에 양쪽 조직에 알림이 간다(신규 알림 타입 없이 기존 `meeting_accepted` 재사용, 건별 발화 — 알림 폭주 대응을 위한 배치 요약은 만들지 않는다). D8의 "바이어 측은 유형별(초청=즉시/일반=수락대기)"는 폐기됐다 — **전체 포화배정도 이제 바이어 측 전원 즉시확정**이다. Open·AI 단일 재트리거·현장 생성은 원래 규칙(일반 바이어/Exhibitor 수신 시 수락대기) 그대로다 — **이 예외는 운영자가 직접 트리거하는 두 채널에만 적용**되고, 참가자끼리 주고받는 일반 신청(Open)은 신청→상대 수락 구조가 그대로 유지된다. 구현은 `backend/app/matching/acceptance_rule.py`의 `resolve_entry_state`가 `Channel.FORCED`/`Channel.AI_SATURATION`을 받는 쪽 유형 분기보다 먼저 검사한다(`_OPERATOR_OVERRIDE_CHANNELS`). ADR-0005 본문도 같은 근거로 정정했다(ADR-0010의 타임존 정정과 같은 형식).

- **D2(confirmed/proposed 운영사 수동 선택)는 ADR-0005로 명확히 폐기됐다.** 구 PRD의 "운영사가 수락 상태를 고른다", "긴급 강제 확정" 흔적은 모두 무효이며, 운영사는 수락 상태를 선택하지 않고 받는 쪽 유형이 자동 결정한다. 일반 바이어 강제 확정 권한은 의도적으로 제거됐다.
- **provenance와 수락 규칙은 독립 축이다**(CONTEXT.md / ADR-0005): 출처는 'Forced'로 기록되어도 진입 상태는 받는 쪽 유형으로 갈린다. 스키마는 `meetings.matching_type='forced'`로 출처만 박고, 수락 컬럼은 따로 두지 않는다(양방향 수락대기 없음).
- **전체 포화배정 vs Forced의 수락 차이:** 전체 포화배정(①)은 참가사 측을 자동확정으로 두므로 Exhibitor 수신도 `accepted`이고 수락대기는 일반 바이어 수신 건에만 발생. Forced(②)·단일 재트리거는 Exhibitor 수신도 `proposed`. 초청 바이어 수신은 양 방식 모두 즉시 확정.
