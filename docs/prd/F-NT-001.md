# F-NT-001: 알림 (Notification)

> 미팅 신청·수락·취소, 미팅 임박, 리뷰 입력 안내, 회의록 정리 완료를 당사자 기업에 **통지하고 조회**하는 시스템. 조직 공유 인박스 + 외부 발송(이메일/SMS).

| 메타 | |
|------|------|
| Page ID / 기능 ID | NT-001 / F-NT-001 |
| 라우트 / 형태 | `/notifications` / 페이지 (+ 전역 nav 벨) |
| 상태 / 디바이스 | draft / 데스크톱 + 모바일 반응형(현장 다수) |
| 가설 | 제때 통지하면 미팅 응답·참석·리뷰 입력률이 올라 매칭 성과가 실현·측정된다 |
| 관리지표 | 알림 도달률, 안읽음 비율, 알림→액션(수락/참석/리뷰) 전환율, 채널별 발송 성공률 |
| 관련 ADR | **ADR-0010(알림 모델)**, ADR-0002(매칭단위 Org), ADR-0004(리뷰·noshow), ADR-0008(경계 B) |
| 관련 PRD | F-MT-001(미팅 상태), F-MY-002(리뷰), F-HM-001(대시보드 소비) |

---

## Problem Statement

당사자 입장에서:

- 미팅이 신청·수락·취소돼도 **앱을 열어보지 않으면 모른다.** 참가사/바이어는 앱을 가끔 열기 때문에 제때 응답하지 못해 미팅 기회를 놓친다.
- 전시 당일 현장에서 **다음 미팅이 임박했는데** 일정을 놓쳐 노쇼가 난다.
- 미팅이 끝나도 **리뷰를 입력해야 한다는 걸 모르고** 지나쳐, 성과 측정 데이터가 비고 보고서 자동화 가치도 못 받는다.
- 같은 기업의 다른 담당자가 이미 처리한 일을 **누가 봤는지 몰라** 중복 대응하거나 빠뜨린다.

## Solution

당사자 입장에서:

- 6가지 사건(신청받음·수락됨·취소됨·10분 전 리마인더·리뷰 안내·회의록 정리 완료)이 **알림으로 도착**하고, 어느 화면에서나 **nav 벨 배지**로 안읽음을 본다.
- **`/notifications`에서 전체를 조회**하고 필터·모두읽음 한다. 알림을 누르면 해당 미팅/리뷰로 바로 이동한다.
- 알림은 **기업 공유 인박스** — 같은 기업 누구나 같은 목록을 보고, **누가 언제 읽었는지** 표시되어 중복/누락이 준다.
- 현장 시급 알림(10분 리마인더)은 **이메일·SMS로도** 도착해 앱을 안 봐도 놓치지 않는다.

## User Stories

1. As a 바이어/참가사, I want 누군가 내게 미팅을 신청하면 알림을 받기를, so that 제때 수락/거부한다.
2. As a 신청자, I want 내 미팅 신청이 수락되면 알림을 받기를, so that 확정된 일정을 안다.
3. As a 당사자, I want 예정된 미팅이 취소되면 알림을 받기를, so that 헛걸음하지 않는다.
4. As a 당사자, I want 미팅 10분 전 리마인더를 받기를, so that 현장에서 제시간에 참석한다.
5. As a 당사자, I want 미팅이 끝나면 리뷰 입력 안내를 받기를, so that 후속 의향·적합도를 기록하고 보고서를 받는다.
5b. As a 회의록 업로드자, I want 녹음 전사·구조화(AI 회의록 정리)가 끝나면 알림을 받기를, so that 비동기 작업 완료를 기다리지 않고 결과를 확인·저장한다.
6. As a 기업 멤버, I want 같은 기업 동료와 알림함을 공유하기를, so that 누구든 먼저 본 사람이 대응할 수 있다.
7. As a 기업 멤버, I want 각 알림에 "누가 언제 읽었는지" 보이기를, so that 중복 대응이나 누락을 피한다.
8. As a 사용자, I want 어느 화면에서나 nav 벨의 안읽음 배지로 새 알림 유무를 알기를, so that 굳이 알림함을 안 열어도 신호를 받는다.
9. As a 사용자, I want `/notifications`에서 전체 알림을 시간순으로 보고 필터(종류별)하기를, so that 원하는 알림을 빠르게 찾는다.
10. As a 사용자, I want 알림을 누르면 관련 미팅/리뷰 화면으로 바로 이동하기를, so that 통지에서 행동까지 한 번에 간다.
11. As a 사용자, I want "모두 읽음" 처리를, so that 쌓인 알림을 한 번에 정리한다.
12. As a 현장 사용자, I want 시급한 리마인더가 이메일/문자로도 오기를, so that 앱을 안 보고 있어도 미팅을 놓치지 않는다.
13. As a 모바일 사용자, I want 리마인더가 알림함 상단에 떠 있기를, so that 작은 화면에서도 즉시 보인다.
14. As a 사용자, I want 미팅이 취소되면 그 미팅의 리마인더가 더는 오지 않기를, so that 잘못된 알림에 혼란받지 않는다.
15. As a Visitor(권한 없음), I want 알림 표면이 노출되지 않기를, so that 내 역할에 맞지 않는 UI에 혼란받지 않는다.
16. As a 운영팀, I want 알림이 통지 당시 내용 그대로 보존되기를, so that "언제 무엇을 통지했는지" 사후에 신뢰할 수 있다.

## Implementation Decisions

**수신 단위 (ADR-0010)**
- 알림은 **Organization 공유 인박스**. read_at·read_by_member_id로 **기업 공유 읽음**(누가 언제). 외부 발송은 멤버 연락처로 팬아웃.
- 운영사 알림은 v1 범위 밖(수신 단위 Org 단일 유지).

**채널 (ADR-0010)**
- 인앱+이메일=전 6종. SMS=현장 시급건(10분 리마인더, 취소 선택)·인프라 조건부. 푸시 보류.
- 우아한 열화: 가능한 채널만 발송, 불가 채널은 `status='skipped'`. 읽음은 외부 발송 성공과 분리.

**트리거 6종 · 발화 (ADR-0010)**
- 이벤트성(신청·수락·취소): 상태 전이 시 즉시 생성. 시간성(리마인더·리뷰안내): 폴링 스케줄러(cron ~1분, `meetings` 현재 상태 조인 "still eligible", 멱등).
- 비동기 작업성(회의록 정리 완료): 전사·구조화 작업(F-MY-002) `done` 시 녹음 업로드한 org에 즉시 발화. due_at NULL, 인앱·이메일만(SMS 제외). 재전사 시 재통지 안 함(org·미팅당 1행).
- 미팅 자동완료: scheduled_end 경과 시 **accepted만** completed(취소/거부 제외). noshow는 리뷰 입력값(ADR-0004).
- 스케줄러 가드: scheduled_start/end 둘 다 있을 때만 enqueue(없으면 소급), 리스케줄 시 리마인더 행 삭제+재생성, 시각은 timestamptz(저장 UTC, 해석·표시는 events.timezone — ADR-0014, ADR-0010 2026-09-12 정정).

**수신 타깃팅 매트릭스** (트리거 × 수신 org × 행 수)

| 트리거 | 수신 org | 행 수 |
|--------|----------|-------|
| 미팅 신청받음 | 받는 쪽(신청 안 한 org) | 1 |
| 내 신청 수락됨 | 신청한 쪽(요청자 org) | 1 |
| 미팅 취소됨 | 취소 안 한 쪽 | 1 |
| 10분 리마인더 | 양측 | 2 |
| 리뷰 입력 안내 | 양측(리뷰는 org별 독립) | 2 |
| 회의록 정리 완료 | 녹음 업로드한 org | 1 |

**데이터 모델 (ADR-0010)**
- `notifications`(recipient_org_id, type CHECK enum, meeting_id FK, due_at[시간성만], payload jsonb 스냅샷, created_at, read_at, read_by_member_id) · **UNIQUE(type, meeting_id, recipient_org_id, due_at) NULLS NOT DISTINCT** + ON CONFLICT DO NOTHING.
- `notification_dispatches`(notification_id, member_id, channel, status, sent_at, error) · UNIQUE(notification_id, member_id, channel).
- payload = 표시 데이터 **스냅샷**(불변 기록). meeting_id 컬럼은 링크·"이 미팅 알림들" 조회용.

**타입별 payload 스냅샷 스키마** (코드에서 Pydantic/TS로 강제)
- `meeting_requested`: { counterpart_org_name, requested_by_role }
- `meeting_accepted`: { counterpart_org_name, scheduled_start, venue_label }
- `meeting_cancelled`: { counterpart_org_name, scheduled_start, cancelled_by_role }
- `meeting_reminder`: { counterpart_org_name, scheduled_start, venue_label }
- `review_prompt`: { counterpart_org_name }
- `review_ready`: { counterpart_org_name }

**표면별 렌더 필드**
- nav 벨: 안읽음 개수(배지)만.
- `/notifications` 행: type 아이콘 + 위 payload로 만든 문구 + 상대기업 + 시각 + 읽음표시(시각·멤버) + 딥링크.

**딥링크 타깃**

⚠ `/meetings/:meetingId`는 **MY-002 미팅 리뷰(회의록) 화면**이다(page-list.csv) — "미팅 상세"가 아니다.
수락/거절/취소는 MY-001 타임라인(`/meetings`)에만 있다. 아래 표는 그 구분을 반영한 정정본이다
(이전 판은 6종 전부를 `/meetings/:meetingId`로 보내 "미팅 신청받음"을 눌러도 회의록 작성 화면이 떴다).

| type | 목적지 |
| --- | --- |
| `meeting_requested` | `/meetings?meeting=:meetingId` (타임라인에서 그 미팅 선택 → 수락/거절) |
| `meeting_accepted` | `/meetings?meeting=:meetingId` |
| `meeting_cancelled` | `/meetings?meeting=:meetingId` |
| `meeting_reminder` | `/meetings?meeting=:meetingId` |
| `review_prompt` | `/meetings/:meetingId` (F-MY-002 리뷰 입력) |
| `review_ready` | `/meetings/:meetingId` (F-MY-002 — 정리된 초안 확인·저장) |
| `meeting_id`가 null | `/notifications` (미팅 비연계 통지) |

- 리뷰 라우트는 **화이트리스트**로만 간다 — FE가 모르는 type이 내려와도 회의록 화면으로 새지 않고
  타임라인으로 떨어진다(`lib/home/notification.ts`의 `REVIEW_TYPES`).
- 컨텍스트 복귀를 위해 `from=notifications` 부여.

**표면·접근 (ADR-0010)**
- 전역 nav 벨(배지) → `/notifications`(드롭다운 v1 컷) = **6종 전체**·필터·모두읽음(조회 본진). 권한 없음(Visitor)=벨 숨김(nav 가드). 모바일: 벨 배지 + 리마인더 상단.
- 아키텍처: Next.js → FastAPI API → RDS(경계 B). 발화(이벤트 훅·cron)·발송(이메일/SMS)·조회 API 모두 FastAPI 소유.

**식별된 deep modules**
- `notification-emitter` — 트리거 → 수신 매트릭스대로 멱등 알림 행 생성(ON CONFLICT).
- `notification-scheduler` — 폴링 due 평가(still-eligible 조인) + 미팅 자동완료.
- `notification-dispatcher` — 멤버×채널 팬아웃·재시도·skip.
- `notification-inbox` — 조회/필터/모두읽음·org 공유 읽음.

## Testing Decisions

- **좋은 테스트 기준:** 외부 동작만. 예) "미팅 신청 시 받는 쪽 org에 행 1개만 생성된다", "같은 트리거가 두 번 발화돼도(cron 재시도) 알림은 1개"(멱등), "9분 전 취소된 미팅은 10분 리마인더가 안 나간다".
- **테스트 대상 모듈:**
  - `notification-emitter` — 수신 매트릭스(트리거별 수신 org·행 수), 멱등(NULLS NOT DISTINCT + ON CONFLICT).
  - `notification-scheduler` — due 평가, 취소건 제외, scheduled_start NULL 가드, 리스케줄 재생성, accepted만 자동완료.
  - `notification-dispatcher` — 멤버 팬아웃, 연락처 없음·SMS 불가 시 skip, 재시도 시 중복 행 없음, 읽음과 발송 분리.
  - `notification-inbox` — org 공유 읽음(한 멤버가 읽으면 공유), read_by 기록.
- **Prior art:** 앱 코드 0인 그린필드. 폴링·멱등·팬아웃 패턴의 기준선이 됨.

## Out of Scope

- **운영사(Organizer) 알림** — v1 제외(OP-001 대시보드 위젯으로 대체). backlog.
- **푸시(웹/앱)** — PWA/네이티브 도입 시. backlog.
- **nav 벨 드롭다운** — v1은 배지→/notifications 딥링크만. backlog.
- **멤버 개인별 읽음** — v1은 org 공유. 개인 "내가 본 시각" 클라 플래그는 post-v1.
- **SMS 실발송** — 발신번호·인프라(인증 OTP 공유)는 선행 블로커. 준비 시 활성(설계엔 포함).
- **HM-001 대시보드 표시 항목** — F-HM-001 소관.

## Further Notes

- 본 기능과 함께 **`meetings.status`에서 `noshow` 제거 + 리뷰 값으로 이전**(ADR-0004 보정)을 db-schema-keeper로 반영한다.
- 멱등 유니크는 **RDS Postgres 15+ `NULLS NOT DISTINCT`** 전제(이벤트형 due_at NULL 중복 제거).
- 관련 문서: ADR-0010, ADR-0002/0004/0008, CONTEXT.md(Notification), F-MT-001, F-MY-002, F-HM-001.
