# 참가자 메뉴 — 행사 설정으로 참가사·바이어 nav를 고른다(기본 "미팅만", 화면 구성용이며 권한이 아니다)

발주사 요청(2026-10-08)으로 참가사·바이어 화면의 왼쪽 메뉴를 "미팅" 하나로 줄인다. 한 행사만을 위한 분기를 코드에 박지 않고 **행사 단위 설정값**으로 두며(ADR-0012의 멀티 행사 원칙), 그 값이 무엇을 하고 무엇을 하지 않는지를 여기 못박는다.

## 배경

발주사가 비즈매칭 진행 방식을 바꿨다 — 참가자가 직접 탐색·신청하는 대신 운영자가 미팅을 배정한다. 그래서 참가사·바이어에게는 "내 미팅"만 보이면 되고, 대시보드·기업 탐색·알림·프로필 메뉴는 숨겨 달라는 요청이다. 방침은 **"화면이 그렇게 보이면 된다 — 내부 기능(화면·API)은 지우지 않고 유지한다."**

이 플랫폼은 행사마다 재사용한다. 다음 행사는 다시 참가자 자율 신청으로 돌아갈 수 있으므로 메뉴를 코드에서 지우는 건 답이 아니다.

## 결정

1. **행사 설정 `participant_menu` 를 둔다. 값은 `meetings_only`("미팅만") / `full`("전체 메뉴") 둘.** 슈퍼어드민(master)이 관리자 콘솔 행사 설정에서 바꾼다(`PATCH /api/admin/events/{id}/settings`). 참가자 화면은 `GET /api/me` 의 `roles[].participant_menu` 로 받는다.

2. **기본값은 `meetings_only` 다(발주사 결정).** 배포하는 순간 참가사·바이어 화면이 미팅 전용으로 보여야 하고, 누가 설정을 따로 켤 필요가 없어야 한다. 그래서 컬럼 `server_default` 가 기존 행도 `meetings_only` 로 백필하고, 값을 알 수 없는 모든 경우 — 설정 행이 없는 행사, 응답에 필드가 없는 구 백엔드, `/api/me` 조회 실패, 목업(dev) 세션, 값을 싣지 않은 알림 봉투 — 가 같은 기본값으로 떨어진다. **기본값은 백엔드·프런트 각각 상수 하나**(`app.models.DEFAULT_PARTICIPANT_MENU`, `lib/event/participant-menu.ts` 의 `DEFAULT_PARTICIPANT_MENU`)이고 모든 폴백이 그 상수를 본다.

3. **`full` 로 설정한 행사는 이 설정이 생기기 전과 완전히 같다.** 고객이 되돌릴 수 있어야 하므로, 전체 메뉴 쪽의 화면 문구·동선·알림 메일 본문은 한 글자도 바꾸지 않는다(메일 본문은 테스트가 글자 그대로 고정한다).

4. **이 값은 화면 구성용이다 — 권한이 아니다.** `meetings_only` 여도
   - 백엔드 API(탐색·관심기업·알림·프로필·미팅 신청/수락/거절/취소)는 그대로 동작한다. 이 값을 읽어 요청을 거절하는 코드를 두지 않는다.
   - 숨긴 화면(`/discover`·`/notifications`·`/profile`·`/exhibitor/profile`)은 주소로 들어오면 그대로 열린다. 라우트 게이트(`proxy`·`route-guard`, FE ADR-0002)는 이 값을 모른다.
   - 달라지는 건 **진입점**뿐이다: 사이드바 항목, 로그인 후 도착 화면, 미팅 화면에서 탐색으로 나가는 버튼, 기업 상세의 미팅 신청·관심기업 토글, 도움말·알림 메일이 가리키는 화면.

5. **저장 위치는 `events` 가 아니라 `event_schedule_settings.participant_menu`**(text, NOT NULL, CHECK 로 두 값만). `events` 는 레포 밖 읽기 전용 계정이 직접 읽는 테이블이라 스키마를 바꾸지 않는다 — 최근 설정 두 개(`slot_gap_minutes`·`max_meeting_minutes`, `mt003gap0001`)와 같은 자리다. 이 테이블의 행은 처음 닿을 때 생기므로 "행이 없는 행사 = 기본값" 규칙이 따라붙는다(결정 2).

## Considered Options

- **메뉴 항목을 코드에서 지운다(기각).** 가장 빠르지만 행사마다 재사용하는 플랫폼에서 다음 행사가 전체 메뉴를 원하면 다시 코드를 고쳐 배포해야 한다. 되돌리는 비용이 설정 하나보다 훨씬 크다.
- **기본값 `full`, 필요한 행사만 `meetings_only` 로 켠다(처음 안 — 발주사 결정으로 기각).** 배포 후 누군가 운영 DB의 설정을 바꿔야 요청한 화면이 된다. 행사 직전에 수동 단계 하나를 남기는 것보다, 배포만으로 요청한 화면이 되는 쪽을 택했다. 대가는 **이 배포가 무동작 변화가 아니라는 것** — 모든 행사의 참가자 화면과 알림 메일 문구가 배포 즉시 바뀐다.
- **`meetings_only` 에서 숨긴 화면·API를 실제로 막는다(기각).** 방침이 "기능 유지"이고, 막는 것은 권한 결정이라 범위가 다르다. 화면 구성 설정이 권한까지 겸하면 "메뉴에 없으니 안전하다"는 잘못된 가정이 생긴다 — 막아야 한다면 서버 쪽 정책으로 따로 결정한다.
- **설정을 `events` 테이블에 둔다(기각).** 행사 정책이라는 성격은 `events` 에 더 맞지만, 외부 읽기 계정이 읽는 테이블의 스키마를 건드리지 않는다는 운영 제약이 우선한다.
- **프런트 환경변수로 켠다(기각).** 행사 단위가 아니라 배포 단위가 되고, 알림 메일을 만드는 백엔드가 같은 값을 알 수 없다.

## Consequences

- **스키마(파생 — db-schema-keeper 동기화 필요, 이 ADR 범위 밖):** `event_schedule_settings.participant_menu`(신설, text NOT NULL default `'meetings_only'`, CHECK `event_schedule_settings_participant_menu_check`). 마이그레이션 `nv001menu0001`.
- **배포 순서:** 마이그레이션 → 백엔드 → 프런트. 프런트가 먼저 올라가도(응답에 필드 없음) 기본값이라 화면은 같다. 마이그레이션을 내릴 때는 이 컬럼을 읽는 백엔드를 먼저 내린다(`/api/me` 가 설정 행을 조인한다).
- **"숨김"을 보안으로 읽지 않는다.** `meetings_only` 행사에서도 참가자는 주소를 알면 탐색·신청을 할 수 있다. 그게 문제가 되는 행사가 생기면 이 ADR을 다시 열어 서버 쪽 차단을 결정한다.
- **목업(dev) 세션은 기본값으로 보인다.** 전체 메뉴의 목업 화면·테스트는 값을 명시해야 한다(dev 쿠키 `nabi_dev_menu=full`, 테스트는 `full` 을 넘긴다). 운영 빌드는 그 쿠키를 읽지 않는다.
- **알림 메일 한 종은 그대로다.** 거절 메일의 "다른 시간으로 다시 신청해 보세요"는 화면을 가리키지 않아 이번에 바꾸지 않았다 — `meetings_only` 행사에서 이 안내가 맞는지는 운영 방식에 달려 있어 별도로 정한다.

Status: accepted
