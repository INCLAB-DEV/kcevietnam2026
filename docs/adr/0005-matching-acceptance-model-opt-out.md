# 매칭 수락 모델 — opt-out 즉시 확정

비즈매칭의 수락 모델을 "제안→양측 수락(opt-in)"에서 "즉시 확정 후 취소 가능(opt-out)"으로 뒤집었다. 수많은 기업이 미팅마다 일일이 요청/수락을 거치는 부담을 없애 매칭 밀도를 끌어올리는 것이 목적이다. 다만 **수락 규칙은 출처(provenance)가 아니라 "누가·언제 받느냐"로 결정**되며, 동의가 필요한 경우(일정이 살아있는 시점에 일반 바이어가 받는 건)에는 여전히 수락대기를 둔다.

## 핵심 규칙

**수락 여부는 "받는 쪽 바이어 유형"으로 결정된다 — provenance(누가 만들었나)와 독립이다.** 운영자가 confirmed/proposed를 수동으로 고르지 않고, 받는 쪽 유형이 자동으로 결정한다.

| 진입 상태 | 적용 케이스 |
|----------|------------|
| **`accepted` 즉시 확정** (거부 단계 없음) | ① **초청 바이어(Hosted)** 가 받는 모든 건 (전 채널) ② **Forced(강제 배정, 단건)·AI 전체 포화배정 확정(일괄)으로 받는 모든 건**(받는 쪽 유형 무관 — 2026-09-15 정정, 아래 참고. 운영자가 직접 트리거하는 두 채널) |
| **`proposed` 수락대기** (받는 쪽 수락 필요) | ① **일반 바이어** 가 받는 건 (Open · 단일 재트리거 — **Forced·AI 전체 포화배정은 제외**, 아래 정정) ② **Exhibitor** 가 받는 건 (Open · 단일 재트리거 — **Forced·AI 전체 포화배정은 제외**) |

즉, **유형-무관 전원 즉시확정 예외는 폐기**됐다. 규칙은 균일하게 **초청 바이어 수신=즉시 / 일반 바이어 수신=수락대기 / Exhibitor 수신=수락대기** — 단 **운영자가 직접 트리거하는 채널(Forced·AI 전체 포화배정)은 예외**(아래 정정)로, 그 두 채널에서는 받는 쪽 유형 무관 항상 즉시확정이다.

> ⚠ **정정(2026-09-15, 발주자 QA 지적 B3)**: 아래 취소선 문단은 원래 "Forced Matching도 이 규칙을 따른다 — 운영자에게 일반 바이어 강제 확정 권한은 없다. 의무 미팅은 받는 쪽이 초청 바이어라 자동으로 즉시 확정되므로 별도 강제 수단이 필요 없다"였다. 발주자가 QA 문서에서 "관리자가 참가사에 바이어를 매칭시켜주면 각각 회사에 알림이 가고 미팅은 무조건 확정으로 바뀐다"를 명시적으로 요구해 이 부분을 뒤집었다 — **Forced(강제 배정) 채널은 받는 쪽 유형과 무관하게 항상 즉시 확정(accepted)**이다. "강제 배정"이라는 이름 그대로 운영자가 대상을 고르면 그 자리에서 확정이고, 확정과 동시에 참가사·바이어 양쪽 조직에 알림이 간다(기존 `meeting_accepted` 알림 재사용 — `backend/app/admin/router.py`의 `_emit_assignment_notifications`). 구현은 `backend/app/matching/acceptance_rule.py`의 `resolve_entry_state`가 `Channel.FORCED`를 받는 쪽 유형 분기보다 먼저 검사해 항상 `ACCEPTED`를 반환하도록 정정했다.

> ⚠ **재정정(2026-09-15, 같은 날 범위 확인)**: 위 첫 정정은 Forced(단건)만 다뤘다. 발주자가 후속 확인에서 **"운영자가 트리거하는 배정은 단건·일괄 모두 무조건 확정"**이라고 범위를 명확히 했다 — 원 문단의 "**AI 전체 포화배정에서 참가사 측**만 자동확정, 바이어 측은 유형별(초청=즉시/일반=수락대기)"도 함께 폐기한다. **AI 전체 포화배정(Channel.AI_SATURATION) 확정도 Forced와 동일하게 받는 쪽 유형 무관 항상 accepted**다 — 전체 포화배정에서 일반 바이어 수신 건도 더 이상 수락대기로 남지 않는다. 신규 알림 타입 없이 기존 `meeting_accepted`를 건별로 재사용하고(배치 요약·묶음 발송 같은 최적화는 발주자가 명시적으로 불필요하다고 판단해 설계하지 않는다), 알림 발화 실패가 이미 커밋된 배정을 되돌리지 않는다는 `notify_after_commit` 원칙은 그대로 지킨다(거절 알림 도입 때와 동일 보장). 이 예외는 **운영자가 직접 트리거하는 두 채널(Forced·AI_SATURATION)에만** 적용된다 — 참가사·바이어가 서로 주고받는 **Open(일반 신청)은 신청→상대 수락 구조가 그대로**이고, AI 단일 재트리거·현장 생성도 받는 쪽 유형별 규칙을 그대로 따른다. 구현은 `resolve_entry_state`가 `Channel.FORCED`·`Channel.AI_SATURATION` 둘 다를 받는 쪽 유형 분기보다 먼저 검사하는 `_OPERATOR_OVERRIDE_CHANNELS` 집합으로 처리한다. `docs/prd/F-OP-005.md`(D2·D3·D8)도 같은 근거로 함께 정정했다(ADR-0010의 타임존 정정과 같은 형식).

- "즉시 확정(accepted)"이 생략하는 것은 **참가자의 수락 단계**다. **운영자의 검토 게이트는 유지**된다: AI 전체 포화배정은 Draft로 생성 → 운영자가 검토(개별 수정/삭제 가능) → 확정하는 순간 위 규칙대로 양측에 배정(`accepted`)/수락대기(`proposed`) 통지. 운영자가 억지 매칭·노쇼 위험을 거르는 마지막 관문.
- **거부(reject)** 는 `proposed` 단계에서만 존재한다. 즉시 확정 건엔 (참가자가) 거부할 틈이 없다.
- **취소(cancel)** 는 출처·유형 무관, 모든 미팅을 양쪽 누구나 할 수 있다(취소 넛지 적용).
- **AI Matching은 2가지 액션**으로 동작한다: 전체 포화배정(전체 참가사·반복 가능·확정 시 양측 전원 즉시확정 — 2026-09-15 재정정, 위 참고) / 단일 기업 빈슬롯 보충 재트리거(받는 쪽 유형별, 추가 전용·비파괴).

## Considered Options

- **opt-in (제안→양측 수락, 기존 결정):** 동의·통제는 확실하나, 수백 건의 미팅마다 요청/수락 왕복이 필요해 매칭 밀도가 낮고 이탈이 크다. 일회성 이벤트에서 "일단 잡혀 있는" 일정의 가치를 살리지 못함.
- **opt-out (즉시 확정→취소, 채택):** 매칭 밀도 극대화. 단, 동의 없이 일정이 잡히는 부담을 **일정이 살아있는 시점의 일반 바이어**에 한해 수락대기로 완화.

## Consequences

- **F-MT-001의 D3·D4·D9 및 상태흐름을 supersede.** 특히 "AI는 제안만 한다"는 기존 서술은 폐기.
- 같은 "AI가 빈 슬롯을 채운다"는 동작이 **채널(전체 포화배정 vs 단일 재트리거)에 따라 수락 규칙이 달라진다**(전체 포화=운영자 확정 버튼이라 항상 즉시확정 / 단일 재트리거=받는 쪽 유형별, 2026-09-15 재정정) — 구현·UI에서 분기 필요.
- "추천받아 직접 선택" 모드는 동일 인터랙션이나 **주체의 권한이 provenance를 결정**한다(운영자=Forced, 참가사/바이어=Open). 단 수락 규칙은 둘 다 받는 쪽 유형 따라 동일(단, 운영자가 트리거하는 Forced/AI 전체 포화배정은 예외 — 위 정정 참고).
- **F-OP-005의 confirmed/proposed 수동 선택(D2) 폐기.** 운영자는 수락 상태를 고르지 않는다 — 받는 쪽 유형이 자동 결정하되, **운영자가 직접 트리거하는 두 채널(Forced·AI 전체 포화배정)만은 그 결정이 항상 accepted로 고정**된다(2026-09-15 정정·재정정). "긴급 강제 확정" 같은 수단을 의도적으로 제거했던 원래 트레이드오프는 폐기됐다 — 운영자 트리거 자체가 그 수단이 됐다.
- 바이어 3유형의 "플랫폼 경험 동일" 원칙은 **매칭 수신 시 초청 vs 일반**(전 채널)에서만 깨진다(CONTEXT.md 반영 완료).
