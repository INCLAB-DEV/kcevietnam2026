# KOTRA 무역관 도메인 — 운영자대행 바이어 적재(스냅샷 공존)·대리신청 출처/수락·체류정보

ADR-0012가 운영자 권한을 계정×행사 master/sub + 바이어 소유권 관할로 모델링하면서 **별도 후속으로 미뤄둔 세 충돌**(Consequences ③)을 닫는다: ① KOTRA 무역관이 데려온 해외 바이어를 NABI에 어떻게 적재하는가(ADR-0007 스냅샷 모델과 충돌), ② 무역관의 대리신청을 매칭 상태흐름(ADR-0005)에 어떻게 잇는가, ③ 방한 바이어 체류정보(항공·숙박·통역)를 어떻게 모델링하는가. 출처는 KOTRA "통합 상담주선 시스템 기능 요구사항"(블록 ④ 해외무역관)이며, 이 결정들이 무역관(sub) 콘솔(#110)을 푼다.

## 배경

ADR-0007은 "모든 등록자는 주관사(DX Korea)가 export한 **전체 스냅샷 파일**을 운영자가 업로드 → **주관사 회원ID 키로 멱등 upsert**"로 적재하고, **공개 자체 회원가입은 없다**(딥링크 + DX Korea 인증)로 닫았다. 그런데 KOTRA 해외무역관은 **현지에서 해외 바이어를 직접 모집**한다 — 이 바이어들은 DX Korea에 신청한 적이 없어 스냅샷에도 회원ID에도 없고, 한국 주관사 인증 경로로 로그인할 수도 없다. KOTRA PDF는 이를 "국내기업·무역관 self-register + 관리자 승인"으로 풀었으나, 그대로 채택하면 ADR-0007의 스냅샷·무가입 원칙과 정면 충돌한다.

ADR-0005는 수락 규칙을 "**받는 쪽 유형**으로 결정(provenance 무관)"으로 정했고, CONTEXT 글로서리는 **대리신청**을 "무역관이 자기 관할 바이어를 대신해 참가사에 신청, Forced와 구분"으로 정의만 해뒀다(출처·수락 미확정).

체류정보(항공·숙박·통역)는 현재 스키마에 없다(ADR-0012에서 의도적 보류). 다만 **바이어 참석자(`buyer_attendees`)에 통역 필드가 이미 있다**(`interpreter_need`, `interpreter_languages`, `languages`).

## 결정

### 1. 적재 — 운영자 직접입력 경로를 스냅샷과 **공존**시킨다 (대체 아님)

- 무역관이 모집한 해외 바이어는 주관사 스냅샷 밖이므로, **운영자가 NABI에서 직접 Buyer로 등록**한다(폼 입력). **`Registrant` 적재층(스냅샷·회원ID 키)을 거치지 않고**, 곧장 `Organization` + `organization_event_role`로 생성한다 — 회원ID가 없어 멱등 키가 성립하지 않기 때문. **두 경로의 가르는 축은 국적이 아니라 "상류 신원(주관사 회원ID)의 유무"** 다: 스냅샷 경로는 **회원ID가 있는 모든 신청자**(ADR-0007 키가 해외업체·개인 바이어도 커버 — 국적 무관)에 유지되고, 운영자 직접입력은 **회원ID가 없는(무역관 현지 모집) 바이어 한정**이다. 두 적재 경로가 공존한다.
- **국내기업(Exhibitor)의 self-register는 채택하지 않는다.** NABI는 DX Korea와 통합돼 있어 참가사 진실 원천은 스냅샷이다(PDF의 국내기업 자가등록은 KOTRA 독립 시스템 가정).
- **공개 자체 회원가입 없음(ADR-0007)은 유지**된다 — 직접 등록은 *바이어 본인의 가입*이 아니라 *운영자의 대리등록*이다. 이 바이어는 **본인 로그인·DX Korea 인증이 없고**, 무역관이 프로필·신청·체류정보를 전부 대행한다(operator-managed/proxy buyer).
- **승인 게이트:** 직접 등록분도 기존 `application_status`(…→`submitted`→`approved`) 상태머신을 그대로 통과한다 — **매칭 노출은 master(주최사/KOTRA 본부) 승인(`approved`) 이후**. PDF의 "관리자 승인"이 NABI 기존 승인 문에 1:1로 매핑된다(sub는 승인 불가, ADR-0012). 새 승인 메커니즘을 만들지 않는다.
- 스냅샷 재업로드는 **add/update만(삭제 없음, ADR-0007)** 이므로 운영자 직접입력분을 덮거나 지우지 않는다.

### 2. 대리신청 — 신청자는 바이어, 대행 운영자는 별도 도장, 수락은 ADR-0005 그대로

- **provenance:** 미팅의 신청 측은 **바이어(`requested_by='buyer'`)** 로 기록한다 — 미팅 당사자·후기·관계는 바이어↔참가사이고, 무역관은 행위자일 뿐. 채널은 바이어 자가신청과 같은 **Open(`matching_type='open'`)**. 대행한 무역관은 **별도 필드(대행 도장)** 로 남겨 감사·추적을 보장한다.
- **수락:** 받는 쪽이 **참가사(Exhibitor)** 이므로 ADR-0005 규칙대로 **`proposed`(참가사 수락 필요)**. 무역관이 대행했다고 참가사 일정에 강제 확정되지 않는다 — 그것은 Forced이며 대리신청과 구분된다. 운영자에게 일반 측 강제확정 권한은 없다(ADR-0005).
- 따라서 대리신청은 **"바이어의 Open 신청을 무역관이 대행"** 으로 환원되어, 수락 규칙·UI 분기를 새로 만들 필요가 없다.

### 3. 체류정보 — 참석자(사람)별, 통역은 재사용

- **항공(도착/출발 편명·일시)·숙박(호텔·체크인/아웃)** 을 **`buyer_attendees`(참석자=사람) 단위**로 단다 — 일행이 서로 다른 항공편·호텔일 수 있으므로 회사 단위로 묶지 않는다.
- **통역(필요 여부·언어)은 `buyer_attendees`에 이미 존재**하므로 재사용한다(중복 신설 금지).
- 매칭과 무관한 **운영 로지스틱스** 데이터다. 입력 권한은 ADR-0012 관할대로 — sub(무역관)는 자기 관리 바이어, master는 전체, 그 외는 열람.

## Considered Options

- **적재: PDF 그대로 전면 self-register + 승인 (기각).** 국내기업·바이어 모두 자가등록으로 열면 ADR-0007의 스냅샷 진실 원천·무가입 게이트가 무너진다. 국내기업은 DX Korea가 원천이라 자가등록이 불필요·위험.
- **적재: 스냅샷 일원화(무역관은 열람·대리신청만) (기각).** 무역관 모집 바이어를 주관사 스냅샷에 끼워 넣어야 하는데, 이들은 DX Korea 신청자가 아니라 회원ID가 없고 현지 모집 현실과 맞지 않는다.
- **적재: 운영자 직접입력 + 스냅샷 공존 + master 승인 (채택).** 두 현실(국내=스냅샷 / 해외=무역관 직접)을 각자의 진실 원천에 맞추고, 품질 게이트는 기존 승인 상태머신을 재사용.
- **대리신청: 운영자 행위로 기록(`requested_by='organizer'`) (기각).** Forced와 기록상 구분이 흐려지고, 미팅 당사자(바이어↔참가사)와 행위자를 혼동시킨다.
- **체류정보: 바이어 회사 단위 1묶음 (기각).** 일행의 개별 항공/호텔을 표현 못 하고, 이미 참석자별인 통역과 단위가 엇갈린다.

## Consequences

- **스키마(파생 — db-schema-keeper로 동기화):**
  - `meetings`에 **대행 운영자 도장** 컬럼 추가(nullable FK → `organizers`, 예: `proxy_applied_by_organizer_id`). 대리신청만 채워지고 일반 신청은 NULL.
  - **체류정보**를 `buyer_attendees`에 부착 — 항공·숙박 필드(도착/출발 편명·일시, 호텔·체크인/아웃). 통역 필드는 기존 것 재사용(신설 없음). (1:1이므로 컬럼 추가 또는 `buyer_attendee_stays` 1:1 보조표 중 db-schema-keeper가 결정.)
  - 운영자 직접입력 바이어는 `Registrant` 없이 `organization_event_role`(ADR-0012의 `managing_organizer_id`/`created_by_organizer_id` 사용)로 직접 생성됨 — 신규 테이블 불필요. `Registrant.organizer_member_id`(NOT NULL·unique)에 의존하지 않는 경로임을 적재 서비스가 보장해야 한다.
- **ADR-0007 보완(대체 아님):** 스냅샷·무가입 원칙은 유지하되, **운영자 대리등록**이라는 두 번째 적재 경로가 공존함을 명시(국내=스냅샷 / 무역관 해외바이어=직접입력+승인).
- **ADR-0005 적용:** 대리신청은 기존 수락 규칙으로 완전히 포섭됨(새 규칙 없음) — 받는 쪽 참가사 → `proposed`.
- **#110(무역관 sub 콘솔) 언블록:** 바이어 직접 등록·대리신청·체류정보 입력의 도메인 계약이 확정됨. 콘솔은 `managing_organizer_id` scope 가드(capability+scope, ADR-0012/0008) 위에서 이 세 행위를 구현한다. (단 #110은 #108 실 인증 배선에도 여전히 의존.)
- **인증 미해결(주관사/KOTRA 의존, backlog):** 운영자 대행 바이어가 v1에서 본인 로그인을 전혀 안 한다면(현장 일정 열람 등 포함) 별도 인증 경로 불필요. 추후 본인 접근이 필요해지면 그때 별도 인증(예: 매직링크) 슬라이스로 다룬다.

### 구현 전 닫아야 할 가드레일 (codex 교차검수 2026-06-29 반영 — 대부분 #110 구현 소관)

- **중복·병합 정책(master 전용):** `organizations`엔 자연 unique 키가 없어 "같은 해외 바이어를 두 무역관이 입력" 또는 "직접등록분이 나중에 주관사 스냅샷에 회원ID로 등장"을 DB가 자동으로 못 막는다. 병합/재배정은 **master 전용 운영 행위**로 처리한다(소유는 `managing_organizer_id` 재배정 가능 — ADR-0012). 키 부재는 의도된 것이며, 정책으로 메운다.
- **대행 도장 불변식(app 강제):** `proxy_applied_by_organizer_id`는 **`requested_by='buyer'` ∧ `matching_type='open'`** 일 때만 채운다. 행위 운영자는 해당 행사 scope + **그 바이어를 관할**해야 한다(capability+scope, ADR-0012). DB CHECK가 아니라 FastAPI 단일 지점에서 강제.
- **체류정보 변이 위험(중요):** 현재 `bm/service.py`는 프로필 패치 때 `buyer_attendees`를 **전체 delete-recreate** 한다 — 체류(항공·숙박)가 같은 행에 있으면 일반 프로필 편집이 체류 데이터를 **조용히 날린다**. 구현은 ① 패치에서 체류 필드를 보존하거나 ② 안정 키(예: `buyer_profile_id`+`email`)로 체류를 분리 보관해야 한다. 보조표로 옮겨도 FK cascade로 같이 죽으므로 **변이 로직 수정이 본질** — 단순 테이블 분리로 해결되지 않는다. 도메인 단위(참석자별)는 불변.
- **무로그인 운영 플로우(v1 명시):** 운영자대행 바이어는 본인 로그인이 없으므로 미팅 **열람·수락·취소·현장 체크인**을 **무역관이 대행**한다 — CONTEXT의 "바이어 누구나 취소"는 이들에겐 *운영자 대행*으로 충족된다. 알림 수신 주체도 무역관.
- **승인 후 편집 의미:** 현재 submit 로직은 재편집 시 `approved`를 보존한다. **체류·로지스틱스 편집은 승인 유지**, **매칭 노출 프로필 편집**이 재검토(`submitted` 회귀)를 트리거할지는 #110에서 확정(로지스틱스/프로필 편집 분리 권장).
- **파생물 정합(#110 구현 TODO):** 이 ADR는 파생 ERD(`schema.sql`)만 동기화했다. **runtime 진실원천인 `models.py`(`Meeting`·`BuyerAttendee`)와 Alembic 마이그레이션은 #110 구현 슬라이스에서 추가**한다 — codex가 schema↔models drift로 [P1] 표시했으나, 설계 단계의 의도된 분리다(ADR-0008: schema.sql=파생, Alembic=진실).
