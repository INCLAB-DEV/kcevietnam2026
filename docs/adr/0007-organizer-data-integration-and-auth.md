# 주관사 데이터 연동·인증 — 전체 스냅샷 파일 동기화 + 딥링크 진입 + DX Korea 인증 API(아이디/비번)

NABI는 참가사·바이어 명단을 주관사(DX Korea 2026)에서 받아온다. **데이터 적재와 인증을 분리**한다: 데이터는 **라이브 API 연동이 아니라 "주관사가 export한 전체 신청자 스냅샷을 운영자가 업로드 → NABI가 주관사 회원ID 키로 멱등 upsert"** 하는 파일 동기화(엑셀)로 적재한다. 인증은 적재된 명단 위에서 **딥링크(토큰) 진입 → DX Korea 인증 API 규격에 맞춘 아이디/비번 검증(1회) → 세션 생성 → 역할 자동 분기**로 처리한다. 데이터까지 라이브로 묶지 않아 주관사 IT 일정에 출시가 묶이지 않으면서, 신원 검증만은 주관사가 제공하는 인증 API로 확실히 한다.

## 데이터 연동

- **소스 = 주관사가 주는 전체 신청자 파일(CSV/엑셀) 스냅샷.** 변경분(delta)이 아니라 매번 그 시점 **전체**를 받는다 — 주관사가 변경분을 골라내는 건 비현실적이라, 전체를 주고 NABI가 흡수하는 게 가장 쉽다.
- **멱등 upsert(있으면 갱신, 없으면 추가)** 로 import한다. 같은 파일을 여러 번 올려도 중복이 안 생기고 최신값으로 덮어쓴다.
- **안정적 키 = 주관사가 모든 등록자에 부여하는 회원ID(또는 신청ID).** 이 키로 "같은 레코드"를 식별해 upsert/갱신한다. 키 조건은 **전 레코드에 100% 존재 + 출처(주관사)가 안정적으로 유지**다.
  - **사업자등록번호는 키로 쓰지 않는다** — 국내 법인에만 있어 **해외업체·개인 바이어는 결측**이고, 키가 비면 멱등성이 깨진다(매번 새 레코드로 꽂힘). 사업자번호는 **부가 속성**(있으면 저장)으로만 둔다.
  - **이메일은 보조 대조용**(회원ID 결측·충돌 시 fallback).
  - **연동 협의 1순위 = "전 레코드 고유·안정 ID(회원ID)를 데이터에 반드시 포함시켜 달라"** (사업자번호 아님).
- **운영 방식:** 주관사가 신청기간(8/26~9/11)엔 주기적으로(예: 매일 1회), 이후엔 수시로 전체 명단을 줌 → **운영자가 OP-002에서 직접 업로드** → NABI가 upsert. v1은 자동화·라이브 연동 없이 운영자 수동 업로드로 충분.
- **모든 신청자 = 비즈매칭 신청자뿐 아니라 전체 등록자**를 받는다. 적재된 등록자(Registrant) 중 비즈매칭 프로필을 작성한 기업만 매칭 엔진에 들어간다(용어는 CONTEXT.md `Registrant` 참조).

## 인증

- **딥링크 토큰**(긴 랜덤·만료)으로 로그인 화면 진입 → **DX Korea 인증 API 규격에 맞춰 아이디/비번 검증(1회)** → 세션 생성.
- 딥링크 토큰만으론 부족하다(포워딩·유출 시 제3자 진입). **신원의 닻을 "링크"가 아니라 "주관사(DX Korea)가 보유한 회원 계정"** 에 둔다 — 로그인하려면 그 사람의 DX Korea 아이디/비번을 알아야 하므로 외부인을 차단한다. (구버전의 "등록 연락처 OTP"를 대체)
- **인증 성공 시 DX Korea가 돌려주는 회원ID로 적재 레코드를 매핑**한다 — 파일 동기화 시 upsert 키로 쓴 회원ID와 동일 키라 인증 결과가 적재 명단에 깔끔히 연결된다.
- 매칭·권한은 **Organization 단위·플랫**이라 같은 기업 내부 사용자 교체는 문제가 아니다(ADR-0002). 막아야 할 대상은 회사 밖 외부인이며 아이디/비번 검증이 이를 막는다.
- 로그인 후 **역할(참가사/바이어/둘 다)은 적재된 명단 레코드에서 읽어 자동 분기**한다.
- **운영사도 같은 로그인 화면(AU-001)을 쓴다.** 단 운영사는 주관사 명단(roster) 밖의 **NABI/주최 내부 계정**(소수, 별도 발급)이라 import·딥링크·DX Korea 인증 대상이 아니다(자체 계정으로 인증). 로그인 후 역할 분기로 운영사 → `/organizer`(OP-001), 참가사/바이어 → `/home`(HM-001).
- **공개 자체 회원가입은 열지 않는다**(진입은 딥링크 + 당일 QR Visitor만). 단 **DX Korea 인증 성공 후 최초 진입 시 NABI 자체 계정을 발급**한다 — 비즈매칭 정보동의 **약관 동의(방산=민감정보)를 1스텝으로 받고** NABI 계정(Cognito 유저풀)을 생성해 DX Korea 회원ID·적재 레코드에 연결한다. **공개 가입이 아니라 DX Korea 검증을 통과한 사람만 받는 게이트된 가입.** 이후 로그인은 NABI 계정(Cognito) 세션으로 처리한다. 약관 동의 이력(약관 버전·동의 시각)은 감사 가능하게 저장한다. (구버전의 "약관 v1 미구현(backlog)"을 **v1 범위로 승격**)

## Considered Options

> 데이터 연동과 인증을 별개 축으로 평가한다.

- **데이터: 라이브 API 연동 (기각):** 실시간·자동이지만 **주관사가 데이터 제공 API를 개발·노출·보안책임**져야 한다. 그 일정에 NABI 출시가 묶이고, 일회성 이벤트엔 과한 통합 비용. 데이터 제공측 API는 우리가 만들 수 없는 영역.
- **데이터: DB 직접 접근 (기각):** 결합도·보안 위험 큼.
- **데이터: 전체 스냅샷 파일 동기화 (채택):** 주관사 부담은 export 버튼 수준. 이미 엑셀 명단을 보유 중이라 즉시 시작 가능.
- **인증: 자체 OTP(등록 연락처) (기각):** DX Korea가 회원 인증 API를 제공하므로 NABI가 별도 OTP 채널(이메일/SMS 발송·검증)을 운용할 필요가 없다. 주관사 계정에 직접 신원을 닻 내리는 편이 더 강한 보증.
- **인증: DX Korea 인증 API 아이디/비번 검증 (채택):** *데이터*가 아니라 *인증*만 라이브로 붙는다. 주관사가 이미 운용 중인 회원 인증을 그대로 쓰므로 통합 비용이 작고, 신원의 닻이 주관사 회원 계정이라 가장 확실하다. 인증 API 규격은 주관사 합의로 닫는다(backlog).

## Consequences

- **소스 교체 가능성을 열어둔다.** 회원ID 기반 멱등 upsert 파이프라인을 고정해두면, 추후 주관사가 API를 제공할 경우 **"운영자 파일 업로드" 부분만 "API pull"로 교체**하면 된다 — 뒷단(upsert·키·매칭)은 불변. API는 상대측이 개발해야 우리가 붙는 구조.
- **지각 신청(신청기간 마감 후)에 별도 플로우·페이지가 필요 없다.** 전체 신청자가 계속 동기화되므로 지각 기업도 이미 등록자로 DB에 있고, **유형(참가사/바이어) 무관·컷오프 없이** 로그인 → 비즈매칭 프로필 작성 → 매칭에 합류한다. AI 전체 포화배정이 **반복 실행 가능**해졌으므로(ADR-0006) 지각분은 다음 포화배정 재실행 또는 보정채널(Open·재트리거·Forced)로 합류한다. On-site(현장 바이어 — 구 Visitor 자기전환이 유일 생성 경로였으나 폐지: 2026-07-02, 별도 정책 변경 전까지 생성 안 함)와는 별개 경로.
- **미해결(주관사 의존):** 실제 파일 전달 채널(이메일/공유드라이브/SFTP), **전 레코드 고유·안정 ID(회원ID) 제공 여부**, 그리고 **DX Korea 인증 API 규격(엔드포인트·인증 방식·회원ID 반환 여부)** 은 주관사 합의로 닫는다(backlog).
- **두 번째 적재 경로 공존(ADR-0013).** 위 스냅샷·무가입 원칙은 **주관사 회원ID가 있는 모든 신청자**(국내기업·국내외 바이어 — 위 회원ID 키가 해외업체·개인 바이어도 커버하므로 국적 무관)에 그대로 적용된다. 단 **KOTRA 무역관이 현지 모집해 회원ID가 없는 해외 바이어**는 스냅샷에 없으므로, 운영자가 NABI에서 **직접 등록(대리등록)** 하는 별도 경로로 적재한다 — 공개 가입이 아니라 운영자 대행이며 master 승인 게이트를 거친다(ADR-0013). 가르는 축은 국적이 아니라 **상류 회원ID 유무**. 스냅샷은 add/update만(삭제 없음)이라 직접입력분을 덮지 않는다.
