1.보고 개요

1.1사업 개요 및 보고 범위

NABI는 MICE 방산 전시회를 대상으로 하는 AI 에이전트 기반 바이어–셀러 매칭 서비스다. 참가사와 바이어의 정보를 최대한 수집하여 매칭 정확도를 극대화하고, 그 효과를 정량적으로 입증하는 것을 사업의 핵심 목표로 한다. 발주기관인 마인즈그라운드(주)는 MICE 전문 대행사로서 복수의 행사를 연속 운영하는 것이 비즈니스 모델이며, 따라서 본 서비스는 특정 전시회 전용 시스템이 아니라 행사를 갈아 끼울 수 있는 플랫폼으로 설계된다.

본 보고서는 2026년 8월 28일 수행된 병렬 개발 사이클의 산출물을 정리한다. 해당 사이클은 개발계획서 §7(신규 요구사항) 및 §8(우선순위 긴급 개발 5건)에 대응하여, 7개 워크스트림을 동시에 진행하는 멀티에이전트 병렬 개발 방식으로 수행되었다. 보고 범위는 다음과 같다.

  • 기능 구현 — 알림·이메일, 슈퍼어드민 API, 엑셀 연동, 참가자 화면 정책, 슈퍼어드민 콘솔, 다국어, 회원가입/권한
  • 인프라·정합성 — 배포 차단 요인(P0) 해소, 마이그레이션 체인 정리, 스키마 파생 문서 동기화, 계약 문서 정리
  • 품질 보증 — 이종 벤더 크로스리뷰 프로세스와 그 성과, 실 PostgreSQL 첫 구동 검증

2.설계 원칙 및 기준 문서 체계

2.1멀티 행사 전제와 행사별 정책 설정

발주기관의 비즈니스 모델이 단일 행사가 아니라 연속되는 복수 행사의 운영이라는 점은 본 시스템의 최상위 설계 제약이다. KADEX with DX Korea 2026이 첫 적용 대상이지만, 그 다음에 베트남 전시가 오고, 그 다음에 또 다른 행사가 온다. 따라서 개별 행사의 운영 규칙을 코드에 새기는 것은 곧바로 기술 부채가 된다.

이번 사이클에서 이 원칙은 events 테이블의 정책 컬럼으로 구체화되었다. 운영 규칙 요구가 들어오면 조건문을 심는 대신 컬럼을 하나 세우고, 도메인 규칙 함수가 그 값을 파라미터로 받는다.

설계 판단

allow_same_role_discovery는 동일 역할 간 열람만 제어한다. 참가사와 바이어 사이의 열람은 이 플래그로도 막히지 않는데, 이는 매칭 서비스의 존재 이유에 해당하는 구조적 규칙이기 때문이다. 정책 파라미터가 흔들 수 있는 범위와 흔들면 안 되는 범위를 코드에서 명시적으로 분리하였다.

2.2의사결정 기록(ADR)과 기능정의서(PRD) 체계

본 프로젝트는 아키텍처 결정을 docs/adr/에, 기능 스펙을 docs/prd/에 분리 관리한다. 기준일 현재 ADR 13건(0001–0013), PRD 17건이 등록되어 있으며, PRD 파일명은 F-{기능ID}.md 규약을 따라 docs/page-list.csv의 화면 ID와 1:1 대응한다. 이번 사이클의 구현은 다음 ADR에 직접 근거한다.

  • ADR-0001 Organization 단일 엔티티 — 참가사·바이어를 하나의 organizations로 통합, 역할은 행사별 역할 행에서 부여
  • ADR-0002 매칭 단위는 Organization — 개인이 아니라 기업이 매칭 대상
  • ADR-0008 플랫폼 스택 AWS + 백엔드가 DB를 소유 — Next.js는 DB 직접 접속 없음
  • ADR-0010 알림 모델 — 조직 공유 인박스, 멱등 생성, 채널 팬아웃 (§4.1의 직접 근거)
  • ADR-0012 운영자 권한의 행사 단위 부여와 scoped sub — 3계층 권한 모델의 근거 (§3.3)

알림 타입은 단순 주석 규약이 아니라 실행 가능한 검증으로 묶여 있다. app/notifications/schemas.py는 임포트 시점에 assert set(get_args(NotificationType)) == set(models.NOTIFICATION_TYPES)와 assert set(PAYLOAD_MODEL_BY_TYPE) == set(models.NOTIFICATION_TYPES)를 수행한다. ORM 상수와 Pydantic 스키마가 어긋나면 애플리케이션이 기동하지 못하므로, 불일치가 런타임까지 흘러갈 수 없다.

3.시스템 아키텍처

3.1시스템 컨텍스트

NABI는 Next.js 16(App Router) 프레젠테이션 계층과 FastAPI 애플리케이션 계층으로 구성된 2-tier 구조이며, 두 계층의 경계는 ADR-0008에 따라 "FastAPI가 모든 DB 접근을 소유한다"로 고정되어 있다. Next.js는 데이터베이스에 직접 접속하지 않고, 브라우저의 요청을 same-origin 라우트 핸들러가 받아 FastAPI로 전달하는 BFF 2-hop 방식을 취한다.

3.2백엔드 수직 슬라이스 구조

백엔드는 계층(Controller–Service–Repository)을 가로로 자르는 대신 기능 단위로 세로로 자르는 수직 슬라이스 구조를 취한다. 각 슬라이스는 router.py(HTTP 경계) · service.py(트랜잭션 소유) · schemas.py(입출력 계약)를 자체 보유하며, 슬라이스 간에는 서로의 내부를 참조하지 않는다.

이 구조의 이점은 이번처럼 여러 워크스트림이 동시에 진행될 때 명확히 드러난다. 알림·어드민·엑셀 세 슬라이스가 같은 날 병렬로 작성되었음에도 파일 충돌이 발생하지 않았고, 각 슬라이스가 독립적으로 테스트 가능했다. 공통 로직은 두 방향으로만 새어나간다.

  • app/domain/ — I/O가 전혀 없는 순수 함수 모듈. visibility_rules.py(열람 범위), acceptance_rule.py(수락 모델), review_capture.py·review_provenance_binding.py(리뷰 귀속). DB도 HTTP도 모르므로 단위 테스트가 즉시 가능하다.
  • ports / adapters — 외부 세계와의 접점을 Protocol로 선언하고 구현체를 갈아 끼운다. NotificationChannel, EmailSender(SMTP↔Fake), SessionAuthenticator·EventOperatorDirectory(Cognito↔테스트 더블).
FastAPI 라우터 등록 현황

app/main.py는 기준일 현재 10개 라우터를 등록한다 — roster, auth, login, signup, consent, reviews, bm, excel, notifications, admin. 이 중 signup·excel·notifications·admin 4개가 이번 사이클에 신규 등록되었다. 앱 인스턴스는 리마인더 스케줄러를 lifespan으로 물고 있다 (lifespan=reminder_scheduler_lifespan).

3.3권한 모델

권한 체계는 ADR-0012에 따라 3계층으로 구성되며, 계층마다 부여 경로가 다르다. "어떤 권한을 누가 줄 수 있는가"를 API 설계 수준에서 강제하는 것이 이 모델의 핵심이다.

3.4멀티 행사 데이터 모델

데이터 모델의 중심은 events이며, 운영에 관계된 거의 모든 테이블이 event_id를 보유한다. 이는 "행사가 바뀌면 데이터가 완전히 분리된다"는 요구를 스키마 수준에서 보장하기 위함이다.

3.5알림 채널 포트 구조

알림은 ADR-0010에 따라 조직(Organization) 공유 인박스 모델을 취한다. 알림의 수신자는 개인이 아니라 기업이며, 한 명이 읽으면 조직 전체에 읽음으로 표시된다. 외부 채널(이메일 등) 발송만 소속 멤버 개인 연락처로 팬아웃된다.

크로스리뷰로 수정된 결함

이 get-or-create 경로에는 동시 요청 시 race condition이 있었다. 두 요청이 같은 member_id로 동시에 진입하면 둘 다 조회에 실패하고 둘 다 INSERT를 시도하여, 유니크 제약 위반으로 한쪽이 500 Internal Server Error를 반환했다. 이종 벤더 리뷰에서 발견되어 IntegrityError 포착 → 롤백 → 재조회 패턴으로 수정하였다(§6.2).

4.4참가자 화면 정책 3건

개발계획서 §8의 우선순위 요구 중 참가자 화면에 해당하는 3건을 구현하였다. 세 건 모두 베트남 전시 전용 값을 코드에 박지 않고 행사 설정값으로 구동되도록 하였다 (3번 항목은 후술하는 예외).

① 기업 탐색 상호 열람 차단

순수 판정 함수 visibleOrgs(viewerRole, orgs, allowSameRoleDiscovery)를 두고, 데이터 접근 계층에서 일괄 필터한다. 즉 뷰가 아니라 lib/api-client/server.ts의 getOrganizations()가 먼저 걸러내므로, 클라이언트 페이로드에 애초에 볼 수 없는 기업이 실리지 않는다. 여기에 더해 직접 URL 접근 (상세 페이지 → redirect)과 지연 조회 엔드포인트(→ 403)에도 같은 규칙을 적용하여 3중 방어를 구성하였다. 백엔드에도 동일 규칙의 순수 모듈 app/domain/visibility_rules.py가 존재하며, 운영자는 이 규칙 밖에 있어 전체를 열람한다.

② 미팅 장소 = 참가사 부스만

장소 카탈로그 자체는 3종(부스·매칭존·비즈니스룸)을 유지하되, getEventSettings().venueTypes로 필터한다. 현재 설정값이 ["booth"]이므로 선택지가 1개가 되며, UI는 선택지가 1개일 때 자동 선택하여 단계를 접는다. 운영자가 다른 장소 유형을 활성화하면 선택 단계가 자동으로 다시 나타난다 — 화면을 다시 만들 필요가 없다.

③ 참가사 폼 불가슬롯 UI 제거

§4.2에서 서술한 운영자 전용화에 대응하여, 참가사 신청 폼 4단계와 읽기전용 요약 탭에서 슬롯 그리드를 제거하였다. 이 항목만은 조건부가 아니라 정적 제거이다 — 권한 이동은 정책 토글이 아니라 업무 절차의 변경이므로 플래그를 두지 않았다. 관련 타입과 헬퍼 모듈은 어드민 콘솔이 재사용하도록 보존되어 있다.

행사 스위처 — 행사 간 완전 분리

콘솔의 핵심 장치다. 선택된 행사는 nabi_admin_event 쿠키(유효기간 1년, SameSite=Lax)에 저장되고, 8개 페이지 전부가 서버 컴포넌트에서 resolveAdminContext()로 이를 읽어 event.id를 데이터 클라이언트에 주입한다. 서버 측에서 scopeToEvent()가 적용되므로 다른 행사의 데이터는 클라이언트 페이로드에 실리지 않는다. 알 수 없는 쿠키 값이면 첫 번째 행사로 폴백하여 콘솔이 빈 화면으로 떨어지지 않는다.

2단 접근 제어

1단은 라우트 가드(proxy.ts)로 /admin* 전체를 organizer 전용으로 막고, 2단은 lib/admin/guard.ts가 권한 등급을 판정한다. master만 쓰기 가능이며, 알 수 없는 등급을 포함한 그 외 전부는 read-only로 폴백하는 fail-closed 설계다. 서브어드민에게는 쓰기 컨트롤이 렌더링되지 않는다.

mock seam — 실연동 전환 지점

콘솔은 현재 목업 데이터로 동작하며, 실 API 전환 시 수정할 지점이 소수 파일로 수렴하도록 설계되었다. 어드민에 한정하면 읽기는 lib/admin/server.ts 한 곳, 쓰기는 lib/admin/admin-actions.ts의 dispatch() 함수 한 개, 경로는 lib/admin/api-paths.ts에 집중되어 있다.

4.6다국어(i18n)

4.7회원가입 및 역할 체계

backend/app/auth/signup_router.py · signup_service.py · signup_schemas.py · local_verify.py

기존에는 DX Korea 딥링크 진입만이 유일한 계정 경로였으나, 자체 가입 경로를 추가하였다.

  • 엔드포인트 — POST /api/auth/signup. 201 생성 / 409 중복 / 422 검증 실패 / 404 대상 행사 없음.
  • 비밀번호 — bcrypt 해시(gensalt() 기본 cost 12). argon2-cffi 대신 bcrypt를 택한 것은 cffi 빌드체인 없이 설치되어 컨테이너 이미지를 단순하게 유지하기 때문이다.
  • 선택 가능 역할 — buyer, exhibitor 2종만.
  • 로그인 검증 체인 — LocalCredentialVerifier를 최우선에 배치하여, 자체 가입 계정이 DX Korea 인증 어댑터(현재 스텁)에 도달하지 않고 로컬에서 처리된다.

organizer 자체가입의 이중 차단

운영자 권한이 자체가입으로 획득되는 경로는 존재해서는 안 된다. 프런트엔드에서 이를 두 층으로 막았다.

  1. 컴파일 타임 — SignupRole = "buyer" | "exhibitor" 리터럴 유니온. "organizer"는 타입 오류가 된다. 이 보증은 @ts-expect-error 테스트로 고정되어 있어, 유니온이 넓어지면 그 테스트가 오히려 실패하도록 설계되었다.
  2. 런타임 — z.enum(["buyer","exhibitor"])로 제출 직전 재검증. UI 자체도 두 개 버튼만 렌더링하므로 organizer는 제시되지 않는다.

슈퍼어드민은 어떤 API로도 생성되지 않으며, DB 직접 부여만이 유일한 경로다. 그 절차는 backend/README.md에 문서화되어 있다. 여기에 대응하여 행사 생성 가드 (require_existing_master_identity)를 두어, 새 행사를 만들려면 이미 어딘가에서 master인 계정이어야 한다 — 최초 1건은 반드시 DB 부트스트랩을 거친다.

6.품질 보증 — 이종 벤더 크로스리뷰

6.1방법론: 작성자 ≠ 리뷰어, 벤더 교차

본 사이클은 AI 에이전트를 병렬 투입하는 개발 방식을 취했다. 이 방식의 가장 큰 위험은 같은 오답에 함께 수렴하는 것이다. 유사한 모델을 여러 개 붙여 다수결을 하면 리뷰어 수를 늘려도 검출력이 비례해 늘지 않는다 — 비슷한 학습 분포를 가진 모델은 비슷한 실수를 비슷하게 놓치기 때문이다.

따라서 리뷰어를 늘리는 대신 다르게 틀리는 리뷰어를 섞는 원칙을 채택하였다.

크로스리뷰 2원칙

원칙 1 — 작성자 ≠ 리뷰어. 자신이 작성한 코드는 자신이 리뷰하지 않는다. 작성 시점의 가정이 리뷰 시점에도 그대로 유지되어 검증이 자기확인으로 전락하는 것을 막는다.

원칙 2 — 벤더 교차. Claude가 구현했으면 Qwen이 리뷰하고, Qwen이 구현했으면 Claude가 리뷰한다. 서로 다른 실패 모드를 가진 리뷰어를 배치하여 사각지대를 줄인다.

7.1판정 기준과 보고 취지

앞의 §4–§6이 이번 사이클에 무엇을 만들었는가를 다뤘다면, 본 장은 지금 이 순간 어디까지 실제로 동작하는가를 기능정의서(PRD) 단위로 정리한다. 프런트엔드와 백엔드가 병렬로 진행되는 프로젝트에서는 "양쪽 다 만들었는데 아직 연결되지 않은" 구간이 필연적으로 생기며, 이를 구분하지 않으면 진행률이 과대 보고된다.

본 장에 기재되는 미구현 항목은 이번 사이클의 미달이 아니다. 2026-08-28 사이클의 범위는 개발계획서 §8 우선순위 긴급 개발 5건과 §7 신규 요구 일부로 한정되어 있었고, 그 범위는 §4에 기재한 대로 전량 완료되었다. 본 장이 다루는 것은 애초에 이번 범위 밖에 있던 잔여 개발 항목이며, 사업 개발기간은 2026년 12월 31일까지다. 따라서 아래 표는 "부족분"이 아니라 남은 일정에 배치할 작업 목록으로 읽어야 한다.

10.결론 및 다음 단계

10.1결론

2026년 8월 28일 사이클을 통해 NABI 비즈매칭 서비스는 운영자 도구 계층을 완비하고 배포 가능한 상태에 도달하였다. 구체적으로,

  • 7개 워크스트림을 병렬로 완주하여 알림·어드민·엑셀·회원가입 등 운영 필수 기능을 실 코드로 확보하였다.
  • 발주기관의 멀티 행사 비즈니스 모델을 events 정책 컬럼과 행사 스위처로 구현하여, 다음 행사를 코드 변경 없이 수용할 수 있는 구조를 마련하였다.
  • Alembic 단일 head 수렴과 컨테이너 이미지 신규 작성으로 배포 차단 요인을 전량 해소하였고, 실 PostgreSQL 17에서 16개 리비전 클린 적용과 테스트 1,182건 전량 통과를 확인하였다.
  • 이종 벤더 크로스리뷰 프로세스를 통해 단일 리뷰로는 검출되기 어려운 결함 3유형 (계약 불일치·동시성·정책 공백)을 사전 제거하였고, 실 DB 첫 구동에서 프로덕션 500 결함 1건을 배포 전에 잡아냈다.
  • 실 환경 E2E 검증으로 운영자 업무 축 전 구간의 실동작을 확인하였고, 단위 테스트로는 드러나지 않는 통합 계층 결함 2건(CORS 자격증명 헤더, 운영자 디렉터리의 DB 미참조)을 추가 검출하여 수리·재검증까지 완료하였다. 후자는 행사가 2개 이상일 때 어드민 콘솔이 붕괴하는 결함으로, 멀티 행사 운영이라는 사업 전제에 직결되는 사안이었다 — 수리 후 행사 2건 상태에서 정상 동작을 확인하였다.

동시에, 남은 개발 범위도 명확해졌다. §7에서 정리한 대로 운영자 업무 축은 실 DB 기준으로 닫혀 있으나, 참가자 업무 축은 중간 구간(승인 심사 → 탐색 → 미팅)의 백엔드가 비어 있다. 이는 이번 사이클의 미달이 아니라 애초에 이번 범위(개발계획서 §8 긴급 5건 + §7 일부) 밖에 있던 잔여 로드맵이며, 개발기간이 2026년 12월 31일까지인 점을 고려하면 일정상 여유가 있다. 다만 그중 매칭 엔진(F-OP-005)만은 fit score 정의가 확정되지 않아 착수 자체가 대기 상태이며, 이는 기술적 준비 부족이 아니라 의사결정 대기이므로 최우선 해소 대상이다.

부록 B. 용어 정리

Organization (기업)
참가사와 바이어를 통합한 단일 엔티티(ADR-0001). 역할은 행사별로 organization_event_roles가 부여한다. 매칭의 단위이기도 하다(ADR-0002).
Organizer (운영자)
행사 운영 주체 계정. 행사 단위로 master 또는 sub 권한을 가진다(ADR-0012). 전역 master 개념은 없다.
관할 (Jurisdiction)
서브어드민이 볼 수 있는 범위. managing_organizer_id로 연결된 자신의 바이어에 한정된다.
행사별 정책 (Event Policy)
events 테이블의 slot_minutes·enabled_venue_types· allow_same_role_discovery. 행사마다 다른 운영 규칙을 코드 변경 없이 수용하는 장치.
mock seam
목업 구현과 실 API 구현을 교체하는 지점. 호출부를 수정하지 않고 파일 내부 또는 환경변수만으로 전환되도록 설계된 경계.
BFF 2-hop
브라우저 → Next.js 라우트 핸들러(same-origin) → FastAPI로 이어지는 2단 호출. Next.js는 DB에 직접 접속하지 않는다(ADR-0008).
수직 슬라이스 (Vertical Slice)
계층이 아니라 기능 단위로 코드를 분할하는 구조. 각 슬라이스가 router·service·schemas를 자체 보유한다.
fail-closed
판단이 불확실하면 허용이 아니라 차단·실패 쪽으로 떨어지는 설계. 권한 등급 판정, SMTP 자격증명 검증, 어드민 쓰기 가드에 적용되었다.
멱등 (Idempotent)
같은 요청을 여러 번 수행해도 결과가 한 번 수행한 것과 같은 성질. 알림 생성과 명단 임포트에 적용되었다.
대리작성 (Proxy Profile)
명단만 반입되고 회원가입하지 않은 기업의 신청서를 운영자가 대신 작성하는 것. proxy_written_by_organizer_id에 감사 기록이 남고, application_status는 registered(미신청)를 유지한다 — 대리작성은 제출이 아니다.
귀속 (Provenance)
미팅이 어떤 경로(AI 추천/직접 신청 등)로 성사되었는지의 출처 정보. 리뷰가 이 귀속에 묶인다(ADR-0004).
